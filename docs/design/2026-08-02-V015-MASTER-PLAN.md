## 2b. Milestone review cadence (binding, added 2026-08-03)

Independent cross-family review at **stage boundaries**, not only when something feels wrong. Three
of these have already paid for themselves: the first rewrote this plan (rev 1 -> rev 2), the second
found that every D-036 arm had been delta-scoped to *test* files leaving ~1,932 lines of production
code unreviewed, and the third caught four defects in the Runtime C goal *before* dispatch — including
a repair instruction that could not work.

| # | Fires at | Question it must answer |
|---|---|---|
| M1 | plan written | is the plan itself sound? ✅ rev 1 -> rev 2 |
| M2 | integration merge complete | did anything get lost, and what is unreviewed? ✅ found the production-code gap |
| M3 | before dispatching a large lane | is the frozen goal correct *before* a worker burns on it? ✅ 4 defects caught |
| M4 | last build lane complete | is the tree ready to freeze? |
| M5 | after the full exact-SHA gate, before landing | is the release candidate actually releasable? |
| M6 | after production rollout | did production match what we proved locally? |

Rules that make these worth running:

- Review the **artifact**, not a summary of it — hand over paths, not prose.
- A review that returns no findings is a result; a review that returns only praise was mis-scoped.
- Findings go into the artifact they concern, with superseded lines kept and marked dead.
- **A milestone review is not a substitute for a D-036 arm**, and a D-036 arm is not a substitute for
  a milestone review. The first asks "is this plan right?", the second asks "is this diff right?".

Reserve them for genuine boundaries and for the case where several attempts at one problem have
failed. Running one per routine checkpoint dilutes the signal and wastes the budget.
