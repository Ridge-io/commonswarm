## 4. The mention merge

`mergeMentionRecipients` is correct in one session: a tag adds, a removed key stays out while it remains in `applied`, a refused tag is remembered so the cap notice does not fire every keystroke.

That memory dies with the body restore in (1). After reload, workspace switch, or failed send, the same tag is “fresh” and is added with no new keystroke.

Ambiguous names are not stored in `applied`. They stay in the notice only while `notice === composerToNotice`; that part does not chatter.

A cap refusal is named once, then cleared on the next pause because `fresh` is empty and `notice` becomes `""`. The name is not silent on first refuse. It is gone on the next debounce while `@Dana` is still in the box.

## 5. The one-signal rewrite

Success: one pending id, one post, pending swapped for the posted row, `rememberComposerTo`, draft cleared. Catch: `landed === (posted !== null)`; Retry only when nothing landed and the channel is still this one; a throw after the post does not put the body back. That is the right one-signal failure model.

Broken case, same applied hole:

1. Chip for River removed, `@River` still in the body. Send posts `[Orbit]`, `commandId` A.
2. `composerToApplied = []` runs **before** the await.
3. Network error; server actually accepted A (`posted` stays `null`).
4. Body restored. Retry runs the mention pass, River joins, `audienceKey` changes, **new** `commandId` B.
5. Two signals. A is Orbit. B is Orbit+River.

That is a double-post the idempotency key cannot collapse, and it relights Retry after A has landed.

I did not find a ghost pending row on the happy failure path: `pendingId` is dropped in both success and catch. Workspace change during post returns without that cleanup, but `resetComposer` already ran on the switch.
