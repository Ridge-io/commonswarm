## Checks to attack

1. **Hidden recipient.** If a roster change happens mid-draft (`renderRoster`), `composerTo` is pruned and the To: row immediately hides the removed recipient. However, if this happens while a send is in flight (during the `await postBrowserSignal` pause), the `recipients` array was already captured by the submit closure. The message goes out addressing the pruned recipient, but the To: row on screen no longer shows them.
2. **The wire body.** `browserSignalCommand` accepts both `recipients` and `placement` with `threadRootId`. If the client passes both (e.g. a thread reply with recipients), it builds a body containing both `to` and `thread_root_id`. The served edge (in `channels.ts` `postSignalFieldProblem`) will refuse this body with: `"A thread reply is readable by everyone who can read its thread, so it cannot also be addressed to a recipient."`
3. **The wake claim.** The claim "for every set the cap allows" is false. If the set contains multiple agents, the edge ledger only records a delivery for recipient 0. The local listener (`delivery.ts`) refuses deliveries where `toAgent` (recipient 0) is not its own principal. Thus, only recipient 0 is ever woken, and the client's `browserSignalKind` truthfully sets `"ask"` only if an agent is at the front, rendering `"note"` otherwise.
4. **The mention merge.** Type a tag that is over the cap. It is refused, but its name is added to `applied` so the notice doesn't repeat. Then, remove a *different* chip from the To: row to make room. Press space to trigger the debounced pass. The refused tag is NOT added back to the To: row because it is already marked in `applied`, and no notice is shown. It silently cannot be added back.
5. **The one-signal rewrite.** If a workspace switch (`workspaceId !== activeWorkspaceId`) or auth reload (`version !== requestVersion`) happens while a send is in flight, the submit handler returns early. The `signals.unshift(optimisticSignal)` was already executed before the try block, leaving a ghost pending row in the `signals` array. This case is byte-identical to main (the early return and array push were already there).
6. **Generated versus typed.** The phrase `"No agent is notified. Everyone here can read this."` and `"Orbit is notified. Kenji Ito can read this and reply."` are typed directly into the `mobile-measurements.json` as hardcoded strings rather than being built from the enforcing constants. 
7. **Retired claims.** The design doc states that "the 80px budget it bought is spent". However, the mobile measurements show the resting composer height increased from ~80px to `99.38px` (at 390x844) and `128.81px` (at 320x568), which means the budget is not just spent, it is actively exceeded.
8. **THE CLASS.** 
- `restoreComposerTo`: reads `localStorage`, writes `composerTo` and clears `composerToApplied`. (Move together).
- `restoreComposerDraft`: body is replaced by draft text, `composerTo` and `composerToApplied` read from draft. (Move together).
- `applyComposerMentions`: reads body, updates `composerTo` and `composerToApplied`. (Move together).
- Submit flush: body cleared, `composerToApplied` cleared, `composerTo` kept. (Move together: text is fresh, previous chips remain for the next message).
- `selectChannel`: both cleared. (Move together).
- **Further instance:** `renderRoster()` prunes `composerTo` but leaves `composerToApplied` alone and does not remove the tag from the body. A removed member remains in the text and in the applied record. A point fix would only close this door. The true cause of the family is that `composerTo` and `composerToApplied` are derived state from the body and the roster, but are being manually synchronized across multiple disconnected event handlers instead of being a single derived reactive pass.
9. **The controls.** The `mutate.mjs` test expecting `secondTag: a second tag adds rather than replacing` fails for the wrong reasons. Breaking the clear of `composerToApplied` (which runs *after* a send) makes the test fail because state leaks to the *next* message, not because the second tag in the *same* message replaced the first. Removing `chip.dataset.composerToNotified` fails the same test because the DOM selector relies on that styling hook, not because the logic of adding a second tag broke.

VERDICT: FAIL
