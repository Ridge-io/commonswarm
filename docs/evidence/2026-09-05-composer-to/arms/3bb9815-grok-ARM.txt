## 2. The token

Bumped in exactly two places: `const sendToken = ++composerSendToken` at submit (`7689`) and `composerSendToken += 1` in `resetComposer` (`3585`). That is enough.

- Refresh / retry / roster reopen: no `resetComposer`, token unchanged, the in-flight send still owns the flag and may lower it.
- Switch or sign-out: `resetComposer` runs (`5747`, `5463`). Token moves. The in-flight send cannot lower a later send's flag and cannot write its body into the new box.
- Return with no second send: token moved twice. Failure does not restore. `returnedBeforeItFailed` is the control that can tell this from a later send invalidating the earlier one on its own.
- Two submits on the same composer: `composerSending` blocks the second (`7532`) until the first finally runs.

I did not find a sequence where the wrong send lowers a flag, or where a send that still owns its composer fails to lower one. Wraparound is not a practical case.

## 3. The catch's new order

Send work first (`7848–7857`), then the box-guard (`7864–7878`), then screen work. Previews: unsent + box still this send's keeps them (they go back in the box). Unsent + box not this send's revokes from `attachmentSnapshot` (`7874`). A render throw after the success-path revoke can revoke again; `URL.revokeObjectURL` on an already-revoked URL is a no-op.

Screen writes in the catch sit behind `boxIsStillThisSends`. A switch does not put `rawBody` or the error into the box the reader moved to.

## 4. The settle

`syncComposerAddress()` only when token and workspace still match (`8003–8014`). `persistComposerDraft` inside it uses the live key. The live key equals `sendDraftKey` on that path.

`clearComposerDraft(sendDraftKey)` runs for any landed post, after that settle (`8020`). It names the captured key, so it cannot remove a draft the reader is writing in another workspace. On a landed same-workspace finish it removes the draft the settle just wrote, which is the rule: a sent message is not one being written. On a failed send `posted` is null, so the restored body stays.

Removing `await sampleSendWindow()` makes the whole try/finally finish in that turn, so `sawFlagUp` is false and the mutation names that assertion.

Each named mutation can fail for the reason it names:

- Restoring the old `requestVersion` lift leaves the flag up under Refresh. If the sample reopen did not bump the generation, that entry would report NOT CAUGHT. That is the proof the bump is reached.
- Restoring the old catch guard skips the restore under Refresh. `restoreComposerOnEntry` does not paper over it: `restoredComposerKey` is already this workspace (`3232`), so the restore is a no-op and the box stays empty.

- Dropping the `sampleSignals` write makes the second Refresh miss the row. The first Refresh can copy the store before the post lands; the assertion is on a later Refresh, which is the refetch the store exists for.
- Dropping the persist-while-sending guard lets the switch flush the emptied box.

`unsentBodySurvivesSwitch` and `resentOnce` have no `sawFlagUp` of their own. They follow `switchedUnderFailedSend`, which does. That is a continuation, not a vacuous step.
