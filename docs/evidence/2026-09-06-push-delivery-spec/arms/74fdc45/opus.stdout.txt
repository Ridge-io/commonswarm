## PART 2 — DEFECTS

### D1. §2.2 W4 — the wake trigger as specified CANNOT SEND, and its own guard hides that forever

**Claim.** `swarm.wake_agent_delivery()` … `SECURITY DEFINER`, owner `swarm_admin`, `SET search_path = pg_catalog`, "because `swarm_command` cannot execute `realtime.send`"; body wrapped in `EXCEPTION WHEN OTHERS THEN RETURN NULL`. Same for `swarm.wake_workspace_signal()`. §9 adds "the `realtime.send` grant to `swarm_admin` [is] not in the repo (locally `EXECUTE` is `PUBLIC`)".

**What is wrong.** `swarm_admin` cannot reach schema `realtime` at all:
```
has_schema_privilege('swarm_admin','realtime','USAGE')          -> false
has_table_privilege('swarm_admin','realtime.messages','INSERT') -> false
has_function_privilege('swarm_admin','realtime.send(...)','EXECUTE') -> true
rolsuper / rolbypassrls for swarm_admin                         -> false, false
```
Live probe with positive control. Two byte-identical `SECURITY DEFINER` plpgsql functions, `SET search_path = pg_catalog`, both `PERFORM realtime.send('{"v":1}'::jsonb,'wake',t,true)`; the first in schema `swarm` altered to `OWNER swarm_admin` (verified `owner=swarm_admin secdef=true`), the second left owned by `postgres`. Both granted EXECUTE to `swarm_command`, both called after `SET LOCAL ROLE swarm_command` — exactly what `command/index.ts:1377` does:
```
SELECT swarm.zz_wake_probe_admin('cswarm-wake:PROBE-ADMIN');
  ERROR:  permission denied for schema realtime
  LINE 1: SELECT realtime.send('{"v":1}'::jsonb, 'wake', t, true)
  CONTEXT: PL/pgSQL function swarm.zz_wake_probe_admin(text) line 3 at PERFORM

positive control, same session:
SELECT zz_wake_probe.as_postgres('cswarm-wake:PROBE-POSTGRES');
  -> cswarm-wake:PROBE-POSTGRES | 1   in realtime.messages
```
Both dropped; `leftover_funcs=0, leftover_schema=0, leftover_msgs=0`.

**Consequence.** The failure lands inside the body W4 deliberately wraps in `EXCEPTION WHEN OTHERS THEN RETURN NULL`. The delivery row commits, the listener's join succeeds, `cswarm listen status` reads `mode: "push"` because `state === subscribed` is genuinely true, and **no wake is ever sent**. Every seat silently runs on the 5-minute reconcile with nothing reporting a fault — the exact false-success shape §2.3's status rule exists to stop.

The stated **reason** is also wrong. `realtime.send` is SECURITY INVOKER with `proacl = =X/supabase_admin,…` (EXECUTE to PUBLIC), so `swarm_command` *can* execute it; what it lacks is USAGE on schema `realtime` and INSERT on `realtime.messages`. `activity/index.ts:139-145` works because `RESET ROLE` restores the **connection** role (postgres), not because it becomes `swarm_admin`. And `realtime.send` swallows its own INSERT failure with `RAISE WARNING`, so a privilege blocking only the INSERT gives a silent no-op.

**Fix.** Either own both trigger functions with the connection role (`postgres`/`supabase_admin`, matching the control and the activity precedent), or have L2 `GRANT USAGE ON SCHEMA realtime TO swarm_admin` + `GRANT INSERT ON realtime.messages TO swarm_admin`. §9's sentence must be rewritten: EXECUTE is not the binding privilege and the local state is *not* already sufficient. L2's listed test must assert the **row**, never the absence of an error — the guard guarantees there is no error.

### D2. §2.2 W3.1 / §4.1 / §6 — no lane owns the database change the read edge needs, so the watcher can never learn a topic

**Claim.** W3.1: the read edge's inbox page "gains an optional `wake: { topic, event }`… how the watcher learns it without ever calling a command." §4.1 makes it the watcher's only source. §6 gives L3 `read/index.ts`; L2's enumerated migration contains no read-path grant or function change.

**What is wrong.** The read edge runs as `swarm_read`:
```
read/index.ts:417   SET LOCAL ROLE swarm_read
has_table_privilege('swarm_read','swarm.agent_principals','SELECT') -> false
```
`swarm_read`'s only reach into principals is EXECUTE on `swarm.agent_delivery_read_context(bytea,uuid)` (`20260731000001:487`), whose live signature is a fixed ten-column `RETURNS TABLE(token_id, principal_id, owner_user_id, principal_workspace_id, run_id, device_id, first_use, membership_revoked_at, is_revoked, pending_delivery_count)` — no wake column, and `read/index.ts:437-451` selects exactly those ten.

The escape hatch is closed too. `swarm_read.agent_principals` exists but is `WHERE swarm.is_member(workspace_id, auth.uid())`, and the agent branch installs no `request.jwt.claims` (only the human branch does, `:421-428`), so `auth.uid()` is null and the view returns no rows for an agent.

**Consequence.** W3.1 requires a migration — a grant, a view column, or an extra output column on `agent_delivery_read_context` (which cannot be `CREATE OR REPLACE`d, since the OUT list changes: DROP/CREATE plus re-GRANT). All three are L2's file; L2 lists none, and L3 owns no migration. The **listener** could eventually get its topic from a claim (W3.2 is fine — `swarm_command` does hold SELECT, measured true). The **watcher** cannot: `arrival-watch.ts:336-338` enforces the read-only invariant, and §4.1 leans on W3.1 by name. Requirement (4) of the ask is unbuildable in the order §6 gives.
