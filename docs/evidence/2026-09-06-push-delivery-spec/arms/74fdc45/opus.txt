D1. §2.2 W4 — the wake trigger as specified CANNOT SEND, and its own
    exception guard hides that forever.
-------------------------------------------------------------------------
CLAIM. "swarm.wake_agent_delivery() AFTER INSERT ON swarm.signal_deliveries ...
calls realtime.send(payload,'wake','cswarm-wake:'||wake_id,true). SECURITY
DEFINER, owner swarm_admin, SET search_path = pg_catalog, because swarm_command
cannot execute realtime.send (the activity function has to RESET ROLE for the
same reason, activity/index.ts:139-145). The body is wrapped in BEGIN ...
EXCEPTION WHEN OTHERS THEN RETURN NULL; END so a Realtime failure can never fail
the signal insert." The same construction is specified for
swarm.wake_workspace_signal() (W2/W4). §9 adds: "the realtime.send grant to
swarm_admin [is] not in the repo (locally EXECUTE is PUBLIC, local-plans.out)".

WHAT IS WRONG. swarm_admin cannot reach schema realtime at all.

  select has_schema_privilege('swarm_admin','realtime','USAGE');        -> false
  select has_table_privilege('swarm_admin','realtime.messages','INSERT');-> false
  select has_function_privilege('swarm_admin',
         'realtime.send(jsonb,text,text,boolean)','EXECUTE');            -> true
  select rolsuper, rolbypassrls from pg_roles where rolname='swarm_admin';
                                                        -> false, false

Live probe, with a positive control on the same invocation. Two byte-identical
plpgsql functions, both SECURITY DEFINER with SET search_path = pg_catalog, both
doing PERFORM realtime.send('{"v":1}'::jsonb,'wake',t,true); the first created
in schema swarm and ALTERed to OWNER swarm_admin (verified:
"owner=swarm_admin secdef=true"), the second left owned by postgres. Both
GRANTed EXECUTE to swarm_command and both called inside a transaction after
SET LOCAL ROLE swarm_command, which is exactly what command/index.ts:1377 does:

  SELECT swarm.zz_wake_probe_admin('cswarm-wake:PROBE-ADMIN');
    ERROR:  permission denied for schema realtime
    LINE 1: SELECT realtime.send('{"v":1}'::jsonb, 'wake', t, true)
    CONTEXT: PL/pgSQL function swarm.zz_wake_probe_admin(text) line 3 at PERFORM

  positive control, same session, prior run:
  SELECT zz_wake_probe.as_postgres('cswarm-wake:PROBE-POSTGRES');
    -> topic cswarm-wake:PROBE-POSTGRES | count 1  in realtime.messages

Both objects dropped afterwards; leftover_funcs=0, leftover_schema=0,
leftover_msgs=0.

CONSEQUENCE. The failure is inside the trigger body, which W4 deliberately wraps
in EXCEPTION WHEN OTHERS THEN RETURN NULL. So: the delivery row commits, the
listener's join succeeds (W5 is unaffected), `cswarm listen status` reads
mode: "push" because state === subscribed is genuinely true, and NO WAKE IS EVER
SENT. Every seat runs on the 5-minute reconcile with nothing anywhere reporting
a fault. That is the precise false-success shape §2.3's own status rule and the
brain topic false-success-signals exist to stop, and §2.4's "Trigger cannot send"
row assumes this is a rare degradation rather than the default state.

The stated REASON is also wrong, in a way that matters for the fix.
realtime.send is SECURITY INVOKER (prosecdef=false) with proacl
`=X/supabase_admin,...`, i.e. EXECUTE to PUBLIC — swarm_command CAN execute it.
What swarm_command lacks is USAGE on schema realtime (false) and INSERT on
realtime.messages (false). activity/index.ts:139-145 works because RESET ROLE
restores the CONNECTION role (postgres), not because it becomes swarm_admin.
And realtime.send swallows its own INSERT failure with RAISE WARNING (read its
pg_get_functiondef), so even a privilege that only blocks the INSERT produces a
silent no-op rather than an error.

WHAT TO CHANGE. Either (a) own both trigger functions with the role the
connection already uses — postgres/supabase_admin — which is what the positive
control proves works and what the activity precedent actually does; or (b) have
L2's migration add GRANT USAGE ON SCHEMA realtime TO swarm_admin and GRANT
INSERT ON realtime.messages TO swarm_admin (and confirm the day partition
inherits it). Either way §9's "not in the repo ... locally EXECUTE is PUBLIC"
must be rewritten: EXECUTE is not the binding privilege, and the local state is
NOT already sufficient. L2's listed test "trigger inserts one realtime.messages
row per delivery" is the right control and would catch this — but only once the
owner or the grants are fixed, and it must assert the ROW, never the absence of
an error, because the guard guarantees there is no error.
