## PART 3 — Findings

### DEFECT 1 — §2.1 / §0 / §2.4: the signal TTL is never mentioned, and on the two wake-loss rows the delivery is LOST, not late

§2.1 says "a lost wake … never a delivery". §2.4's **Missed wake** and **Trigger cannot send** rows both answer "why no delivery is lost" with "the reconcile".

The ledger row existing is not sufficient:

- `durable-delivery.ts:283` — the candidate CTE carries `AND s.until > statement_timestamp()`. An expired signal's delivery is not a candidate.
- `durable-delivery.ts:212-231` — step 3 of the *same call* terminalizes every unleased, unacked delivery whose `s.until <= statement_timestamp()` to `ack_outcome = 'expired'`.

And that TTL can be shorter than the reconcile interval, from supported surfaces:

- `command/index.ts:1844` accepts `until_ms` at `integer(cmd.until_ms, 1)` — a **1 ms floor**.
- `src/cli.ts:2565-2581` accepts `--until 1m` (regex `/^([1-9]\d*)(m|h|d)$/`).
- `command/index.ts:8004` clamps a thread reply to the root's remaining TTL — seconds, without anyone typing one.

So `cswarm ask --until 1m …`: row commits, wake dropped (or the trigger's `EXCEPTION WHEN OTHERS` swallowed it — both rows §2.4 concedes), nothing claims for 300 s, and at the reconcile step 3 marks it `expired` and the candidate select excludes it. Today's 2 s poll and lane A's 15 s poll both deliver it. The 150× widening of the only fallback is what turns latency into loss.

The document never mentions `signals.until`, `until_ms`, `SIGNAL_DEFAULT_UNTIL_MS`, or `ack_outcome = 'expired'` — I grepped it. No earlier arm raised it.

Fix options, none a redesign: (a) bound the next deadline by `min(reconcileDueAt, nearestUntil − margin)` using the read the reconcile already runs; (b) put a floor on `until_ms` above the reconcile interval and say so; (c) state plainly in §2.1 and both §2.4 rows that a signal whose TTL is shorter than the reconcile interval can be lost. What cannot stand is a 300 s fallback paired with "never a delivery".

### DEFECT 2 — §2.2 W3.1 / §6 L2: the DROP/CREATE is pointed at the superseded body

W3.1 cites the function as `20260731000001:487, re-granted 20260820000002:306`. But `20260820000002:103` is a full `CREATE OR REPLACE` that **changed the body**. Diffing `20260731000001:285-489` against `20260820000002:103-306` gives exactly one functional difference:

```
-   ELSIF v_membership_revoked_at IS NOT NULL
+   ELSIF NOT swarm.is_member(v_principal_workspace_id, v_owner_user_id)
+      OR v_membership_revoked_at IS NOT NULL
```

That is the `archive_revokes_access` boundary — `swarm.is_member` gained `w.archived_at IS NULL` in the same file (`:4-21`). Archiving does not revoke memberships (`command.test.ts:3604` says so), so without the predicate an archived workspace keeps serving agent reads. A DROP/CREATE built from the line the spec names reverts a security boundary in the function that authenticates every agent read.

Honest mitigation: `command.test.ts:3580-3582` archives and asserts 403, and W3.1 already names `command.test.ts` as must-stay-green. So it costs a red test, not a shipped hole — *provided* L2 runs `p1-server`, which §6's L2 row does not list.
