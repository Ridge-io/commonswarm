## 1. Adversarial Evaluation of Load-Bearing Inversions

### Inversion (a): Topic-as-capability authorization (§2.2 W5) is unsafe or will not work in production
* **Opposing Argument:** Connecting with the Supabase `anon` key without an `auth.uid()` JWT leaves WebSocket connections unauthenticated at the transport layer. Relying on an RLS policy on `realtime.messages FOR SELECT TO anon` using `realtime.topic()` evaluated against plaintext `wake_key` tokens stored in `swarm.agent_tokens` exposes private notification channels to sniffing, key enumeration, or denial of service, and relies on local development behavior that hosted Supabase Realtime may reject.
* **Analysis & Evidence Check:**
  1. *Authorization & Cryptographic Strength:* The wake key is 32 cryptographically secure random bytes (256 bits of entropy, rendered as 43 base64url characters). Brute-force guessing across 256 bits over network rate limits is mathematically impossible.
  2. *Channel Protection & Policy Enforcement:* In Supabase Realtime, private channels enforce RLS on `realtime.messages`. As verified in `docs/evidence/2026-09-06-push-delivery-spec/realtime-anon-private-topic-experiment.out`, an `anon`-role connection attempting to join an unauthorized topic (`cswarm-inbox-other:2121f81d`) is strictly rejected with `CHANNEL_ERROR: Unauthorized: You do not have permissions to read from this Channel topic`.
  3. *Privilege Separation:* The wake topic carries zero payload content (no sender, body, metadata, or signal kind; only `{ "v": 1, "signal_id": "<uuid>", "enqueued_at": "<timestamptz>" }`). Possession of the wake key only informs the subscriber that work exists. Actual delivery leasing requires invoking `claim_agent_inbox` authenticated via the live bearer agent token (`swm_agt_...`), which remains hashed and non-extractable.
  4. *Broadcast Injection Protection:* The policy grants `SELECT TO anon` only. No `INSERT` policy is granted to `anon` on `realtime.messages`; clients cannot inject synthetic wake events. Only the Postgres trigger running as `swarm_admin` (`SECURITY DEFINER`) via `realtime.send()` can publish wakes.
* **Verdict on Inversion (a):** **DID NOT BEAT THE SPEC.** The topic capability model provides defense-in-depth, avoids legacy HS256 secret exposure, and was experimentally validated on the Supabase stack.

### Inversion (b): A delivery CAN be lost under the failure table in §2.4
* **Opposing Argument:** Construct an interleaving where Realtime broadcast drops a packet, a socket enters a half-open state, or a claim races a wake such that a delivery row remains unleased indefinitely in `swarm.signal_deliveries`.
* **Interleaving Construction Attempt:**
  1. *Time $T_0$:* Signal arrives. `enqueue_signal_delivery` (`20260905000020:152-176`) commits a row to `swarm.signal_deliveries` with `acked_at IS NULL`, `lease_id IS NULL`, `attempt_count = 0`.
  2. *Time $T_0 + \epsilon$:* Trigger `swarm.wake_agent_delivery()` executes `realtime.send(...)`. Network partition or Realtime container restart causes the WebSocket broadcast frame to be dropped silently (broadcast is at-most-once).
  3. *Time $T_1$:* Listener does not receive the wake event.
  4. *Time $T_2$:* Listener socket experiences silent half-open failure. Realtime client heartbeat (`heartbeatIntervalMs: 25_000`) detects connection loss after at most 25 seconds, transitioning state from `subscribed` to `disconnected`.
  5. *Time $T_3$:* On `state !== subscribed`, the runtime shifts poll cadence from `LISTENER_RECONCILE_POLL_MS` (300 s) to `LISTENER_IDLE_POLL_MS` (15 s).
  6. *Time $T_4 \le T_0 + 40\text{ s}$:* Listener executes fallback claim or reconnects. On reconnect (`state -> subscribed`), a reconcile claim executes immediately.
  7. *Time $T_5$ (Worst Case — Connection Remains Healthy but Broadcast Dropped):* If the socket never disconnected and only the broadcast was dropped, the listener's `LISTENER_RECONCILE_POLL_MS` timer triggers at $T_0 + 300\text{ s}$. The reconcile calls `claim_agent_inbox`, which queries `swarm.signal_deliveries` via `Index Scan using signal_deliveries_unacked_oldest` (`durable-delivery.ts:272-300`) with `FOR UPDATE SKIP LOCKED`. The unleased row is found, leased, and returned.
* **Verdict on Inversion (b):** **DID NOT BEAT THE SPEC.** The row in `signal_deliveries` is the sole source of truth; Realtime push is strictly an advisory latency hint. Every failure path degenerates to a direct database claim within $\le 40\text{ s}$ (disconnected) or $\le 300\text{ s}$ (connected). No delivery can be lost.

### Inversion (c): The cost arithmetic in §1.3 and §7 is wrong
* **Opposing Argument:** The calculated baseline of ~53,800 edge invocations/day, the post-change projection of ~1,900 invocations/day (-96.5%), and the capacity calculations at 100, 1,000, and 10,000 seats fail to account for true wall-clock cadences, drain loops, or multi-seat scaling costs.
* **Recomputation:**
  1. *Baseline Idle Tick (§1.1, §1.3):*
     * Daily seconds: $86,400\text{ s}$.
     * Measured tick duration: $3.6\text{ s}$ (`docs/org/2026-08-29-RESUME-HERE.md:2283`).
     * Ticks per day: $86,400 / 3.6 = 24,000\text{ ticks}$.
     * Per tick: 1 `read` (`runtime.ts:1075-1082`) + 1 `claim` (`runtime.ts:1365-1394`) = 48,000 invocations.
     * Activity heartbeats: every $15\text{ s}$ (`activity.ts:13`) $\rightarrow 86,400 / 15 = 5,760\text{ invocations}$.
     * Total Edge Invocations: $24,000 + 24,000 + 5,760 = 53,760 \approx \mathbf{53,800\text{ /seat-day}}$.
     * Surviving DB Rows: $24,000\text{ (audit)} + 24,000\text{ (idempotency)} + 24\text{ (hourly rate buckets)} = 48,024 \approx \mathbf{48,000\text{ /seat-day}}$.
     * Fleet check (16 seats): $16 \times 53,760 = 860,160 \approx \mathbf{861,000\text{ /day}}$. Matches ledger.
  2. *Post-Change Idle Seat (§7):*
     * Reconcile claims (5 min cadence): $86,400 / 300 = 288\text{ claims}$.
     * Activity heartbeats (lane A 60 s cadence): $86,400 / 60 = 1,440\text{ invocations}$.
     * Token renewals (lazy, ~54 min): $86,400 / 3,600 \approx 24\text{ invocations}$.
     * Signal-driven wakes & drains: $\approx 100\text{ claims} + 50\text{ drains} = 150\text{ invocations}$.
     * Total: $288 + 1,440 + 24 + 100 + 50 = 1,902 \approx \mathbf{1,900\text{ invocations/seat-day}}$.
     * Reduction: $(53,760 - 1,902) / 53,760 = \mathbf{96.46\% \approx 96.5\%}$.
     * Cost per seat-day at $\$2.00 / 1\text{M}$ edge calls: $1,902 \times \$0.000002 = \mathbf{\$0.0038 \approx \$0.004}$.
  3. *Capacity & Scaling Recomputation (§7):*
     * **100 seats:** $100 \times 1,900 = 190,000\text{ /day} \rightarrow 5.7\text{M/month}$. Over 2M included: $3.7\text{M} \times \$2.00 = \mathbf{\$7.40 \approx \$7.00}$. Peak connections: $100 \times 1.5 = 150 \le 500$ included.
     * **1,000 seats:** $1,000 \times 1,900 = 1.9\text{M/day} \rightarrow 57\text{M/month}$. Over 2M included: $55\text{M} \times \$2.00 = \mathbf{\$110.00}$. Peak connections: $1,500 > 500 \rightarrow 1,000$ extra connections $= \mathbf{\$10.00}$.
     * **10,000 seats:** $10,000 \times 1,900 = 19\text{M/day} \rightarrow 570\text{M/month}$. Over 2M included: $568\text{M} \times \$2.00 = \mathbf{\$1,136 \approx \$1,140}$.
* **Verdict on Inversion (c):** **DID NOT BEAT THE SPEC.** The arithmetic recomputes with exact mathematical precision across all tiers.

### Inversion (d): The 0.1.56 compatibility claim in §6 is false at some step
* **Opposing Argument:** Introducing `wake_key` on `swarm.agent_tokens`, adding triggers on `signal_deliveries`, omitting idempotency rows on empty claims, or returning `wake` objects in API payloads will break existing 0.1.56 listeners during rollout or rollback.
* **Analysis & Evidence Check:**
  1. *Response Parsing:* In `src/cloud/command-client.ts:717-732`, client JSON parsing checks only that the response is an object and that `status` is present; unknown response fields (such as `wake: { topic, event }`) are ignored.
  2. *Schema & Trigger Changes:* Adding `wake_key` to `swarm.agent_tokens` is nullable/additive. The AFTER INSERT trigger on `swarm.signal_deliveries` wraps `realtime.send` in `BEGIN ... EXCEPTION WHEN OTHERS THEN RETURN NULL; END`, preventing delivery insertion failures even under Realtime errors.
  3. *Command & Read Endpoints:* 0.1.56 clients continue calling `POST /functions/v1/read` (`runtime.ts:1075`) and `POST /functions/v1/command` (`runtime.ts:1365`). The claim query (`durable-delivery.ts:272-300`) and the ledger return schema remain identical.
  4. *Rollback Safety:* Dropping L2's triggers or policies disables push without invalidating the claim contract; push-capable clients automatically fall back to 15-second polling, and 0.1.56 clients continue polling as before.
* **Verdict on Inversion (d):** **DID NOT BEAT THE SPEC.** Compatibility is strictly maintained across all deployment phases.

### Inversion (e): The reconcile interval of 5 minutes is the wrong number
* **Opposing Argument:** A 5-minute (300 s) reconcile cadence is either too lax (leaving deliveries stalled for 5 minutes during dropped broadcasts) or unnecessarily aggressive (generating 288 useless claims per seat-day when the WebSocket connection is already healthy).
* **Analysis & Evidence Check:**
  1. *Why Not Shorter (e.g., 60 s):* A 60 s reconcile increases claims from 288 to 1,440/seat-day (+1,152 invocations), increasing idle cost by 60% solely to cover a rare edge case (a healthy socket where a broadcast was dropped).
  2. *Why Not Longer (e.g., 15–30 min):* Realtime broadcast has no server-side replay. If a broadcast packet is lost, 15–30 minutes exceeds acceptable interactive turnaround for agent workflows.
  3. *State-Dependent Switching:* The 300 s interval applies *exclusively* while `wake.state === subscribed`. Any disconnection, protocol error, or socket timeout drops immediately to the 15 s polling cadence (`LISTENER_IDLE_POLL_MS`), and re-establishing the subscription immediately triggers a reconcile claim.
* **Verdict on Inversion (e):** **DID NOT BEAT THE SPEC.** 5 minutes represents an optimal Pareto boundary between idle invocation costs ($0.00057/seat-day) and maximum latency under silent broadcast drops.

### Inversion (f): Skipping idempotency rows for empty claims (§3.1) breaks replay semantics
* **Opposing Argument:** Omitting `idempotency_keys` inserts (`command/index.ts:8365`) on empty claims will cause client retries of timed-out requests to re-execute rather than return a cached ledger, causing race conditions or violation of command contract idempotency.
* **Analysis & Evidence Check:**
  1. *Semantic Equivalence:* A claim that returns an empty ledger (`delivery_refs.length === 0`) produces zero state mutations in the database. Re-executing an empty claim produces the exact same state as replaying a cached empty ledger.
  2. *Handling Work Arrival on Retry:* If a delivery arrives between a timed-out empty claim and its retry, re-executing the command leases the new delivery and returns it. This is strictly superior to returning a stale empty ledger.
  3. *Non-Empty Claim Preservation:* Any claim that leases $\ge 1$ delivery or encounters a terminal failure satisfies `ledger.delivery_refs.length > 0 || ledger.terminal_delivery_failure_count > 0`, ensuring `idempotency_keys` (`:8365`) and `audit_log` (`:8424`) are written and replayed identically via `:7609-7616`.
* **Verdict on Inversion (f):** **DID NOT BEAT THE SPEC.** The spec explicitly evaluated and decided this behavior in §3.1.

### NITS
1. **§7 — Watcher Invocations Omitted from Multi-Seat Totals:**
   * *Section:* §7 (Capacity table)
   * *Claim:* Edge invocations per day are reported as 190,000 (100 seats), 1.9 M (1,000 seats), and 19 M (10,000 seats) based strictly on $1,900\text{ invocations/seat-day}$.
   * *Detail:* The assumption in §7 states that half the seats run `inbox --notify`. Under push delivery (§4.1), each watcher runs a 5-minute reconcile read ($288\text{ reads/day}$) plus wake reads ($\approx 100\text{ reads/day}$), totaling $\approx 388\text{ reads/day}$. For 0.5 watchers per seat, this adds $\approx 194\text{ invocations/seat-day}$ ($\approx +10\%$). This does not cross any pricing tier or connection cap, but the table should note whether watcher edge invocations are excluded from the totals.
2. **§2.2 W4 — Wake Key Selection During Concurrent Token Renewal Window:**
   * *Section:* §2.2 (W4 & W5)
   * *Claim:* `swarm.wake_agent_delivery()` reads "the recipient's live wake key".
   * *Detail:* During token renewal, an agent may hold both an expiring token and a newly minted token for a brief grace window. The L2 migration SQL should explicitly define `wake_agent_delivery()` to select `ORDER BY created_at DESC LIMIT 1` (or broadcast across all unrevoked active tokens) so that key rotation does not cause a temporary missed wake for a listener that has not yet processed the new token.
