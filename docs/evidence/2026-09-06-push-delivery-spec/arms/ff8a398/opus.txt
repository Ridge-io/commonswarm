## Five DEFECTs

**D1 — W6's revocation bound does not exist.** §2.3 pins the Realtime credential to the anon key. `realtime-js@2.110.8` `_performAuth` gates the whole `access_token` push on `if (this.accessTokenValue != tokenToSend)`. Re-calling `setAuth(anonKey)` is a no-op, so the policy is never re-evaluated. A revoked subscriber stays joined until the socket drops — not "one renewal period at most".

**D2 — the watcher's `limit: 0` claim is rejected.** `command/index.ts:1510` is `integer(limit, 1)`; `integer` at `:1435-1437` is `>= minimum`. limit 0 → 400. The cited `effectiveLimit <= 0` branch is only reachable via lease exhaustion. L5 has no specified way to get its wake topic. Also: the claim is not observation-only — steps 2–4 (`durable-delivery.ts:195-253`) run before the limit and can terminalize deliveries.

**D3 — the §3.1 audit gate misses two mutations.** `terminal_delivery_failure_count` comes from step 4 only. Step 2 (lease reset) and step 3 (TTL → `ack_outcome='expired'`) have no RETURNING and no ledger field (`:66-71`). A claim that expires deliveries would write zero audit rows — the opposite of the rule §3.1 states.

**D4 — "the recipient's live wake key" is singular; the schema is not.** `agent_tokens` has no uniqueness on `principal_id` (`20260723000001:192-216`), and §9 itself assumes two live subscribers per principal. Two engineers build two different triggers.

**D5 — §0's 72,000 is 24,000 × 3**, double-counting the hourly `rate_buckets` upsert that §1.1, §1.3, §7 and §8 all count as 24. And "to zero" contradicts §3.1 keeping that upsert.

## Four GAPs

Lane table gives `command/index.ts`, `runtime.ts`, `cli.ts` and `arrival-watch.ts` to two lanes each; no lane owns the retention migration (the purge floor is `GREATEST(30, config)` at `:795-805`, so the config change alone is a no-op); skipping the read starves `classifyDeliveryMode` at `runtime.ts:1104`, so push-mode listeners can never see the rollback §6 relies on; and the experiment's policy is a static `LIKE`, not the SECURITY DEFINER lookup W5 needs.

## What survived

The reconcile-on-subscribe race is genuinely covered — bindings register before `subscribe()` and inbound dispatch gates only on `_notThisChannelEvent`, so a wake in the join window is delivered, and the pre-join window is caught by the reconcile. The trigger's exception guard is fine: the recipient cap of 8 bounds subtransactions, `ON CONFLICT DO NOTHING` does not fire the trigger, and WAL means no wake precedes its commit. W3 really is invisible to 0.1.56.

======================= WHAT I ATTACKED AND FOUND SOUND =======================

- Reconcile-on-subscribe against a wake sent between server-side join acceptance and the
  client's SUBSCRIBED callback: SUFFICIENT, and the window is not even lossy. Bindings are
  registered before subscribe(), and RealtimeChannel's inbound dispatch gates only on
  _notThisChannelEvent (close/error/leave/join by ref) — a broadcast arriving in that window
  is delivered to the handler. The window that matters is the pre-join one, and the
  reconcile claim after SUBSCRIBED covers it because SUBSCRIBED strictly follows join
  acceptance. No finding.
- SECURITY DEFINER + EXCEPTION guard vs the inserting transaction: sound. The subtransaction
  per delivery row is bounded at 8 (the position CHECK BETWEEN 0 AND 7 argued in
  20260905000020's section 3), so no subxact-spill risk. ON CONFLICT DO NOTHING conflicts do
  not fire an AFTER INSERT FOR EACH ROW trigger, so W4's "fires for both enqueue paths" is
  right and does not double-wake. realtime.messages is read from WAL, so no wake can precede
  the commit of the delivery row. §9 already flags the unverified realtime.send grant to
  swarm_admin. No finding.
- W3 additivity for a 0.1.56 client: correct. command-client.ts:717-735 validates only
  object-ness, status, ok and event_ids, and ignores unknown fields; CLIENT_PROTOCOL_VERSION
  is frozen at config.ts:3; the capability set at signals.ts:124-132 is a fixed four-bit
  parse. An added optional `wake` is invisible to 0.1.56.
- §5 plans: local-plans.out matches the prose. The claim uses signal_deliveries_unacked_oldest
  with the (recipient, workspace) Index Cond; the audit DELETE does walk audit_by_cred on its
  second column; the conclusion (stop the write rather than index it) follows.
- Site citations: LiveDashboard.astro:5774 is the 2 s setInterval; commonswarm.ts:176-209 is
  the private-topic template §4.3 says it is.

DISPOSITION: five DEFECTs (D1 and D2 each make a named lane unbuildable as written; D3 loses
audit for a real mutation; D4 is a ruling L2 cannot proceed without; D5 mis-states the cost
the ask asked for) and four GAPs. The design's core — push is a hint, the row is the truth —
survives every attack I made on it, and the failure-mode table is honest where it is right.
The document is not yet a buildable spec.
