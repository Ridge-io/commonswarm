DA. §2.2 W6 and §6 L2 — `revoke_agent_token` is not a database function, so the
    rotation has no buildable home, and the only build available to L2 breaks
    W6's own renewal guarantee.

    supabase/migrations/. `revoke_agent_token` is a COMMAND KIND (index.ts:179,
    :872, :919) whose effect is TypeScript in the edge:
      - token revoke:     command/index.ts:4207-4216 (UPDATE swarm.agent_tokens
                          SET revoked_at WHERE token_id = ... )
      - principal revoke: :4111-4117 and :4139-4143
    So L2 must either edit supabase/functions/command/index.ts — a file §6 gives
    exclusively to L1 (:8348-8445) and L3 (the response builders), and which L2's
    row does not list — or write an AFTER UPDATE trigger the spec never specifies.

    The trigger build is worse than merely unspecified: it is WRONG against W6's
    own text. `discardStrandedSuccessor` (command/index.ts:3565-3587) sets
    agent_tokens.revoked_at, and it is called from the ORDINARY RENEWAL path at

    revoked_at (:3576 :3973 :4012 :4112 :4140 :4172 :4181 :4208 :4237). An
    `AFTER UPDATE OF revoked_at ON swarm.agent_tokens` trigger therefore rotates

GB. §2.3 / §6 L4 — a push-to-poll fallback manufactures a false host lapse, and
    the spec's only sentence on it does not reach the mechanism.

    §2.3: "claimCadenceMs / expectedClaims (read-health.ts:203-207, :403) become
    the reconcile cadence in push mode; the tests that round-trip them ... are
    updated in L4."

    claimCadenceMs is ONE SCALAR (read-health.ts:40, set wholesale by
    recordListenerClaimCadence at :202-207). expectedClaims is derived from that
    single current value INSIDE a loop over every full hour back to
    currentHour - HEALTH_WINDOW_MS (:398-413: `const expectedClaims = HOUR_MS /
    health.claimCadenceMs` at :403, `ratio: claims / expectedClaims` at :411).
    Hours are then filtered against LISTENER_THROUGHPUT_LAPSE_RATIO = 0.5 (:12,
    :415) and rendered to the operator as "Claim throughput fell below 0.50 for
    the full hour at <hour>: <claims>/<expected> expected" (src/cli.ts:4664).

    So changing the cadence RETROACTIVELY rescores the whole window. Push -> poll,
    which §2.4 lists as routine in five of its thirteen rows (socket half-open,
    socket down, policy refused, rotation, proxy), rewrites expected from 12/hour
    to 240/hour for every past hour; hours that were healthy at a 5-minute
    reconcile score ratio ~0.05 and the CLI reports a lapse that did not happen.
    The reverse direction is harmless but equally wrong.

    The ask required the failure modes of the change. This one is created by the
    change, is operator-visible, and is a false signal of exactly the kind the
    document's own false-success rule is written against ("It never says push
    unless state === subscribed right now"). L4 cannot be built without a ruling:
    store expected per hour, or exclude hours whose mode changed.

GC. §2.4 / §7 / §9 — no failure mode for the delivery claim rate limit, which
    push mode is the first design able to saturate, and crossing it is not quiet.

    DELIVERY_CLAIM_RATE_LIMIT_PER_MINUTE = 120 (durable-delivery.ts:21) was sized

    into any of the four seat counts; §9 does not list it as unsettled. The spec

    what the listener does on refusal, and whether 120/min still fits a design

==================== WHAT I ATTACKED AND FOUND SOUND ====================

- The volatile DEFAULT. I did not argue it, I ran it (M1). PostgreSQL's fast-path
  ADD COLUMN applies only to non-volatile defaults; gen_random_bytes is
  provolatile='v', so the table is rewritten and the expression evaluated per row.
  Five rows, five distinct 43-character base64url ids; a later INSERT got a sixth.
  translate's shorter `to` string deletes the '=' padding, so 44 -> 43 as the spec
  says, and 44 characters is under encode()'s 76-character newline wrap. The
  claim in W1 is exactly right, and the additivity argument that rests on it holds.
- The §3.1 gate against steps 2-4. Steps 2 and 3 really do mutate with no
  RETURNING; step 4 really is the only reported one; the two new counters plus
  delivery_refs cover every mutation on the path I could find, including the
  security_alerts insert (already gated on a counter in the set) and
  hydrateDeliveryRefs (no DML). The replay ruling is right: a claim that changed
  nothing is indistinguishable from its own replay.
- The reconcile read. Not decorative. Claims return at command/index.ts:8433,
  before the only other grant-use stamp at :9024-9036, so without the read a
  push-mode seat would stamp nothing and self-suspend at
  20260901000001:199-208. 288/day against a 14-day floor is ~4,000x margin.
  It also feeds classifyDeliveryMode (:1104 / :612-629), which is what makes the
