## DEFECTS

### D1. §7.1 cites a write parser pattern that 400s every installed writer

P1 says old clients keep posting. §7.1 tells the implementer to add `channel` / `thread_root_id` / `broadcast_to_channel` by copying `modernShape` at `supabase/functions/command/index.ts:1532-1541` and `:1570-1576`.

That group is all-or-nothing: if either `to_agent_principal_id` or `in_reply_to` is present, **both** keys are required.

Installed writers already send that pair, always:

- `src/cloud/command-client.ts:983-990` — “New clients always send both target fields and `in_reply_to`”
- `site/src/lib/commonswarm.ts:2002-2008` — browser post sends both, `in_reply_to: null`
- `src/listener/runtime.ts:772-780` — listener reply sends both

Adding `channel` to `modernKeys` makes every current body fail `exactKeys` at `:1553-1562`. Every post returns 400.

The safe pattern is the next lines: `until_ms` / `attachments` as their own `Object.hasOwn` groups (`:1535-1538`). The spec points at the grouped pair and skips the adjacent optional-key pattern.

This is a write outage if P1 is built as cited. It contradicts “leaves old clients working.”

### D2. R2’s worked example gets the resolution order wrong

`in_reply_to` **is** a private re-address. That part of R2 is right:

- Validator: undirected `note` only (`command/index.ts:1588-1595`)
- `resolveSignalWriteTarget` loads the referenced row, requires `addressedToCaller` (`:5789-5802`), then writes `{ toUserId|toAgentPrincipalId: reference.from_principal }` (`:5804-5827`)
- Writers send null targets (`src/cli.ts:3112-3119`, `src/listener/runtime.ts:773-779`)
- Plain success copy: “addressed to the original author” (`src/cli.ts:3159`)

Draft B’s rule is write-time `in_reply_to := COALESCE(parent.in_reply_to, parent.id)`, described as “one extra lookup in a function that already loads the parent.”

The live function uses one `inReplyTo` value as **lookup key and stored value** (`:5747`, `:5781`, `:5813`). Audience comes from the **loaded** parent’s `from_principal`.

If COALESCE is applied to the **stored** column after that load (the reading of B’s “already loads the parent”), hop 3 is still addressed to the agent. The conversation does not die.

The spec’s `A → agent → A → agent` story (200, addressed to A herself, no error) is true only if the coalesced **root id** replaces the lookup key before `addressedToCaller`. B did not specify that. For A’s own agent, `signalAgentOwnedByUser` (`:5795-5800`) would then pass on the root ask and return `{ toUserId: A }`. That is a naive-wiring risk, not what B’s text necessarily does.

R2’s conclusion (do not ride public threads on `in_reply_to`) can still stand. The listener-loop death is not a measured consequence of B’s rule.

## 2. Migration / RLS

**`channel_id` nullable, no backfill, vs the live insert.** Safe for the current edge. Insert names columns and omits `channel_id` (`command/index.ts:5966-5983`). `ADD COLUMN uuid` with no default leaves NULL. `MATCH SIMPLE` on `(channel_id, workspace_id)` lets NULL through. I did not find a current insert trigger that would reject that NULL.

**Reverse window (new edge, file 2 not applied).** Real: `column "channel_id" does not exist` on every post. Spec names it and the `schema_migrations` check (`20260902000001:58-64`). That outage is operational, not a hole in the rule, **if** the apply order is kept. Combined with D1, P1 still has a parser outage after a correct migrate-then-edge.

**`CREATE OR REPLACE VIEW` twice.** Shape protection is real: PostgreSQL refuses rename / retype / drop / reorder. Adding `channel_id` at the end is enforced. The WHERE clause is **not**. Neither are expressions of existing columns (the attachments subquery can become `'[]'::jsonb` with the same type). Three files define this view; only `20260901000010` is live. Copying an older WHERE is a silent auth change. Spec’s “protect on WHERE with a before/after suite” is the right control; it is not mechanical.

File 3 says “add `thread_root_id` and `broadcast_to_channel` at the end.” If someone copies the `20260901000010` body again and omits `channel_id`, replace tries to rename a column and the migration errors. Underspecified, not silent.

**Clause (e) disclosure.** I did not find a third-party DM the new arms should hide.

- `from_principal = auth.uid()` is the sender.
- The owned-agent `EXISTS` shows DMs **your** agent sent. Spec intends that.
- Agent read sets `request.jwt.claims.sub` to the **owner** (`read/index.ts:485-494`), then reads `swarm_read.signals` (`:600`) and keeps only broadcast or `to_agent = this principal` (`:611-612`). Newly admitted sent-by-owner rows have a recipient, so they fail both arms unless they were already addressed to this agent.
- Attachments are a correlated subquery on `s.id`. View owner `swarm_admin` bypasses file RLS, but only for rows the WHERE already admits.
- Receipts: `signal_delivery_receipts` already lets any member who knows a signal id read receipts (`20260902000001:105-110` membership gate; signal load at `:144-150` has no per-signal read check). Clause (e) does not create that. Appendix A already records it.

## 4. Central rulings

**R2 (threads).** Meaning of `in_reply_to` is measured and right: private reply to the author, not a public thread. There is no `--in-reply-to` CLI flag. B’s `src/cli.ts:2932` citation is the wait poll, not a write. The COALESCE death-example is wrong as a necessary outcome (D2). Hop 3 is an `in_reply_to` write only if A uses `cswarm reply`; a new `cswarm ask --to` never hits B’s rule.

**R3 (DMs).** Confirmed. Live `swarm_read.signals` is `20260901000010:122-133`. No `from_principal` arm. Sender cannot re-read a directed row through the view. B’s “no migration” is false. A fifth clause is required. I did not read the live catalog on `ukezjcnxjvkpkeezxaew`; this is from migration files, as the spec itself flags.

**R4 (no backfill).** The case A’s default-channel backfill covered and this shape does not: every pre-migration row stays `channel_id NULL`. Named-channel reads, `?c=` permalinks, and agent `channel=` filters never see that history. It lives only in `#all-signals`. That is a product gap, not a write outage. Spec chooses it to avoid `DISABLE TRIGGER` on `signals_append_only`. Honest, and it does break history-in-channel.
