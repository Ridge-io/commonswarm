3. wake_topic_authorized returns false and never raises — REFUTATION FAILED
================================================================================

First, a correction to the task's framing that is itself worth recording. A direct call **as anon**
is impossible and is supposed to be:

  BEGIN; SET LOCAL ROLE anon;
  SELECT swarm.wake_topic_authorized('cswarm-wake:not-valid');
  ERROR:  permission denied for schema swarm

That is the spec's own design (W5, PUSH-DELIVERY.md:108): a policy stores the function by OID, so
anon needs EXECUTE and not USAGE on the schema. So the anon path is exercised only through the
policy, which is the file's first test. I therefore measured the input matrix as the owner and the
anon path through Realtime separately.

Input matrix (owner-side, one statement, all nine inputs):

  malformed      cswarm-wake:not-valid                    -> false
  empty          ''                                       -> false
  null           NULL                                     -> false
  wrongprefix    cswarm-signals:abc                       -> false
  unknown43      cswarm-wake:AAAA…(43)                    -> false
  len42          cswarm-wake:AAAA…(42)                    -> false
  len44          cswarm-wake:AAAA…(44)                    -> false
  quote          cswarm-wake:' or '1'='1                  -> false
  newline-embed  cswarm-wake:AAAA…(43)\nx                 -> false

Nine inputs, nine `false`, zero errors raised. I added the last three myself: `len42`/`len44`
probe the exact-43 anchor, `quote` probes the fact that the argument reaches a parameterized
comparison and not string concatenation, and `newline-embed` probes whether Postgres's `$` could
match before a trailing newline and let a padded topic through — it does not, because the regex
carries no newline-sensitive flag.

Positive control on the same invocation (this is what makes the nine `false` results evidence
about the function and not about a function that always returns false):

  live topic   swarm.wake_topic_authorized('cswarm-wake:'||wake_id)          -> true
  neg control  swarm.wake_topic_authorized('cswarm-wake:'||reverse(wake_id)) -> false

Index use, not asserted from the index's existence but from the plan:

  EXPLAIN (COSTS OFF) SELECT p.principal_id FROM swarm.agent_principals p
    WHERE p.wake_id='x' AND p.revoked_at IS NULL;
  Index Scan using agent_principals_wake_id on agent_principals p
    Index Cond: (wake_id = 'x'::text)
    Filter: (revoked_at IS NULL)

The unique index is used; the revoked check is a filter on the single fetched row, so a revoked
principal costs the same lookup as a live one.

Timing/existence leakage: the four refusal classes are not distinguishable to the caller, because
the caller never sees the boolean — Realtime sees it. The file's second test measures this the
right way: it normalizes the topic out of the refusal string (`refusalWithoutTopic`, necessary
because Realtime quotes the topic back) and asserts all four normalized strings are equal. It
passed. I did not measure wall-clock timing differences between the four classes; see NOT
ESTABLISHED.

Three policies total: the pre-existing activity policy plus exactly the two the spec lists. The
anon policy is byte-for-byte the spec's block at PUSH-DELIVERY.md:99-106. The signals policy is
the activity policy with `cswarm-activity:` replaced by `cswarm-signals:`, which is what
"authorized exactly like the existing activity topic" (W2, :79) asks for. No INSERT, UPDATE,
DELETE, or ALL policy was added. There is no policy that lets anon read the signals topic or the
activity topic, and none that lets authenticated read a wake topic.

I probed the one widening I could construct. anon does hold ambient reach into the schema:

  has_schema_privilege('anon','realtime','USAGE')          -> t
  has_table_privilege('anon','realtime.messages','SELECT')  -> t

so before this migration anon's SELECT was blocked purely by there being no anon SELECT policy,
and this migration adds the first one. That makes "does it leak outside a Realtime connection?"
a real question rather than a formality. It does not:

  SELECT realtime.topic();                                  -> NULL
  SELECT swarm.wake_topic_authorized(realtime.topic());     -> false

`realtime.topic()` reads a GUC the Realtime service sets per channel, so on any ordinary
connection the USING clause is false and the policy grants nothing. Note that these two
privileges are pre-existing stack state, not something this lane granted.
