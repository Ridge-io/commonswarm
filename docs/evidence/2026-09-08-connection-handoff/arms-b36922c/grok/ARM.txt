1. Fence always longer than any inner backtick run
================================================================

codeBlock() at site/src/components/connect/agent-prompt.ts:54-57:

  const fence = "`".repeat(Math.max(3, ...Array.from(text.matchAll(/`+/g), match => match[0].length + 1)));
  return `${fence}${language}\n${text}\n${fence}`;

I re-ran that exact function against constructed cases (empty; no ticks; a run of exactly three; a run of seven; a run as the whole text; a run at the start; a run at the end; a closer-looking line of ticks; 3-space indent + 5 ticks; trailing spaces after ticks; CRLF; tab indent; many one-tick spans; INSTALL_CMD).

CommonMark closer rule used as the oracle: a content line of 0-3 spaces + N-or-more backticks closes an opening fence of length N. Because fence length is max(3, longest_run + 1), no content line can hold a run long enough to close. Empty matchAll spreads to Math.max(3) === 3, not NaN.

Worst case I built: first and last lines are ```, plus an inner run of 7, plus an indented run of 5. Opening/closing fence was 8. No premature closer. Inner text equalled the input.

I could not construct an input whose fence fails to enclose its content. Production payloads (JSON.stringify envelope; INSTALL_CMD) contain no backticks under current field alphabets (token /^swm_agt_[A-Za-z0-9_-]{43}$/, UUID, https origin, JWT base64url, credential message constants), so the live fence is ```. Growing-fence is still correct for a future payload that does contain ticks.

Did not pipe the output through markdown-it / GitHub's renderer. Spec-level closer scan only.

Probes on this SHA:

  old-shape envelope + real JWT anon_key (underscores, no backslash-underscore) → accepted
  token with embedded _ (swm_agt_ + A_×21 + A) → accepted
  JSON.stringify(envelope).replaceAll("_","\\_") → connection_invalid, Markdown message, no fetch
  leading ```json fence (and leading spaces + fence) → same
  url "[https://fixture.example](https://fixture.example)" → connection_target_invalid, Markdown-link message
  https://api.commonswarm.com → accepted
  http://[::1] and https://[::1] → accepted (local HTTP rule); markdown-link regex does NOT match (no "](" after the "]")
  JWT used as url → connection_target_invalid generic (not the Markdown-link message)
  truncated JSON → generic invalid-JSON message (no Markdown)

False-positive question: can a valid base64url JWT or a real URL look like the detectors?

  JWT alphabet is A-Za-z0-9-_. No backslash, no backtick, no "[" / "](" . A JWT as anon_key inside valid JSON never hits the parse-failure detectors. A JWT as url fails checkedTarget with the generic target message, not the Markdown-link message.
  Real origins start with https:// or http://. The link regex requires the string to START with optional space then "[". http://[::1] starts with "http", not "[". Bare "[::1]" does not match because there is no "](".
  new URL("[https://fixture.example](https://fixture.example)") already throws. So the new url check only specialises the message for a shape checkedTarget already rejected. It cannot refuse an envelope the previous parser accepted.
