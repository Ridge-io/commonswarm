The hole is the click after a **workspace switch**:

```javascript
const openBrainTopic = async (topic: string): Promise<void> => {
  activateWorkspaceView("brain");
  setBrainNotice("");
  const listIsFresh = await refreshBrainTopics(true);
  renderBrain();

};
```

Every other async continuation in this file drops the result when `requestVersion` / `activeWorkspaceId` moved. This one does not.

`createBrainTopicReader.refresh(true)` waits out the in-flight read, then **starts another**. The wrapper is:

```javascript
if (sampleMode || !activeWorkspaceId) return false;
return await readBrainTopics();
```

That second `readBrainTopics` captures **whichever workspace is active at the second start**. Sequence:

1. Click `shared-host` on workspace A.
2. User switches to B (`requestVersion++`, `files = []`, B’s fetch in flight).
3. A’s read returns, version guard → `false`.
4. Forced refresh starts its own read. `activeWorkspaceId` is B. That read **applies**, `files` becomes B’s list, `listIsFresh === true`.
5. `openBrainTopic` still runs: `renderBrain()` on B, then `brainLinkClickOutcome("shared-host", B’s names, true)`.
6. `brain-how-to` / `shared-host` / `releases` exist in many workspaces. Outcome is `open`. B’s topic loads. The user did not click anything in B.

If B does not have the name, B is still yanked to the Brain view with a notice about A’s slug.

The test that claims this shape does not encode it. `switching` stays `true` for every read, so the click’s own read also bails. The real dashboard does the opposite once B is the active id: the second read succeeds. Mutating `openBrainTopic` to omit a version guard does not turn that test red. The observer only checks that `brainLinkClickOutcome(topic, brainTopicNames(), listIsFresh)` appears, not that the continuation is dropped.

`readBrainTopics` not assigning `files` on a bailed A-read is correct and insufficient. The forced “take your own read” fix for the in-flight race is what then authorizes B.
