## 1. Injection

Attempted: topic names with `<`, `"`, `javascript:`, a `data-` attribute, and Markdown that survives sanitization.

`linkifyBrainTopics` runs after `setSanitizedMessageMarkdown` (LiveDashboard 3796–3804). It walks text nodes, `createElement("button")`, and `textContent`. No HTML string, no `innerHTML`. `canonicalBrainTopic` is `[a-z0-9][a-z0-9._-]*`, so a live topic cannot carry `<`, `"`, `:`, or `/`. `title` and `data-brain-link` are DOM properties filled from that canonical name, not from the body. `<a>` is opaque; the sanitizer only allows `http(s)` hrefs.

No injection path found.

## 2. False links

Attempted: `roadmap` vs `commonswarm-roadmap`, trailing `.`, URL path/query, fenced `<pre>`, existing `<a>`, a body written before the topic existed.

Matching is whole-run, not a prefix slice. `commonswarm-roadmap` does not mint `roadmap`; `non-shared-host` and `brain-how-to-v2` stay plain. `RUN_RE` keeps `/ \ @ : ? # = & % +` in one token, so a URL/query/fragment/Windows path equals no topic. `<pre>` and `<a>` are skipped. A body written before the topic existed linkifies only if that name is in the in-memory list at render — that is choice (a), accepted in the design.

Residual, also accepted: a slug-shaped English phrase (`The agent-restart path is slow`) becomes a control if that topic exists.

## 3. Missed links

`There's a brain topic for CommonSwarm-roadmap` is one ASCII run, `toLowerCase()` hits `commonswarm-roadmap`, and the visible slice stays `CommonSwarm-roadmap`. Same mechanism as the `Brain-How-To` unit test. Case folding works; the exact operator string is not in the fixture (the observer uses lowercase).

## 4. Word gate

Enforced in the parser, not only in tests: `isLinkable` is `isSlugShapedTopic(topic) || marked`, and the DOM pass sets `marked` from `CODE`.

A topic named `brain` or `the` is legal (`canonicalBrainTopic` allows it). It would not link in prose. It would link inside every inline-code CLI snippet (`cswarm brain put`, `cswarm brain get brain-how-to`). That is real harm for `brain`; the gate does not reserve those words.

## 5. Live-list binding — this is the defect

Empty `files` is a no-op, and that path is tested. Workspace load assigns `files` before `loadSignals`, so the first feed render is not a race.

`files` is then a snapshot. The only writers are workspace load, `files = []` on switch, and a Brain-panel save of an existing file. `refreshLatestSignals` / `renderFeed` never call `workspaceFiles`.

The design states as a bound (docs/design 108–111, 121–123):

- “A topic created by an agent while the reader sits on the feed appears on the next feed refresh.” False. The live feed tick rebuilds messages against the same `files`. Put-then-cite (`cswarm brain put new-topic` then a note naming it) stays plain for a reader already on the feed until `openWorkspace` (the Refresh control), not until a feed poll, and not until `returnToChannel`.
- “A click after the topic is deleted opens the Brain panel, not the topic… lands on the topic list and can see the topic is gone. `brainView.open` then returns without changing the pane.” The reachable case is the opposite: `files` still holds the name, so the feed still draws a control, `open` finds the stale row, and the download fails with “The topic could not be loaded.” The “topic is gone, list only” path needs `files` already updated without a feed rebuild; nothing in LiveDashboard does that.

`AGENTS.md` repeats the overclaim: “the app renders no dead link.” A control whose target has been deleted on the server is a dead control. No test covers a missing topic on click.
