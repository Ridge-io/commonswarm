# The production 500s are pooler exhaustion — `EMAXCONNSESSION`, session mode, pool_size 15

Measured 2026-08-05 from the Supabase dashboard logs of `ukezjcnxjvkpkeezxaew` (`cloud-swarm-dev`,
**which is production**). Operator granted authenticated browser access. Range: last 7 days.

This resolves the failure that three earlier hypotheses could not explain, and it was sitting in a
log line the whole time.

## The line

```json
{"event":"command_request_failure","command_kind":"post_signal","outcome":"error",
 "reason":"internal_error",
 "detail":"PostgresError: (EMAXCONNSESSION) max clients reached in session mode
           - max clients are limited to pool_size: 15"}
```

## The measurements

| what | count |
|---|---|
| `command_request_failure` rows, 7 days | **56** |
| …of those, carrying `EMAXCONNSESSION` | **56 — 100%** |
| `supavisor_logs` rows matching `max clients` / `EMAXCONN` | **14,602** |
| `supavisor_logs` total rows (control) | 128,160 |
| edge-function `booted` events | **40,176** |
| edge-function `shutdown` events | 40,061 |
| `read_request_failure` rows | 9,231 |

**The pooler is configured in session mode with `pool_size: 15`.** In session mode a client holds
its server connection for the whole session. The edge functions cold-start roughly **four times a
minute** (40,176 boots in 7 days), and each new instance wants a connection. Fifteen is not enough,
so the pooler refuses — 14,602 times.

## Why this went unexplained for so long

**The read path discards the message.** Its log line records `name`, `code`, `severity`, `routine`,
`constraint` — and not the error text. So a read failure appears as:

```json
{"event":"read_request_failure","phase":"parse","name":"PostgresError","code":"XX000",
 "severity":null,"routine":null,"constraint":null,"retryable":false}
```

`XX000` is Postgres's generic `internal_error`; the driver assigns it to a connection it could not
establish. Every distinguishing detail — *max clients, session mode, pool_size 15* — is in the
message, and the message is the one field the read path drops. **8,990 read failures were
undiagnosable while 56 command failures named the cause outright**, because the command path logs
`detail` and the read path does not.

This also explains the earlier findings without contradicting them:

- **`postgres_logs` shows 2 ERROR lines against 8,990 reported `PostgresError`s.** Correct — the
  *pooler* refuses before the connection ever reaches Postgres. The database was never the problem.
- **`severity`, `routine`, `constraint` are all null.** Correct — a genuine server-side Postgres
  error carries those. This one is generated by Supavisor.
- **`phase: "parse"`** — the failure surfaces when the driver first tries to use the connection.
- **~50% failure at a single request, ~75% under concurrency.** Consistent with a saturated pool
  rather than with contention: concurrency worsens it but does not create it.
- **D-056's cold-start dependence.** Each boot needs a connection, and boots are the demand.

## Wren's connection-exhaustion hypothesis was right, and was rejected for a bad reason

Wren proposed connection exhaustion early and withdrew it. Its own account of why is worth keeping:
the hypothesis predicted Postgres codes `40001`/`40P01`/`55P03`, which the server classifies
*retryable true*, so the observation could never have matched a `retryable:false` failure.

The prediction was wrong; the hypothesis was right. This failure never carries a Postgres lock code
because **it never reaches Postgres** — the driver stamps `XX000` on a pooler refusal. The
reasoning that retired the hypothesis was sound given what was visible, and what was visible had
been narrowed by a log line that dropped the message.

## What this does NOT establish

- **Whether session mode is deliberate.** Transaction mode is the usual choice for serverless
  clients; session mode plus a 15-connection pool is the shape that fails here. Whether that is a
  Supabase default, a project setting, or required by something we do (`LISTEN`, prepared
  statements, advisory locks) is **not** established here, and the fix depends on it.
- **The correct `pool_size`.** Not derived. Raising it without moving off session mode may only
  move the ceiling.
- **Whether the 40,176 boots are themselves excessive.** Four cold starts a minute may be normal
  for this traffic or may indicate the functions are not being kept warm. Not measured.
- **The command path's true failure rate.** 56 logged `command_request_failure` rows do not match
  Wren's measured ~50% over 24 direct requests, so either command traffic is low or not every
  command failure logs. Not resolved.
- Nothing was changed. This is a read.

## CORRECTIONS after exact review (Plumb, non-author, on 1802e65)

Five claims below were overstated. They are kept and marked dead rather than edited away.

**1. ~~"The production 500s are pooler exhaustion."~~ Scope it to the COMMAND path.** What is
established is command-side: 56/56 `command_request_failure` rows carry `EMAXCONNSESSION`. The
8,990 read `XX000` rows are *consistent* with the same condition and nothing more — the read logger
discarded the message, and **no request-or-timestamp join to Supavisor is shown**. 241 of 9,231 read
failures remain unattributed even to `XX000`. Read-path attribution is **inference, not
measurement**.

**2. ~~"The functions cold-start ~4×/minute, each wanting a connection."~~ Dead — the causal link
is unfounded.** `postgres.js` connects **lazily on first query** and closes idle connections after
`idle_timeout`. **A boot row is not a connection attempt**, and an aggregate boot rate does not
establish >15 *concurrent* sessions. `EMAXCONNSESSION` establishes exhaustion; it does not
establish that cold starts caused it. Plumb's alternative contributor, which I did not consider:
**`max: 4` is a per-isolate pool** — four connections per isolate against a 15-connection ceiling
needs only four live isolates.

**3. ~~"The read path must log the error message."~~ DEAD, AND IT WAS A SECURITY REGRESSION.**
`read/diagnostics.ts` maintains an explicit deny-list — `message`, `detail`, `hint`, `query`,
`parameters`, `stack` — with the comment *"Intentionally omits message/detail/query/parameters and
similar secret-prone fields"*, and the header *"logging tokens, Authorization headers, bodies, query
values, or hashes."* Tests inject credential and query data into exactly those fields. **The
omission that cost weeks of investigation is a deliberate control, not an oversight.** The correct
ask is an **allowlisted classifier** for `EMAXCONNSESSION` (or bounded redaction), never the raw
message.

**4. ~~"retryable:false is wrong in effect; pooler exhaustion is the definition of transient."~~
Too coarse.** Pool exhaustion is *later*-recoverable, but **immediate same-request retries
amplify it**. Recoverability and retry-now are different claims. Any remedy must specify backoff,
`Retry-After`, or supervisor restart rather than simply flipping the flag.

**5. Wording narrowed:** ~~"the database was never the problem"~~, ~~"the driver stamps `XX000`"~~,
~~"14,602 refusals"~~ (measured: 14,602 *matching log rows*), ~~"a saturated pool rather than
contention"~~. Each asserted more than the evidence carries.

## Transaction-mode compatibility — corroborated, still a source argument

Plumb's independent audit extends mine and agrees: all three functions use `prepare: false` with
`max: 4` module pools; DB work runs inside `db.begin` with `SET LOCAL`; a full `supabase/` scan
found **no** `LISTEN`/`NOTIFY`, advisory locks, temp tables, cursors, prepared execution, or session
`SET`. That aligns with Supabase's guidance for the transaction port on serverless.

**It remains a source argument, not an end-to-end result.** Local config has the transaction pooler
disabled, so nothing in this tree has executed through it.

## What an operator change would need first

1. **Identify the active key.** `SWARM_DATABASE_URL` overrides `SUPABASE_DB_URL`. Verify which is
   set and confirm host/port **without exposing the URL**.
2. **A bounded smoke/canary across all three functions** — `read`, `command`, `capability` — plus a
   rollback path, before and after.
3. **Verify client-side**, by re-running Wren's probe. The command path under-logs failures, so log
   counts cannot confirm recovery.
4. Treat **`max: 4` per isolate** as an orthogonal lever: lowering it may relieve the ceiling
   independently of pooler mode.
