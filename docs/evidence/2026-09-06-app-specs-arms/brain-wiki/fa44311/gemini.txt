### Inversion Review: Load-Bearing Choices

1. **Hierarchy as Dot-Naming (`area.topic`) without Renames**
   * *Inversion:* First-class hierarchical paths/metadata with atomic rename support.
   * *Predicted failure:* Dotted names collide with versioning semantics (e.g. `release_notes.v2`); lack of rename creates dangling tombstone topics ("Moved to..."), fragments 20-version history windows, and breaks backlinks targeting old names.
   * *Verdict against spec:* Inversion beats spec on link integrity; spec's "no rename" permanently leaks dead topics.

2. **Client-Generated Index Pages vs. Stored Curated Indices**
   * *Inversion:* Stored, human/agent-curated `<area>.index` topics.
   * *Predicted failure:* Ephemeral index pages cannot provide curated narrative context; falling back to line 1 or "updated by" yields low-signal navigation.
   * *Verdict against spec:* Spec beats inversion on concurrency: stored index topics become multi-agent write hotspots that rapidly churn the 20-version window.

3. **Client-Side Background Body Crawl for Backlinks vs. Server-Side Extraction**
   * *Inversion:* Server-side link extraction on `brain put` stored in an edge/relational index.
   * *Predicted failure:* Client-side crawl requires $O(N)$ HTTP requests per session/CLI run; causes network stampedes, rate-limit exhaustion, mobile battery drain, and stale/partial backlink graphs until crawl completes.
   * *Verdict against spec:* Inversion beats spec decisively. Pushing full-corpus graph indexing to client browsers and CLI caches is fragile and scales poorly.

4. **Implicit Mention Linkification vs. Explicit `[[topic]]` Syntax**
   * *Inversion:* Explicit `[[topic]]` wiki syntax.
   * *Predicted failure:* Implicit matching turns common words into accidental graph edges; adding a new topic retroactively rewrites the backlink graph across historical topics.
   * *Verdict against spec:* Inversion beats spec on graph stability, though spec adheres to prior design doctrine.
