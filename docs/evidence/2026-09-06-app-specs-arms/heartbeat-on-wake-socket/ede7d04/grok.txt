## DEFECT

**D1 — §2.3. `idleFrame()` has two shapes, and the runtime attaches it with no phase guard.**  
The JSON in §2.2 is `phase: "idle"`. The same bullet says `idleFrame()` “increments the sequence exactly as `flush()` does” (`activity.ts:318-329`), and `flush()` uses `phase: this.phase`. Then: “the runtime attaches `idleFrame()` to every reconcile read and to every 15 s fallback read.” Reconcile still runs during work (`runtime.ts:1549-1551`).  
- If the frame is always idle, the site keeps it (`agent-activity.ts:137-138`, newer sequence on the same `streamId`) and the panel shows idle while a tool runs.  
- If it is a `flush()` clone, L1 rejects `not_idle` and `activityPublishFailures` ticks every five minutes of work.  
L2’s tests never cover “reconcile during `tool-running`”. Say: return `null` and do not increment unless `phase === "idle"`; attach only then.

**D2 — §2.3. `activityIdleCarrier: "edge"` until the capability is seen does not match the idle timer being removed.**  
The field “says which call currently carries idle frames (`edge` until the capability has been seen)”. The same section removes `armHeartbeat()` for idle and L2’s test is “a read without the capability seen carries nothing”. Nothing then carries idle frames, but status says `edge`. L2-first (claimed safe) goes silent after the one into-idle edge frame.

## GAP

**G1 — §2.3 / §2.2. CamelCase `idleFrame()` vs the snake_case activity body.**  
`idleFrame()` returns `AgentActivityFrameRequest` (`activity.ts:47-57, 318-329`). `parseActivityRequest` closes on `workspace_id`, `stream_id`, … (`activity/core.ts:15-24`). The only map is inline in `AgentActivityEndpointTransport` (`:119-128`). Attach the return value as `activity` and every frame is `invalid_request`. L2 is not given one serializer both paths use.

**G2 — §2.3. `activityLastErrorCode` cannot hold `ACTIVITY_REJECT_CODES` as written.**  
The field is closed on `ActivityPublishErrorCode` (`activity.ts:17-22`; `STATUS_ACTIVITY_ERROR_CODES` at `control.ts:294-300, 607-611`). Reject codes are `invalid_request | forbidden | workspace_mismatch | not_idle`. Writing `not_idle` into the status file makes `listen status` report malformed. Spec does not say to extend the set, prefix, or map to `activity_http_rejected`.

**G3 — §4 L2. `supervisor.ts` is the writer and is not named.**  
`activityPublishFailures` is initialised and incremented in `supervisor.ts:321, 633-637`. `activityIdleCarrier` and read-path rejects have to land in the same persist path for the live control (`activityIdleCarrier: read`) to be true. L2 names `control.ts` and `cli.ts` only.
