**D-036 ARM — ADVERSARIAL SYSTEMS (Opus 5)**
Under review: `docs/design/2026-09-06-HEARTBEAT-ON-WAKE-SOCKET.md`, commit fa44311, branch `spec/app-backlog`.
Method: every `file:line` citation opened; the trust boundary attacked first; two questions settled by read-only probe against the running local stack, each with a positive control on the same invocation. Probes deleted; nothing modified.

### LIVE PROBE TRANSCRIPT (what D1 and D2 rest on)

Read-only DB reads:
```
policies on realtime.messages:
   SELECT {anon}          "agent receives its own wake"
   SELECT {authenticated} "workspace members receive agent activity"
   SELECT {authenticated} "workspace members receive signals"
anon: { USAGE on realtime: true, INSERT on realtime.messages: true, SELECT: true }
hmac: extensions.hmac
```
This confirms three spec claims: one SELECT policy on the activity topic, two more SELECTs and no INSERT from the wake migration, no INSERT policy anywhere, and `anon` already holding both grants while RLS still refuses (as `PUSH-DELIVERY.md:312` recorded).

anon Realtime joins, one invocation, `private:true, ack:false, self:false`:
```
CONTROL cswarm-wake:{live wake_id}      -> SUBSCRIBED
TEST    cswarm-activity:{workspace_id}  -> CHANNEL_ERROR
        "Unauthorized: You do not have permissions to read from this
         Channel topic: cswarm-activity:52ac7c68-...-80ab2743e2e0"
SEND on the JOINED control channel, RLS having NO INSERT policy -> resolves: "ok"
SEND on the UNJOINED activity channel (REST fallback)           -> resolves: "ok"
```
The control proves the probe reaches the gate it claims to test: same client, same call, same options, admitted on the topic that has an anon SELECT policy and refused on the one that does not.

### DEFECTS

**D1 — DEFECT. §2.3 (and §0, §4/L1, §2.6 row 1). The listener cannot join the activity topic at all, so the socket the whole spec is built on never opens.**

Claim: *"§2.3: `WakeSubscriber` gains one method, `publishActivity(frame)`: it opens (once) a second private channel on the same `realtime` client for `cswarm-activity:{workspaceId}`, and sends … over the socket."*

The wake client authenticates as `anon` (`src/listener/wake.ts:136-140`, `:433 setAuth(this.target.anonKey)`). Realtime evaluates the SELECT (read) policy at **join** time on a private channel and refuses the join when it fails. The only SELECT policy on `cswarm-activity:{uuid}` is `TO authenticated` (`20260902000003_realtime_agent_activity.sql:4-17`). The spec adds an INSERT policy `TO anon` and no SELECT policy, so the join is refused — measured above, verbatim.

This is not a novel inference; the repo already pins the behaviour. `tests/p1-local/wake-realtime-auth.test.ts:219-231` asserts SUBSCRIBED when the anon SELECT policy admits the topic and `:232-268` asserts CHANNEL_ERROR for every topic it refuses. The wake lane needed a `TO anon` SELECT policy to let its own listener join its own private topic; this spec omits the equivalent.

Why it fails silently: with the channel unjoined, `canPush()` is false, so `send()` takes realtime-js's REST fallback (`RealtimeChannel.js:522-560`, verified at the cited 2.110.8) — one HTTPS POST per heartbeat plus a `console.warn` per frame. §0's *"5,760 … to zero"* and §3's *"≈ 600 edge calls a day"* survive only on a technicality (they are not *edge function* calls); the design bar the spec quotes, "extremely cost efficient", is not met, because a per-heartbeat HTTP request is what the spec set out to remove. §2.3 names this fallback as a rare degradation; measured, it is the only path.

Nothing in the lane set detects it. L1's five tests exercise the INSERT policy in SQL and never make a client join. L2's live control asserts `activityTransport: "socket"`, but §2.3 derives that field from `wake.state !== subscribed` — the **wake** channel's state — so it reads "socket" while every frame goes over HTTP. §6 lists three lesser unknowns and not this one, though the map the spec was authored from flagged it ("Unknowns: Safety of an INSERT/presence policy for an anon-keyed listener … no design evaluated it").

To be buildable: add a SELECT policy admitting `anon` on `cswarm-activity:{uuid}` (gated as `swarm.wake_topic_authorized` gates the wake topic), then state the consequence it creates — an anon-key listener with read on that topic receives every other agent's frames in its workspace, including their `toolTitle`. Today no anon role can read that topic. That is a new leak and needs a stated ruling, not a silent grant. L1 must own a client-join test.

**D2 — DEFECT. §2.6 row 2 (and §2.3, §4/L2). `send()` resolves "ok" when the policy refuses, so the refusal counter and the edge fallback have no signal.**

Claim: *"policy refuses (bad proof, rotated wake id) | `send` resolves `error`; controller counts `activityPublishFailures`, sets `activityLastErrorCode = activity_publish_refused`, falls back to the edge for that frame".*

The code the spec cites contradicts it. At `RealtimeChannel.js:563-566`, inside the cited `:520-566`:
```js
const push = this.channelAdapter.push(args.type, args, ...);
if (args.type === 'broadcast' && !this.params?.config?.broadcast?.ack) {
    resolve('ok');
}
```
With `ack: false` — the default (`:94`) and the option every channel in this tree passes (`site/src/lib/commonswarm.ts:191-196`, `tests/p1-local/wake-realtime-auth.test.ts:193`) — `send()` resolves "ok" before the server answers. Measured: a send on a **joined** private channel, on a table with no INSERT policy at all, resolved "ok". The REST fallback resolved "ok" too, so neither path carries a refusal.

Consequence: `activityPublishFailures` stays 0 and `activityLastErrorCode` stays null while every frame is dropped by RLS; "falls back to the edge for that frame" never fires; the panel goes dark and `cswarm listen status` truthfully reports zero failures. Same shape as the failure `PUSH-DELIVERY.md:312` warned about ("no wake would ever be sent while `listen status` truthfully said `push`"), and the class AGENTS.md records under "A negative result must reach the path it claims to test".

The spec must specify `broadcast: { ack: true }` and establish — not predict — that Realtime returns a push error on RLS refusal. Neither is stated, and §6 does not list it. `ack: true` also adds a reply message per frame, which bears on §3's "Realtime messages unchanged".

**D3 — DEFECT. §2.2 and §0. The proof covers three of the frame's ten fields, so a member can forge the other seven for another principal.**

Claim: *"`proof = base64url(hmac_sha256(key = wake_id, message = principalId || ':' || sequence || ':' || streamId))`"*, with §0 asserting *"nothing an anon-key client can forge is accepted"* and §2.2 bounding the exposure at *"principal X looked alive again for one frame"*.

The published payload has ten keys (`agent-activity.ts:19-29`). The proof binds three. `phase`, `signalId`, `toolTitle`, `elapsedMs`, `workspaceId` and `emittedAt` are unauthenticated.

The attacker is an ordinary workspace member and needs nothing they do not have:
1. Every member may SELECT the activity topic (`20260902000003:4-17`), so they read a real frame from principal X including its `proof`.
2. The anon key is public — it ships in the site bundle and the live page's meta tag (AGENTS.md, "Deploying the marketing site").
3. They re-insert the **same** principalId, streamId and sequence — so the captured proof still verifies under §2.2's recompute — with arbitrary `phase`, `signalId`, `toolTitle`, `elapsedMs`, and an `emittedAt` of their choosing. The INSERT policy admits it.

It reaches the panel by two routes the replay argument misses:
- `agent-activity.ts:137`: `if (!current) return true`. A tab that just loaded holds no frame for X, so the forged frame is accepted outright and rendered ("Now: `<attacker text>`", `LiveDashboard.astro:2532`).
- `agent-activity.ts:139`: across streamIds the comparison is `Date.parse(next.emittedAt) >= Date.parse(current.emittedAt)`. Once the listener restarts and takes a new streamId, a captured old-stream frame with a forged future `emittedAt` wins every comparison, permanently.

Neither is "one frame". The exposure is: any member can put arbitrary text and an arbitrary phase on another agent's live panel and keep it there. Today that is impossible — the edge stamps `principalId` only after authenticating the agent token (`activity/index.ts:83-131`), so frame content is server-vouched. Fix is small and belongs in the spec: HMAC over a canonical serialisation of the whole payload.

**D4 — DEFECT. §2.1 and §2.5. The socket path drops the edge's credential redaction and its bounded parser, while the spec states nothing changes.**

§1 records the behaviour correctly — *"the server adds `principalId` and `emittedAt` and re-redacts `toolTitle`"* — and §2.1 then asserts *"nothing on the reading side is rewritten"*, §2.5 *"Its parser gains nothing."* Neither section says the listener must take over the edge's work.

Three defences disappear with nothing replacing them:
- `redactCredentialText(frame.toolTitle).slice(0,160) || "Tool"` (`activity/index.ts:135`). The listener applies only `sanitizeText(update.title).slice(0, ACTIVITY_TOOL_TITLE_MAX)` (`src/listener/activity.ts:249`) — a different function that does not redact credentials.
- `parseActivityRequest`, the closed parser with cross-field invariants (`activity/core.ts:44-84`).
- `ACTIVITY_REQUEST_MAX_BYTES = 4_096` (`core.ts:3`), enforced by `boundedJson` (`index.ts:52-75`). The §2.2 policy checks a signature and a principal; it bounds no size and no shape.

The sharp consequence: `src/host/credential-redaction.ts:20-26` defines `cswarm-wake:[A-Za-z0-9_-]{43}` as a credential shape precisely because the wake topic **is** a bearer capability — the same `wake_id` this spec makes the HMAC key. A tool title containing the wake topic is redacted today by the edge; on the socket path it is broadcast in clear text to every member tab, leaking the secret the proof scheme is keyed on and (per D3) letting any reader mint proofs for that principal from then on.

**D5 — DEFECT. §2.4. "An old site build that drops unknown keys" is false, and §4's deploy order does not cover it.**

`site/src/lib/agent-activity.ts:78`:
```js
if (Object.keys(record).some((key) => !FRAME_KEYS.has(key))) return null;
```
An old build does not drop the unknown key — it rejects the entire frame. Old and new behave oppositely: on a deployed site without L3, every socket frame is discarded and the panel shows "no frames" for every upgraded seat. §4's lane order (L3 before L2) helps only if the site is actually **deployed** before listeners upgrade; the production line says "migration → client" and never names the site deploy, which is a separate Vercel deploy. It must read: migration → site deploy → client.

### GAPS

**G1 — GAP. §2.3, `activityTransport`.** "`parseListenerWake`'s closed list gains it" is ambiguous in a way that decides whether status breaks. `WAKE_STATUS_KEY_SET` (the allowed set, `control.ts:388`) and the required-key loop (`:407-409`) both read the same `LISTENER_WAKE_STATUS_KEYS`. Adding the key to "the closed list" makes it **mandatory**: any wake block without it — a status file written by the previous build, or an older daemon answering a newer CLI — returns null and the whole wake block vanishes from `cswarm listen status`. That is the v0.1.46 null-status failure AGENTS.md records. The spec must say required or optional, and what a missing key means.

**G2 — GAP. §2.2, the HMAC's exact bytes.** Two lanes must agree byte-for-byte — L1 in SQL (`extensions.hmac`, confirmed present) and L2 in TypeScript — and the spec gives neither a canonical string nor a test vector. Unspecified: key as text or decoded bytes; whether `principalId`/`streamId` in the message are the payload's text or the stored `principal_id::text` (Postgres renders uuid lowercase; the listener's casing is not pinned); and how `sequence` is rendered. base64url in SQL needs no spec text — `20260906000010:21-27` is the in-tree precedent.

QUOTE-BACK: # Heartbeat on the wake socket: retire the activity edge call
VERDICT: FAIL
REASON: The socket the design depends on cannot be opened — an anon listener's join of `cswarm-activity:{ws}` is refused because the spec adds an INSERT policy but no anon SELECT policy (measured, with a positive control) — and four further defects stand: `send()` resolves "ok" on refusal so the fallback has no signal, the proof authenticates three of ten fields so any member can forge another agent's phase and tool title, the socket path silently drops the edge's credential redaction and byte cap, and §2.4's "an old site build drops unknown keys" is false where the code rejects the whole frame.
