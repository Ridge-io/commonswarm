### DEFECT 1 — §2.1 / §4 L1: re-creating the view as `SELECT p.*` publishes the wake join credential

§2.1: "`swarm_read.agent_principals` projects both." §1 cites the existing shape as `20260730000001:30-35` (`SELECT p.*`), and L1's file list says "view projection".

The tree moved under this sentence. `20260906000010_wake_delivery.sql:22-30` added `swarm.agent_principals.wake_id` (plaintext, `NOT NULL`, unique) **and did not re-create the view** — `grep -n "VIEW" supabase/migrations/20260906000010_wake_delivery.sql` returns nothing. The last `CREATE OR REPLACE VIEW swarm_read.agent_principals` is still `20260730000001:30`, whose `p.*` was expanded before `wake_id` existed, so `wake_id` is **not** projected today.

A lane that re-creates the view with the cited `SELECT p.*` to add `assigned_model` re-expands the star and appends `wake_id` too. `cswarm-wake:{wake_id}` is the join credential: `wake_topic_authorized` (`20260906000010:59-70`) admits any subscriber who presents a live id for a principal with a live token. Every authenticated member of the workspace could then read the other agents' wake topics from PostgREST and join them. That is a shipped boundary this spec silently removes.

Fix: L1 enumerates the projected columns (or excludes `wake_id` explicitly), and its migration control asserts both `assigned_model`/`model_assignment_state` **are** projected and `wake_id` is **not** — the same shape as the existing control at `20260730000001:112-127`.

### GAP 1 — §2.2 / §2.3: `assignment_state` has no value for "no assignment", and the stated site rule then marks a false mismatch

The closed set is `honoured | no_mapping | cli_override`, default `pending`. Neither §2.2 nor §3 says what the listener sends when `assigned_model` is NULL — the state of every seat today.

Two of the three reachable choices produce a wrong row under §2.3's own rule:
- `--model X` on grok with **no** assignment (the ordinary way grok seats are started) → §2.2 step 1 sends `cli_override`; §2.3 marks on `cli_override` unconditionally, so the row reads `not honoured (cli override)` with nothing overridden. §3's acceptance line covers only "`--model X` with an assignment Y".
- No `--model`, no assignment → if the listener sends `honoured`, §2.3's second clause compares `normalizedModel(model)` against `normalizedModel(null)`, they differ, and the mark shows on every unassigned seat.

Only "omit the field" is correct, and the spec never says it. A lane author must invent the rule, and two of its three guesses are visibly wrong on the common row. Name it: the listener omits `assignment_state` when `assigned_model` is NULL, and §2.3's `cli_override` and `honoured` clauses both require a non-null `assigned_model`.
