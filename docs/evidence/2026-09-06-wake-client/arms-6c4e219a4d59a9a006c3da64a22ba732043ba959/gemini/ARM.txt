**Check 1: Wait contract**
- Attempted refutation: The socket drop during the five-minute wait might leave the loop asleep.
- Refutation failed: `wake.ts:onSubscribeStatus` calls `emitPending("state")` when the socket disconnects, which immediately resolves `waiter` (the promise returned by `next()`), correctly breaking the 5-minute wait.
- Attempted refutation: A wake might restart `reconcileDueAt`.
- Refutation failed: `reconcileDueAt` is only updated when `!skipRead` is true (i.e. a Reconcile API call actually occurred). Wakes set `skipRead = true`, thus skipping the update.
- Attempted refutation: Two wakes arriving during one claim might result in the second one being dropped.
- Refutation failed: `emitPending("wake")` correctly collapses multiple wakes into a single pending state that `next()` will immediately consume on the next loop iteration (coalescing them).
- Attempted refutation: `next()` is raced against a separate timer, risking lost promises.
- Refutation failed: `next()` manages its own internal `setTimeout` and cleanup. The main loop's `idleSleep` is bypassed explicitly when `wakeSubscriber` has a topic.
