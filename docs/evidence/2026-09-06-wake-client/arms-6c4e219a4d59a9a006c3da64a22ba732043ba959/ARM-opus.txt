=====================================================================
FINDING 1 (DEFECT, measured) — the 50/min wake-claim budget does not bound
the claim rate. Past the budget the listener issues MORE server work, not less.
=====================================================================

Spec, docs/design/2026-09-06-PUSH-DELIVERY.md §2.3:
  "WAKE_CLAIMS_PER_MINUTE_BUDGET = 50 is enforced client-side: past it the subscriber
   stops claiming on wakes for the rest of that minute and the reconcile catches up."
Spec §2.4, "Claim rate limit reached" row:
  "the client budget (§2.3: 1 s coalescing, 50 wake-claims/min) keeps one listener at
   <= 51/min and two at <= 102"
The whole argument that the server's DELIVERY_CLAIM_RATE_LIMIT_PER_MINUTE = 120 refusal
(which writes an audit row AND a swarm.security_alerts row) is never approached rests on
that <= 51/min number.

Code: src/listener/runtime.ts:1170-1188.
  1170  if (reason === "wake" && !rateLimited && !wakeSubscriber.overWakeBudget(now())) {
  ...
  1185      skipRead = true;
When overWakeBudget() is true the ONLY effect is that skipRead stays false. Control then
falls through to the ordinary read branch at :1192 and on to the same claim_agent_inbox
call. Nothing waits, nothing polls: the loop still runs once per latched wake, because the
top-of-loop wait is wakeSubscriber.next() (:1160-1164) and a latched wake resolves it
immediately (src/listener/wake.ts:305-317, the `pending` fast path).
Worse, src/listener/runtime.ts:1556-1557 then calls noteClaim() and NOT noteWakeClaim(),
so wakeClaimTimes never grows past 50, overWakeBudget() stays permanently true for the
rest of the minute, and every further wake in that minute costs one read POST plus one
claim POST instead of the one claim it was trying to avoid.

MEASURED, not reasoned. Probe test (real WakeSubscriber + real runListenerRuntime, fake
Realtime channel, frozen clock so the whole run is inside one clock minute; each claim
emits the next wake, abort at 70):

  test("PROBE: wake claims past the 50/min budget")   -- my file, arm worktree only
  result: stop=cancelled  claims=70  reads=20
  assertion `claims <= 51` FAILED with "claims in one frozen minute: 70"

50 wake-claims, then 20 read+claim pairs, all inside one clock minute. The spec's ceiling
is 51. The same run also shows 20 read POSTs the budget was supposed to prevent. With a
wake rate above ~120/min -- reachable by the very cases §2.4 enumerates (duplicate wake
from two listeners on one principal, reconnect storm, a burst of directed signals) -- the
client sails through the server limit and trips the security_alerts row §2.3 says the
budget exists to avoid.

No delivery is dropped (the read+claim path still claims), so this is a rate/cost defect,
not data loss. It is still a defect against the stated contract, and it is the exact row
the review brief asked me to refute: "the per-minute wake-claim budget (50/min) and what
happens when it is hit (must degrade to poll, never drop a delivery)". It does not degrade
to poll. It escalates.

There is also NO test for this row at runtime level. tests/listener-wake.test.ts:430
("wake claim budget is 50 per clock minute") asserts only WakeSubscriber.overWakeBudget()
in isolation; it never runs the runtime, so the runtime's response to a hit budget is
unmeasured. That is why two review arms and the author's own mutation table missed it:
the mutation row "WAKE_CLAIMS_PER_MINUTE_BUDGET note 50 wake claims -> overWakeBudget true"
proves the flag flips, not that anything acts on it.

Suggested fix (one line, plus a test): when overWakeBudget() is true, treat the pass like
the poll cadence -- i.e. do not fall through to an immediate read; sleep to
min(reconcileDueAt, now + nextIdlePollMs(...)) before the next iteration. Then add a
runtime test asserting claims <= 51 in a frozen minute under continuous wakes.

=====================================================================
NITS (design gaps the spec allows, or coverage holes — not the FAIL)
=====================================================================

N1. §2.4 "Wake id rotated" has ZERO test. grep setTopic tests/ returns only the class stub
    at tests/listener-wake.test.ts:275 and two calls with the SAME topic (:391, :414).
    topicRotatedAt is never asserted anywhere. The live control exercised rotation once,
    but the tree has no control that would fail if setTopic's rotation branch broke.

N2. Rotation race in src/listener/wake.ts:288-298. setTopic() does `void this.detachChannel()`
    and then calls connect() synchronously. detachChannel's tail (:437-440) later runs
    "if (this.connectionState === 'subscribed') { connectionState='disconnected';
    subscribedAt=null }". connect() sets state to "connecting", so the normal path is safe,
    but if the NEW channel's SUBSCRIBED callback lands before the old unsubscribe()
    promise settles, the stale detach clobbers a live subscription back to disconnected and
    the listener reports poll while pushing. Cheap fix: capture the channel identity and
    only clear state when this.channel is still that channel.

N3. The wake branch (runtime.ts:1154-1158) gates on hasTopic, not on mode==="push". My
    probe took wake ticks while the subscriber had never reported SUBSCRIBED. Harmless
    today (a wake only exists if the socket delivered one) but it means "mode push only
    while subscribed" is true of the STATUS field and not of the claim path.

N4. "mode-change hours skipped for lapse" (read-health.ts:513-515) IS a detection hole,
    but not the one to worry about. A wedged push-mode listener whose socket half-opens
    and never errors does NOT change mode, so its hours are scored normally at
    expectedClaims = 3600000/300000 = 12, and the 5-minute reconcile (runtime.ts:1160,
    capped by waitCapMs()) really does fire and really does claim -- so it keeps hitting
    12/hr and is correctly healthy, at 5-minute latency instead of 15 seconds. Nothing is
    lost; the reconcile catches it, exactly as §2.4's half-open row says. The actual hole
    is a listener that FLAPS mode every hour: every hour gets modeChanged=true, so
    throughput-lapse scoring is permanently suppressed for it even if it genuinely stops
    claiming. One flap per hour is enough. Worth a cap (e.g. skip at most N consecutive
    mode-change hours) but the spec does not forbid the current rule.

N5. Write amplification: emitWake() runs on every loop pass and every wake tick, and the
    supervisor persists status.json on every "wake" event. At the wake rates §2.4
    contemplates that is one secure file write per wake. Not a correctness problem.

N6. No behavioural control for the review brief's item 2 ("a lost wake ends in the delivery
    being claimed within the reconcile bound"). tests/listener-wake.test.ts:591 asserts
    only that LISTENER_RECONCILE_POLL_MS === 300_000 and formats as "5m" -- a constant, not
    a behaviour. The wait-contract code is right as far as I can read it, but nothing in
    the tree fails if the reconcile deadline stops being applied.
