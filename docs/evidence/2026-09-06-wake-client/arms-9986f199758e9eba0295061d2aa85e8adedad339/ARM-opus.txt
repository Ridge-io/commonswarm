FINDING (DEFECT, measured) — the budget pause makes `listen status` state
two things that are false, and a test pins one of them.
=====================================================================
Reached by: subscribe successfully, then hit the client-side 50/min budget. Nothing is wrong
with the socket and no server refused anything.

Probe (real WakeSubscriber, fake channel, SUBSCRIBED, 50 noteWakeClaim in one frozen minute):
  connectionState before: subscribed
  connectionState after : subscribed
  snapshot: {"mode":"poll","subscribedAt":"2026-07-30T00:00:10.000Z","reconnects":0,
             "lastWakeAt":null,"lastReconcileAt":null,"errorCode":"rate_limited",
             "topicRotatedAt":null,"rateLimited":true}
  SENTENCE: poll every 15s. Realtime not connected (rate_limited).

Two false clauses in one operator-facing sentence:
  (a) "Realtime not connected" — connectionState is `subscribed`; the socket is up and the
      channel is joined. Source: src/listener/wake.ts:212, the poll branch of
      listenerWakeStatusSentence (:202-213), which is selected purely on mode and hard-codes the reason.
  (b) "(rate_limited)" — nothing rate-limited this listener. errorCode is set to
      "rate_limited" for the CLIENT budget at wake.ts:259-266 because wakeClaimPaused()
      (:395-397) folds the client budget and a server 429 into one predicate. Spec §2.3
      assigns `rate_limited` to a server refusal, and §2.4's "Claim rate limit reached" row
      says a genuine 429 "writes an audit row AND a swarm.security_alerts row". So the
      operator who sees `wake_error_code: "rate_limited"` in events.ndjson (supervisor.ts logs
      it) will go looking for a security_alerts row that does not exist. That is a concrete
      wrong-triage cost, at exactly the moment the seat is busiest.
  (c) minor, same root: the status JSON now emits mode "poll" together with a NON-NULL
      subscribedAt, which parseListenerWake permits (control.ts:426 only constrains push).
      A reader sees "poll" and a live subscription timestamp and cannot tell which is true.

This is the repo's own named failure mode, twice over. "Honesty is not sufficient": the
sentence must say what is true now and what happens next, and here it says the opposite of
what is true. "Claim controls prove stability, not truth": tests/listener-wake.test.ts:625
asserts `snap.errorCode === "rate_limited"` for the budget case, so the new control pins the
wrong claim and will keep pinning it. The behaviour underneath is correct — this is a state
word and a copy defect, not a delivery defect, and nothing is lost — but it is verified in the
tree by running the code, and it is not a gap the spec allows: the spec allocates
`rate_limited` to a server refusal and never sanctions "not connected" while subscribed.

Remedy (small): give the client pause its own member of WAKE_ERROR_CODES — e.g.
`wake_budget` — set it in snapshot() only when `nowMs >= rateLimitedUntil && overWakeBudget()`,
and add a third branch to listenerWakeStatusSentence for it, something like
"poll every 15s. Push is connected; wake claims are paused for the rest of this minute."
Then flip :625 to assert the new code and add a sentence assertion for it.
