"mode: poll while paused, with subscribedAt set" — DEFENSIBLE. I checked it.
=====================================================================
The coordinator asked me to rule on this either way, so: it is right, and my round-2 sub-nit
(c) about the contradiction is answered.
`mode` in this design names **how the listener learns there is work**, not the socket's state.
§2.3 already sets the precedent the report cites: "A `rate_limited` refusal, if one still
arrives, flips the listener to the 15 s poll for 60 s and records `wake.rateLimited`" — the
listener polls while the websocket is still perfectly joined, because a claim-endpoint refusal
has nothing to do with the socket. The client budget is the same shape, so mode poll is the
consistent answer, not an exception.
§2.4's mode rule ("push only while subscribed") also survives: subscribed is still NECESSARY
for push (snapshot.mode, wake.ts:268-272, requires connectionState === "subscribed"), it was
never claimed to be SUFFICIENT, and no row of §2.4 says a subscribed listener must print push.
What made round 2 wrong was not the mode value — it was that the only place carrying the socket
fact said the opposite. Now `subscribedAt` is non-null, `errorCode` is `wake_budget`, and the
sentence opens with the word "Subscribed", so the JSON reader and the human reader are told
both facts and neither has to guess which is true. Test :628 pins `snap.subscribedAt` non-null
alongside mode poll, so the pairing is deliberate and controlled rather than incidental.
