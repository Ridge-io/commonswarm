## 11. The clamp's clock

**Finding. `remaining_ms` is not the INSERT clock. An explicit horizon is still silently shortened. The comment that says otherwise is false.**

```6379:6384:supabase/functions/command/index.ts
  /**
   * The window left on the root, measured by POSTGRES against the same
   * statement_timestamp() the clamp uses. Never recomputed from Date.now():
   * Deno and Postgres do not share a clock, and a skewed comparison lets an
   * explicit horizon pass the refusal and then be silently shortened by the
   * clamp, which is the one branch this design calls dishonest.
```

`remaining_ms` is `EXTRACT(EPOCH FROM (until - statement_timestamp())) * 1000` in `resolveThreadRoot`'s SELECT (`:6424-6425`). The clamp uses `statement_timestamp()` of the later `INSERT` (`:6823-6832`). Those are different statements. `statement_timestamp()` advances per statement.

Handle order: attachments (`:7538`) and the rate bucket (`:7564`) run *before* `resolveThreadRoot` (`:7626`). The GREATEST comment (`:6813-6822`) still says they run between that SELECT and the INSERT. They do not. The real gap is one client round-trip from the SELECT to the INSERT.

Concrete case. SELECT at `T`. Root `until` is `T+5000ms`. `remaining_ms` is `5000`. Caller sends `until_ms: 5000`. `5000 > 5000` is false (`:7665`), so no 409. INSERT at `T+8ms`. SQL `LEAST(T+8ms+5000ms, T+5000ms)` stores `T+5000ms`. The caller asked for 5000ms from the INSERT and got 4992ms.

That is the dishonest branch named at `:7645-7648` and in the design at `docs/design/2026-09-04-chat-platform-reconciled.md:642-643`. The 200 body carries `signal.until` (`:6871`). There is no 409 and no other tell. The planned composer is told to show the inherited ceiling (`design:647-648`); sending that ceiling as `until_ms` lands in this band on every post.

How much: the SELECT-to-INSERT gap, typically milliseconds, the top of the allowed explicit window. Under an event-loop stall it can grow. It cannot exceed the 1s floor without hitting GREATEST.

**Outlive / CHECKs.** On the happy path `LEAST` caps at the ceiling (and `toISOString()` truncates microseconds early, which shortens). `CHECK (until > created_at)` and the 30-day CHECK do not fire.

GREATEST (`:6823-6832`) is the remaining outlive path. It fires if the root's remaining at INSERT is `<= 1ms`, which needs ~1s of stall after a SELECT that required `until > statement_timestamp() + interval '1 second'` (`:6451`). Theoretical. If it did fire, `until = created_at + 1ms` while the root is already expired. The comment at `:6820-6822` says no reader can see either row. That is false: `swarm_read.signals` has no `until` filter, and a live feed (`until > now`) would show the reply for 1ms without the root. I do not treat that stall as reached.
