## 4 / 11 / 16 / 22. Thread clamp

No finding that a stored row can outlive its root.

`postSignal` computes `until_value` once in a CTE and the `WHERE` tests that same value (`command/index.ts:6873-6940`). Explicit path: `now + Nms`, then `GREATEST(..., now+1ms)`. Defaulted path: `LEAST(now+Nms, ceiling)`, then the same floor. `WHERE ceiling IS NULL OR until_value <= ceiling`. `statement_timestamp()` is stable inside one statement, so the CTE and the `WHERE` agree.

`CHECK (until > created_at)`: the floor is `now+1ms` and `created_at` is `statement_timestamp()` in the same statement, so `until > created_at`. `CHECK (until <= created_at + 30 days)`: the validator caps `until_ms` at `SIGNAL_MAX_UNTIL_MS` (`:1804-1808`); a clamped reply is at most the root's `until`, which already passed that check.

Explicit `until_ms` is not `LEAST`'d. If it no longer fits, zero rows → 409, not a silent shorten. The floor can raise a defaulted value past the ceiling when the root has &lt;1ms left; that path returns null and 409 (`:6951-6958`, `:7840-7868`). The `WHERE` has no other arm, so a 409 here is the horizon, not a lying FK miss (those throw).

`untilExplicit` is `command.until_ms !== undefined` (`:7837`). The atomic sentence branches on the same test (`:7862`). They cannot disagree.
