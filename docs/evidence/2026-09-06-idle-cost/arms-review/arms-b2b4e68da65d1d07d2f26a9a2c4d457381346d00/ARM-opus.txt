NOT REFUTED — DEFECT (verified in the tree, with a positive control):
 A cadence change WITHIN an hour is neither handled nor stated. The bucket is
 last-writer-wins: src/listener/read-health.ts:213 `if (hour) hour.cadenceMs =
 cadenceMs;` overwrites whatever the hour was actually run at. The doc comment
 at read-health.ts:204 ("the claim cadence in force at `ts` for that hour's
 expected count") asserts a single cadence per hour that the code does not
 guarantee, and neither the README nor any comment states the last-writer rule.

 The reachable sequence is ordinary, not exotic: a seat idles an hour at the
 60 s back-off floor, then ONE delivery arrives near the end of that hour. The
 delivery resets the idle streak, so the next idle_poll event carries the 15 s
 base (src/cloud/idle-poll.ts:90-107 resets to base on any delivery;
 supervisor.ts:421-429 records that interval against the SAME hour). The hour
 is then scored at 240 expected against ~60 real polls.

 Measured against this SHA's own dist (node probe, summarizeListenerReadHealth):
   60 polls at 60 s + one 15 s cadence record at :59:30 in the same hour
     -> {hourStart 2026-09-01T10:00Z, claims 61, expectedClaims 240,
         ratio 0.254} and throughputLapseHours contains that hour.
   src/cli.ts:4686 renders this as
     "Claim throughput fell below 0.50 for the full hour at <hour>: 61/240
      expected (0.254)."
 POSITIVE CONTROL (same 61 claims, only the mid-hour 15 s record removed):
     -> {claims 61, expectedClaims 60, ratio 1.017}, throughputLapseHours [].
 The single mid-hour cadence write is the whole cause. This is the same
 false-lapse-on-a-healthy-listener failure that round 5 set out to remove,
 narrowed from "every past hour" to "the hour in which the cadence changed".

 The lane's own tests do not reach it: `healthHourThenReset`
 (tests/listener-host-limits.test.ts:371) deliberately records the later
 cadence at NEXT_HOUR, so the mid-hour path has no control on it.

 Fix shape (either is acceptable): accumulate expected claims by summing the
 per-poll interval into the hour bucket (expected = sum of intervals / hour),
 or keep the MINIMUM-expected (i.e. largest cadence) seen in the hour, or —
 if the lane chooses to defer — say plainly in README "Not established" and in
 the read-health.ts:204 comment that an hour whose cadence changes is scored
 at the LAST cadence of that hour and can over-expect. Add a test that drives
 60 polls at 60 s then a 15 s record inside the same hour.
