1. MY ROUND-5 DEFECT IS FIXED — re-measured the same way
================================================================
The fix is `src/listener/read-health.ts:213-217`:
    hour.cadenceMs = hour.cadenceMs === undefined
      ? cadenceMs
      : Math.max(hour.cadenceMs, cadenceMs);
Max keeps the SLOWEST cadence (largest ms), so expectedClaims can only fall,
and an hour can no longer be scored against a cadence faster than any it
actually ran at. Scoring itself is unchanged (read-health.ts:437-444).

The exact case I measured at b2b4e68 — 60 polls at 60 s, then one 15 s cadence
record at :59:30 INSIDE the same hour — re-run against this SHA's own built

             ratio 0.254}  -> hour PRESENT in throughputLapseHours   (FALSE LAPSE)
  446ebb4 : {hourStart 2026-09-01T10:00Z, claims 61, expectedClaims 60,
             ratio 1.017}  -> hour ABSENT from throughputLapseHours  (FIXED)

POSITIVE CONTROL (same 61 claims, the mid-hour 15 s record removed) at 446ebb4:
  {claims 61, expectedClaims 60, ratio 1.017}, throughputLapseHours [] —
  identical to the defect case, which is the point: the mid-hour record no
  longer changes the score.

3. THE RULE IS STATED, IN BOTH PLACES, AND MATCHES THE CODE
================================================================
README (docs/evidence/2026-09-06-idle-cost/README.md, last line of
"Not established"):
  "An hour whose cadence changes is scored at the slowest cadence recorded in
   it. That cannot false-lapse. It can miss a wedge only inside one hour that
   also had a slow interval."
Code comments, both updated away from the now-false "cadence in force":
  src/listener/read-health.ts:30  "Slowest cadence recorded in this hour;
    absent on files written before per-hour scoring."
  src/listener/read-health.ts:204 "An hour is scored at the slowest cadence
    recorded in it."
I checked the under-detection claim against the code rather than against the
sentence: test :435 IS that case made concrete — an hour that really ran 60
claims at 15 s but also saw a 60 s record scores 60/60 and does not lapse,
where a uniformly-15 s hour with the same 60 claims scores 60/240 and does
(my detection control above). So the documented miss is real, bounded to one
hour, and the direction of the error is the safe one: under-detect, never
false-alarm. The README states it as a limitation and not as a guarantee.
