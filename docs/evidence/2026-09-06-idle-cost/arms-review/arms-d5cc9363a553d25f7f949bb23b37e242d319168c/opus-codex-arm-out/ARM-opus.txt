DEFECT 2 — a varying idle interval is written into claimCadenceMs, which the
health math treats as one constant for every past hour
================================================================
src/listener/supervisor.ts:421-429 (new `idle_poll` branch)
src/listener/read-health.ts:403 (`const expectedClaims = HOUR_MS / health.claimCadenceMs;`)
src/listener/read-health.ts:202 (doc comment "the configured claim cadence")
src/cli.ts:4686 (the lapse WARNING built from it)

Before this lane, `claimCadenceMs` was set once, from the `ready` event's `cadenceMs`
(supervisor.ts:459-467), and the poll interval was the constant 2 s, so
`expectedClaims = 3_600_000 / cadence` was a sound per-hour expectation: a `delivery_claim`
event fires on EVERY claim POST, empty ones included (runtime.ts:1448, signalId null), so
claims/hour ≈ 3600 s / interval.

This lane makes the interval swing 15 s → 30 s → 60 s and writes the CURRENT value into the
same field on every poll. read-health.ts:403 then applies that one value to every hour in the
window. Worked example with this SHA's constants:
  - a listener idles a whole hour at the 60 s floor → ~60 claim POSTs in that hour;
  - a delivery lands just before the hour closes → runtime.ts:1481-1486 resets the streak and
    emits `idle_poll` with intervalMs = pollMs = 15 s;
  - the closed hour is now scored expected = 240, actual ≈ 60, ratio 0.25;
  - 0.25 < LISTENER_THROUGHPUT_LAPSE_RATIO (0.5, read-health.ts:12) → `listenerLapse` true and
    `cswarm listen status` prints "Claim throughput fell below 0.50 ..." for a healthy listener.
The inverse is worse: a listener that wedged during a busy hour but ends parked at 60 s is
scored expected = 60, so a real lapse is hidden.

Attempted refutation, all failed:
  - "the hours are recomputed per hour with the cadence of that hour": no. There is one scalar
    `health.claimCadenceMs`; `expectedClaims` is computed once outside the hour loop
    (read-health.ts:403) and assigned to every row.
  - "claims counts deliveries, so the ratio was already loose": no. `recordListenerClaim`
    (supervisor.ts:637) runs in the `delivery_claim` branch, which the runtime emits for every
    claim POST including empty ones. The metric really did mean POSTs per hour.
  - "back-off only reaches 60 s when nothing arrives, so the reset case is rare": the reset is
    exactly the interesting case — the hour in which work finally arrives is the hour most
    likely to be inspected, and it is the one this scores wrong.
No test in the diff pins hourly throughput across a cadence change; `grep -rn claimCadence
tests/` finds only three unrelated fixtures.
This also falsifies the doc comment at read-health.ts:202: the value is no longer "configured".
