## Round sixteen walk

The 684c6f2 merge asked `row.createdAt >= pageFloor` where `pageFloor` was a timestamp string. Gemini failed it: a stand-in that shares the 25th row’s timestamp with a smaller id sorts below that row under `created_at DESC, id DESC`, has rolled off, and was still kept, so the page held 26 rows. This SHA changes the same reset branch (`:4676–4694`):

```
pageFloor = page.hasMore ? page.rows.at(-1) ?? null : null
onThisPage = pageFloor === null ||
  row.createdAt > pageFloor.createdAt ||
  (row.createdAt === pageFloor.createdAt && row.id >= pageFloor.id)
keep if !fetched.has(id) && rowShowsOnScreen(row) && onThisPage(row)
signals = [...arrivedWhileFetching, ...page.rows].sort(createdAt DESC, id DESC)
```

`signalPage` (`:2090–2098`) is `.order("created_at", { ascending: false }).order("id", { ascending: false }).limit(SIGNAL_FETCH_SIZE)` with `SIGNAL_FETCH_SIZE = 26` and `rows = slice(0, 25)`. `hasMore` is `raw.length === 26`. Confirmed, not assumed. `swarm.signals.id` is `uuid` (`20260724000003_signals.sql:4`). The next-page cursor is `created_at.lt OR (created_at.eq AND id.lt)` (`:2086–2088`). `page.rows[0]` is newest; `page.rows.at(-1)` is the oldest of the displayed 25.

**Is that the query’s order exactly?** Yes. DESC on `(created_at, id)` means a row is on this page iff it is not older than the 25th. Older than the 25th is exactly the cursor predicate `created_at < floor OR (created_at = floor AND id < floor.id)`. Invert it: `createdAt > floor.createdAt OR (createdAt === floor.createdAt AND id >= floor.id)`. That is `onThisPage` when `pageFloor` is set.

**Is `>=` right at the tie?** Yes. The next page uses `id.lt`, so the floor row itself stays on this page. A stand-in with the same id is the floor row and is already in `fetched`. A stand-in with a larger id sorts above the floor and belongs. A stand-in with a smaller id sorts below the floor and is the 26th — the case Gemini named. I checked JS `>=` against `localeCompare` on canonical lowercase UUID strings, including `…000f` vs `…0010`; they agree, and hyphenated lowercase hex is the same order as UUID bytes, so it matches `id.lt` on the uuid column.

**`page.hasMore` as “the page is the whole history”?** Yes. `hasMore === false` means the replica returned fewer than 26 rows, so nothing has rolled off. `pageFloor` is then `null` and every pruned, on-screen, not-fetched stand-in is kept. That includes: an empty channel; a channel with 1–25 messages; and the lag case where the replica has 25 and is missing this browser’s post (25 ≠ 26). `hasMore === true` means a 26th row exists; it was fetched to know that and then sliced off `page.rows`, so `fetched` does not contain it. Without the id tie-break that discarded 26th would come back through the map. With it, `onThisPage` is false. Using `page.rows.length === 25` instead would still be wrong: a complete history of exactly 25 would look like a window.

**Can a stand-in be shown twice?** Reset replaces `signals` wholesale. `!fetched.has(row.id)` keeps the Map half off `page.rows`. Load older uses `known` from current `signals` and a cursor from `page.rows.at(-1)`, not from a stand-in. The poll concat is the routed `d9fa25b:4360` path.

**Ordered wrongly against a row with the same timestamp?** The merge comparator is the query’s own order, including `id DESC`. A same-timestamp stand-in with a larger id sits above the floor row; a smaller id is not merged. The 684c6f2 Gemini FAIL is closed.

Mutation table: the new pins discriminate. `pageFloor` mutated back to `page.rows[0]`, the id conjunct reduced to `row.createdAt === pageFloor.createdAt`, and `onThisPage` dropped from the filter, each against the observer that names that test.

## Findings considered and refuted

1. **`>=` (UTF-16) vs `localeCompare` (the merge sort) could disagree and still paint a 26th row.** File: `LiveDashboard.astro:4681–4694`. For mixed-script strings they can disagree. Signal ids are uuid text in canonical lowercase hyphenated form; I ran the pairs, including the nibble-carry case `…000f` / `…0010`. No disagreement. Postgres uuid order is the same byte order. Not a break.

2. **`postedSinceReset` is written only for `visible` / `visibleOnFailure`, so a send that finishes after a move to another named channel is not in the map when the reader comes back.** File: `LiveDashboard.astro:7148–7151` and `:7192–7193`. How you would see it: attach a file, send in `#ops`, click `#mobile` during the upload, click `#ops` again before the replica has the row. I almost failed the SHA on this. Refutation: the map’s job, as written, is a page requested before the post committed. Completing on the channel, then leaving, then coming back, still records the row (round 12). Completing on a screen that must not show the row correctly does not prepend it; the return visit starts a new fetch after the write. Replica lag on that later fetch is the 2s poll. Recording every posted id would be a strict improvement; it is not the 26th-row defect this SHA claims to close, and merge already filters with `rowShowsOnScreen`.

3. **`refreshLatestSignals` still concatenates `[...page.rows, ...signals.filter(not on page)]` and never asks `onThisPage`.** File: `:4743–4745`. A rolled-off stand-in that is already in `signals` can sit below the page until the next reset. Byte-identical on `origin/main` at `d9fa25b:4360`. Routed. Not this lane.
