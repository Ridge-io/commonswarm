**3. When the open’s channel read is dropped, `applyChannelFromUrl` still runs against whatever `channels` is, which may be `[]`.**  
`LiveDashboard.astro` 5211–5214, 5230, 5263–5273, 5677–5691, 5837–5868.

Generation is taken **before** the fetch. A newer `refreshChannels` no longer gets overwritten by a slow open. That part of the last FAIL is fixed. Two opens of the same workspace also do not deadlock: each bumps `requestVersion`, and the older open returns before it writes.

The URL step is **outside** that guard. Open starts by setting `channels = []`. If a create bumps `channelReadGeneration` and its refresh has not landed yet:

1. Open skips its successful snapshot (`channelGeneration !== channelReadGeneration`).
2. `applyChannelFromUrl` resolves `?c=` against `[]`, so a real id becomes `unknownChannelId`.
3. `syncChannelUrl` keeps that id in the bar.

A create that then `selectChannel`s heals this. A create whose `workspaceChannels` **fails** does not: `channelListFailed` becomes true, `channels` stays `[]`, the head says the list did not load (or the id is missing) for a channel the dropped snapshot had. `channelListFailed` follows the latest **applied** flag, not “do we have a good list”.

**How to see it:** already in a workspace with `?c=` set, re-open it (retry / current workspace in the menu), create a channel while it is pending, and fail the follow-up channel read (slow or killed network). Head: Channel not found, for a channel that exists.

**Refute:** I asked if this only flashes. On the success-create path, `selectChannel` overwrites it. The stuck case needs the refresh to fail. That is narrow, and it is exactly the question round 5 asked. It is not the load-bearing FAIL; finding 1 is.
