**What breaks**

Stay in the channel. Fail a send. Retry is showing. Rename the channel. Press Retry.

- Usual case: the old slug is gone. The edge returns 404 `unknownChannelMessage`. Retry stays on (`addressStillActive` is still true). The remaining hops never file. The box still names the new slug.
- Worse case: another member creates the freed slug. Retry files in **their** channel. The optimistic row still carries `placementChannelId` (the renamed channel). The server row does not. `showsOnScreen` drops it. The reader is still in `#ops` and sees no row.

The round-8/9 retirement was built to stop “replaying the old address from a box that says Message #ops”. Rename updates the box and leaves the frozen slug in place.

**How you see it**

1. Open a channel. Send a two-tag body (or any send that fails with hops unsent).
2. Retry is visible.
3. Rename the channel in Manage.
4. Press Retry. The refusal names the **old** slug, or the hop lands in a new channel that reused that name.

**Refute**

I asked whether typing remints. The `input` listener (`:6659–6662`) nulls the intent, and the next Enter uses `freshPlacement` from `activeChannel()`. Programmatic `input.value = rawBody` does not fire `input`, so Retry itself does not remint.
