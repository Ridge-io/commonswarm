### 2. A post from one channel is applied under another channel’s name

`loadSignals` and `refreshLatestSignals` capture `activeChannelId` and drop the page if it changed. `selectChannel` in live mode clears `signals` before the next fetch. That part holds.

The composer success path does not.

`LiveDashboard.astro` 7016–7026: after `postBrowserSignal` returns, the only guards are `requestVersion` and `activeWorkspaceId`. There is no `activeChannelId` check. Then:

```javascript
signals = [...posted, ...signals.filter(...)];
```

`selectChannel` (5672–5719) does **not** bump `requestVersion`. A channel click is not a workspace change.

How you see it:

1. Open `#mobile`. Send a message.
2. Before “Posting…” finishes, click another live channel (`#ops`).
3. `selectChannel` clears `signals` and starts `loadSignals` for `#ops`.
4. If that fetch lands first, `signals` is the `#ops` page. The composer then prepends the `#mobile` row.
5. `refreshLatestSignals` (4698–4706) keeps any local id that is not in the new page, so the stray row stays until you leave the channel.

I tried to refute this: maybe `loadSignals` always overwrites after. If the post returns first, you get a flash and then the `#ops` page wins. If `loadSignals` returns first, the stray row is durable. Sample mode is synchronous, so this race is live-mode only.

This is the same class of defect the query-capture was meant to close.

### 3. `renderChannel` puts `aria-current` back on `#all-signals` after the honest mark

`syncChannelCurrent` (5515–5522) is correct: an unresolved `?c=` marks nothing; a live channel marks only that channel.

The all-signals button has **both** `data-workspace-view="signals"` and `data-channel-place=""` (341–350). `renderChannel` (5074–5078) calls `renderChannelRail` / `renderChannelHead` (which call `syncChannelCurrent`), then marks every `[data-workspace-view="signals"]` current. That includes `#all-signals`.

`openWorkspace` (5245–5253) does `applyChannelFromUrl` then `renderChannel`. That is boot, menu switch, create, retry, and close-and-fall-through.

How you see it:

- Reload `/app?w=<id>&c=<valid-channel-id>`. Head and channel button say `#mobile`. `#all-signals` also has `aria-current="page"` (styled at 8677). Two current places.
- Reload with a `?c=` that is not in this workspace. Head says “Channel not found”. Doctrine at 5508–5513 says the rail marks nothing. `#all-signals` is marked current anyway, which says you are reading the whole feed.

`activateWorkspaceView("signals")` runs `syncChannelCurrent` **after** the workspace-view loop, so a later click repairs the mark. The open path never does. The new test only pins the Files/Brain clear, not this order.

I tried to refute this: maybe only the phone “Signals” tab is meant to stay current. That tab has `data-workspace-view` and no `data-channel-place`, so it should stay current. The all-signals **place** must not. The comment at 5605 already says `data-workspace-view` on a place button would mark the wrong thing. The static all-signals button still has both attributes.

Round 2 asked whether the mark comes back correctly and whether any view has nothing current. On Files/Brain, nothing channel-related is current (good). On an unresolved `?c=` after `renderChannel`, `#all-signals` is current (bad). The design note item 8 that says the rail and head can no longer disagree is false on the open path.
