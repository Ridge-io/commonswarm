## Findings

### 1. Workspace switch keeps the old `?c=` / `?w=` and can open as “Channel not found”

**File:** `site/src/components/app/LiveDashboard.astro`

- `syncChannelUrl` (5614–5627) is the only writer of `?w=` and `?c=`.
- The only caller is `selectChannel` (5671, 5693).
- `openWorkspace` reads the URL at 5243 (`applyChannelFromUrl`) and never writes it.
- The workspace menu calls `openWorkspace(workspace.id)` at 3160 with no URL update.

**What breaks:** The URL is not the address of what you are reading, except after a channel click.

How you see it:

1. Open workspace A, click a channel. URL becomes `?w=<A>&c=<C>`.
2. Switch to workspace B from the menu.
3. `applyChannelFromUrl` still reads `c=<C>`. C is not in B, so `unknownChannelId` is set (5634–5644).
4. Head says “Channel not found”. Composer is hidden. B’s feed is not shown.
5. Reload still has `?w=<A>&c=<C>`, so you land back in A.

Same class of bug without a channel: first load of `/app` never writes `?w=`. Switch to B, reload, default workspace opens again.

I tried to refute this: maybe some other `replaceState` writes `w=`. Grep finds only `syncChannelUrl`. Maybe UI switch is supposed to honour a leftover `?c=` as a permalink. That cannot be right: the user picked B, not a link. Design §8.1 says every filter state round-trips. The observer test at `chat-channels.observer.test.ts:230` only checks that `syncChannelUrl` contains `set("w"` and that boot reads `?w=`. It does not require `openWorkspace` to call the writer, so this stayed green.

This is the same family as the round-one unknown-channel hole: the honest empty state fires, but for the wrong reason.
