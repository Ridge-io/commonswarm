## Round fourteen walk

`loadSignals` reset (`:4664–4681`) now asks a third question of a stand-in, after prune and `rowShowsOnScreen`:

```
newestFetched = page.rows[0]?.createdAt ?? ""
keep if !fetched.has(id) && rowShowsOnScreen(row) &&
        (newestFetched === "" || row.createdAt >= newestFetched)
```

`signalPage` (`:2090–2092`) is `.order("created_at", { ascending: false }).order("id", { ascending: false })`, then `slice(0, SIGNAL_PAGE_SIZE)` with `SIGNAL_PAGE_SIZE = 25` (`:1510`). `page.rows[0]` is the newest row the replica returned. Confirmed, not assumed.

**Is `createdAt >= newestFetched` the right boundary?** Replica lag is a write this browser just made that the page does not have yet. Sequential apply means that write is newer than everything the replica did return, or the page is empty. Page roll is a row the replica does have, off the first 25: older than `page.rows[0]`. Those two share `!fetched.has` and `rowShowsOnScreen`; they differ only in that timestamp. Both values are the server’s: the Map stores `postBrowserSignal`’s row (`command/index.ts:6993` `created_at: signal.created_at.toISOString()`), and `newestFetched` is the read view. `>=` (not `>`) is the equal-timestamp lag case the previous Grok arm named: a concurrent post missing from the replica still stands in. A rolled-off row with `createdAt === newestFetched` would need 25 other rows with the same timestamp; `MENTION_MAX` is 8 and the first page is 25. Not the 0.83 msg/s fill both arms used.

**Empty page.** `page.rows[0]` is `undefined` → `newestFetched === ""` → every pruned, on-screen, not-fetched row stands in. A new channel, or a replica that has not caught the first post, is empty. There is no page-roll on an empty page. `row.createdAt >= ""` would also be true for any ISO string; the `=== ""` arm is the documented empty case, not a second rule.

**Can a row that should stand in be dropped?** Stay in the channel: the composer already prepended it; the Map is for the next reset. Switch to all-signals: `rowShowsOnScreen` is true; if the replica missed it, it is newer than `page.rows[0]` (or the page is empty) and comes back. Switch to another named channel: `rowShowsOnScreen` is false; the row stays in the Map; coming back hits the same comparison. A hole — later writes replicated, this write did not — would look like page-roll and be dropped. Physical WAL does not apply that way; that is not the lag this record exists for. Command serializes `toISOString()` (`…sssZ`); PostgREST typically serializes `+00:00` with optional microseconds. Those strings only invert inside the same millisecond (`Z` > a fourth fractional digit). Page-roll over 25 rows is not inside one millisecond. I am not failing the SHA on that.

**Does anything else depend on it silently?** Composer landing (`showsOnScreen`) does not read `newestFetched`. The poll does not either — that concat is the routed `d9fa25b:4360` path. `forgetFetchedPostedIds` still drops an id as soon as any landed page carries it, including Load older, so a rolled-off row that later appears on page 2 is forgotten and will not stand in on the next reset. Observer pins the comparison (`chat-channels.observer.test.ts:464–471`). Mutation table: 51 PASS, 0 not discriminating, including `newestFetched = ""` and the filter reduced to `!fetched.has`.
