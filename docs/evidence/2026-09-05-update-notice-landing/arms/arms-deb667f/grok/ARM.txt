## 4. State and dismissal

Checked `runningBuild`, `baselineMarkup`, `dismissedBuild`, `servedBuild` at `LiveDashboard.astro:6531-6608`.

`runningBuild` is captured once. `baselineMarkup` is set once from the first body with hashes. `dismissedBuild` starts as `null`. A probe that learned nothing returns before assignment (`:6572`, `:6575`, `:6585`).

Identity is always `${served}\n${markup}` (`:6591`). Dismiss stores that (`:6607`). `dismiss-then-markup` is the control for the old “store one half” bug. That bug is gone.

`served` is URL lines; `markup` starts with `<live-dashboard`. A join-on-newline collision is not realistic.

**Dismissal is sticky across a rollback.** `if (!isNewBuild)` only hides (`:6593-6595`). It does not clear `dismissedBuild`. Sequence:

1. Tab runs A. Server deploys B. User clicks Not now. `dismissedBuild = B`.
2. Server rolls back to A. `isNewBuild` is false. Bar hides. `dismissedBuild` is still B.
3. Server deploys B again. `servedBuild === dismissedBuild`. `showUpdateNotice(false)` (`:6600`). The tab is out of date and stays quiet for the rest of its life.

The note at `:130-134` and the comment at `:6597-6599` only promise that a *third* (different) identity asks again. They do not say a later ship of the same bytes after the tab was back in step asks again. The `dismiss-then-markup` case never rolls back, so it cannot go red on this.
