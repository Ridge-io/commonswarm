Sequences I tried to construct:

**Rollback missed for ever.** Dismiss B. An in-flight poll that saw rollback to A is dropped. Next poll: if the server is still A, 6617–6625 clears the dismissal. **Dismissal never cleared.** Cleared only by a non-stale `!isNewBuild` poll, or by reload (memory dies). A later in-step poll still clears it.

## 4. Is the case flaky?

Polls this sequence issues, if each cycle starts with `pollInFlight === false`:

1. Boot `startUpdatePoll` — stage 0, running build
2. First visibility cycle — stage 0
3. Cycle after stage 2 — assets, bar up
4. Cycle after `/__hold` — **held**, stage 3, running build
5. Cycle after stage 4 — assets again

`pollRequested` is used only when a cycle hits an in-flight poll (6565–6567). After `until(shownNow)` for build two, poll 3 has already applied (`finally` runs before the show). Hold is armed after that, so poll 4 is the held one.

Wrong-interleaving I checked:

- Extra poll at stage 3 **before** the click would apply “back in step”, set `servedBuild` to the running build, and the click would remember the wrong build. Stage 4 would then raise the bar (false red). That needs a poll between `shownNow` and hold. That gap is two parent fetches (`/__stage?to=3`, `/__hold`) and is not a timer.
- Extra poll **after** stage 4 makes `servedStages` end in `4,4` or `3,4,4`, and `endsWith("3,4")` fails (false red). After polls go up they only `spin(60)` parent `/__polls` fetches, which do not increment `polls`.
- `shown === false` can pass if the stage-4 **apply** has not run yet, because the click already hid the bar. `servedStages` / `polls` only prove the request was received. `spin(60)` after the count bump is the apply wait. Same shape as `wait(120)` in the other dismiss cases, with fetches instead of `setTimeout`.

Virtual time: Chromium `--virtual-time-budget` pauses virtual time while a load is pending. A held `fetch` parked on `response.text()` is such a load. `setTimeout` in `wait` / `until` would not fire until release. That reading is right.

Applied where it is needed: after `/__hold`, the branch uses only `fetch` loops (`spin`, `untilFetched`, the polls-count loop at 255–257). No `setTimeout` until report. Before the hold, `until(shownNow)` still uses `wait(25)`; the held fetch has not started. After release, `setTimeout` would work again; they keep using `spin`, which is stricter, not a gap.

Residual flake: `endsWith("3,4")` is brittle to a trailing extra poll; a stage-4 apply that is slower than `spin(60)` could hide a broken version check (false green). I did not measure either on this machine.
