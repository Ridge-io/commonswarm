**1. Does the version check actually cover the destructive path?**
Yes. I read `site/src/components/app/LiveDashboard.astro` around `checkForNewBuild`. The writes to state that outlive the function are:
- `pollInFlight` and `pollRequested`: Reset in a `finally` block before the version check.
- `baselineMarkup`: Set via `if (!baselineMarkup) baselineMarkup = markup;` after the check.
- `servedBuild`: Set via `servedBuild = ...` after the check.
- `dismissedBuild`: Set to `null` on the `!isNewBuild` branch after the check.
- DOM through `showUpdateNotice`: Called after the check.

A stale poll returns at `if (version !== noticeActionVersion) return;` and therefore drops its payload, unable to reach `baselineMarkup`, `servedBuild`, `dismissedBuild`, or the DOM.
Skipping these writes does not wedge the feature. A stale poll is discarded because its information is outdated relative to the user's action; the next scheduled or queued poll will measure the server post-click and update `baselineMarkup` or `dismissedBuild` accurately.
Resetting `pollInFlight` and `pollRequested` in `finally` BEFORE the version check is exactly right, not a hole. If they were reset after, a dropped poll would leave `pollInFlight = true` forever, permanently wedging all future polls. Releasing the lock ensures the feature continues to poll.

**2. Can the fix strand a dismissal or wedge the bar?**
No. If a stale poll is dropped, the polling mechanism itself restores the behavior. 
If a genuine rollback occurs, but the poll measuring it was in flight before the user clicked "Not now", that poll is correctly dropped because its answer predates the dismissal. The dismissal isn't cleared yet. However, this does not strand the dismissal permanently. The next timer tick (5 minutes via `updatePollTimer`), a tab visibility change (`visibilitychange`), or an immediate queued poll (if `pollRequested` was true) will fire a new poll. This new poll, having a captured version equal to `noticeActionVersion`, will see the rollback (`!isNewBuild`) and correctly clear `dismissedBuild = null`. No event is missed permanently, only delayed to the next valid measurement.

No, the interleaving is deterministic.

This is guaranteed because `until(shownNow)` waits for the bar to show for build 2, which only happens once the prior poll completes its `finally` block and updates the DOM. The `cycle()` command immediately following `/__hold` triggers exactly one poll (since `pollInFlight` was false), which is reliably intercepted by the server. 
The reasoning about Chrome's `--virtual-time-budget` is correct: virtual time pauses while a network fetch is pending. The test deliberately avoids `wait(...)` and correctly spins microtasks using `untilFetched` and `spin` (which execute immediate `fetch` requests) everywhere within the held-poll sequence to allow execution to proceed.
