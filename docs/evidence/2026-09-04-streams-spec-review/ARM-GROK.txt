## Findings

**Phase 1 as written breaks posting.** Not the parser. The insert.

`postSignal` writes a fixed column list and does not name `channel_id`:

```5966:5969:supabase/functions/command/index.ts
    INSERT INTO swarm.signals (
      id, workspace_id, from_principal, from_kind,
      to_user_id, to_agent_principal_id, in_reply_to,
      about, kind, body, until, created_at
```

§4.3 then does `ALTER TABLE swarm.signals ALTER COLUMN channel_id SET NOT NULL` with no `DEFAULT` and no `BEFORE INSERT` trigger. Postgres will reject every omit of that column.

Apply order is the spec’s own rule (`20260902000001_broadcast_recipient_roster.sql:58-64`): migration commits, then the edge deploys. After the migration commit, the live edge is still this INSERT. Every `post_signal` fails until a new edge ships. Edge-first is also unsafe: a new INSERT that names `channel_id` dies if the column does not exist yet. There is no safe apply order for “NOT NULL, no default, no trigger.”

§9’s “yes, old clients work” never looks at this INSERT. It only looks at the read parser.

**Reads would survive.** That part of §9 is true.

- CLI: `src/cloud/signals.ts:891-894` names columns. A new view column is not returned. `parseSignalRecord` (`:317-325`, implemented `:361-383`) ignores unknown keys. `until` is required (`checkedTimestamp` at `:250-254` and `:380`).
- Browser: `LiveDashboard.astro:1746-1750` uses `schema("swarm_read")`, table `signals`, an explicit select with no `in_reply_to`, and `.or(\`until.is.null,until.gt.${cutoff}\`)`. Extra view columns are not requested.
- Agent `read` `exactKeys` (`read/index.ts:222-234`) rejects unknown *request* keys. An old body without `channel_id` still matches.

So: old **reads** keep working. Old **writes** die in the migration→edge window. After a new edge that fills `channel_id`, writes work again. Phase 1 as written still ships a committed shape the live edge cannot write.

**§4.2 `until` CHECK does not do what it says.** After §4.3 every row has `channel_id`. Then

```
until <= created_at + 30 days
OR (channel_id IS NOT NULL AND until <= created_at + 100 years)
```

is `until <= created_at + 100 years` for every row. The 30-day rule is dead at the table. `SIGNAL_MAX_UNTIL_MS` at `command/index.ts:512` is the only remaining ceiling, and it is not a constraint. “Keeps 30 days for everything that has it today” is false once backfill runs.

**§5 clause (d) leaks directed mail.** (d) is “I am in the channel → I see every signal in it,” with no undirected test. Phase 3 adds (d). Old clients never send `channel_id`. `resolveSignalChannel` defaults them onto the workspace default channel. `cswarm ask --to alice` therefore keeps landing in public `#all-signals` as a directed row.

If anyone is a live `channel_members` row on that channel, (d) shows them Alice’s private ask. The spec’s Phase 3 claim that visibility “is already decided by clauses (b) and (c), which do not change” (`§9`) is false the moment (d) exists. Auto-join to the default channel makes it workspace-wide.

The predicate that does not leak: membership only widens **undirected** rows.

```
undirected AND (visibility = 'workspace' OR I am a member)
OR to_user_id = me
OR to an agent I own
```

Do not add “member sees every row in the channel.”

**New tables have no RLS, REVOKE, or GRANT.** §4.1 is `CREATE TABLE` plus indexes. House style is owner + `ENABLE ROW LEVEL SECURITY` + `REVOKE ALL` + grant `swarm_command` only (`20260724000003_signals.sql:29-41`). An implementer who types the sketch can leave `swarm.channels` and `swarm.channel_members` selectable. `dm_key` is the participant set. §8 rule 2 refuses to put that set in a URL, then stores it on a table with no policy.

**`in_reply_to` is not a thread. §7 is right.** Validation (`command/index.ts:1588-1595`) allows `in_reply_to` only on an undirected `note`. `resolveSignalWriteTarget` loads the parent (`:5768-5787`), requires the caller was addressed (`:5789-5802`), and re-addresses to the original author (`:5804-5827`). `cswarm reply` is a private answer. Reusing the column for a channel-visible thread is a privacy change, not a rename.

**§1.7 protocol grep is right.** `grep -rni signal src/protocol/` is 0 hits across 10 files. Positive control: `post_signal` at `src/cli.ts:2896`, `:3114`, `src/listener/runtime.ts:773`, `src/cloud/command-client.ts:136`, `src/cloud/seed.ts:15`.

**§1.4 broadcast fan-out is right.** Trigger body `20260731000001_signal_deliveries.sql:126-137` inserts only when `to_agent_principal_id IS NOT NULL AND kind IN ('ask','note')`. No later migration replaces it.

**§1.6 live view is right.** Three `CREATE VIEW swarm_read.signals`. Newest is `20260901000010_signal_attachments.sql:81-133`. WHERE is `:122-133`. Owner is `:135`. `security_barrier` is `:82`, not `:135`.

**privacy.astro:121 is not “right.”** Spec §11.1 says the RLS settles it and `:121` is correct. `:121` says a directed signal is visible to the addressee **and its sender**. The view (`20260901000010:122-133`) has no `from_principal = auth.uid()` branch. Sender re-read is refused. `P3-1-SIGNALS-BRIEF.md:323-324` says that refusal is intended. The spec picked the wrong sentence as the true one.

**§12.2 is establishable, and it is false.** You do not need production data. Default-channel writes + clause (d) is enough. See above.

**§12.1 and §12.6 stay unestablished.** Row count and live `ukezjcnxjvkpkeezxaew` schema are not in this repo.

**Phase order is fine.** Channels first, threads second, DMs as the first RLS change, private channels last. Do not start with DMs: they need `channel_id`. Do not start with private channels. The thing to change in Phase 1 is the `NOT NULL` and the missing fill trigger, not the order.

## Would Phase 1 as written leave old clients working?

**NO.**

Walk of apply order (`20260902000001:58-64`):

1. **Migration commits** (`§4.1` + `§4.2` + `§4.3` in one file, one transaction). `channel_id` is `NOT NULL`, no default. Trigger is back on. This is the shape clients see.
2. **Live command edge still runs `command/index.ts:5966-5969`.** It does not write `channel_id`. Every post from the installed CLI, the browser, and agent listeners fails with a not-null error. No client change can save it. The failure is the server INSERT.
3. **`read` / `command` edge deploy.** If the new edge fills `channel_id`, posts work again. Old CLI bodies omit the field; `exactKeys` can stay compatible if `channel_id` is optional like `until_ms` (`:1535-1540`).
4. **Publish client / site.** Read path was already compatible: CLI select `signals.ts:891-894` + ignore-unknown `:317-325`; browser select `LiveDashboard.astro:1748`.

§9’s “row set is byte-identical” is also false as soon as a second public channel has posts. Old clients have no channel filter (`signals.ts:890-898`, `LiveDashboard.astro:1746-1750`). They will mix `#eng` into the one feed. That does not crash the parser. It is not byte-identical.

`until=gt.now` at `signals.ts:898` is real. A NULL `until` would vanish from the CLI with no error. Phase 1 does not make `until` nullable. That trap is not the Phase 1 break. The `NOT NULL` column with no default is.

**Five-phase order.**

Channels first as **identity** is right. Channels first as **this SQL** is not.

A first phase that actually leaves old clients working:
