### BREAKING CASE
**Phase 1 Migration breaks all signal posting.**
The apply order is: migration → deploy read/command edge → publish client. In the Phase 1 migration sketch (§4.3), step 3 executes `ALTER TABLE swarm.signals ALTER COLUMN channel_id SET NOT NULL`. Because `channel_id` is made strictly required with no `DEFAULT` value at the database level, and the new command edge is not deployed yet, the OLD command edge (`supabase/functions/command/index.ts:5941`) continues running. The old `postSignal` function attempts to `INSERT INTO swarm.signals` without supplying a `channel_id`. This immediately throws a Postgres `not-null constraint` violation, causing an outage for all signal posting until the edge is deployed.

*(Secondary RLS Data Leak)*: The Phase 3 RLS predicate (clause d) creates a severe privacy leak. It grants read access for a signal to any user who is explicitly in `channel_members` for that signal's `channel_id`. Because Phase 1 defaults all old client posts (including directed DMs) into the public `#all-signals` channel, any user who explicitly joins `#all-signals` will evaluate to `TRUE` for clause (d), gaining full visibility into ALL private directed signals posted by old clients to `#all-signals`.

**Would Phase 1 as written leave old clients working?**
NO. Old clients will break at the first step (the migration) when trying to post.
While old client **reading** works perfectly because both `src/cloud/signals.ts:891-894` and `site/src/components/app/LiveDashboard.astro:1748` use explicit `select` lists that safely ignore the new columns, **posting** breaks completely. The migration sets `channel_id` to `NOT NULL`, but during the deploy window, the old `command` edge is still handling requests. When an old client submits a post, it hits the old edge, which omits `channel_id` in its `INSERT`, crashing with a Postgres constraint violation.
