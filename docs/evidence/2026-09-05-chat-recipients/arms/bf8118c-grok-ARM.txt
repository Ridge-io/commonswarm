## Round 2 — `signalNamesRecipient`

This arm does not grant more than the read path.

- The view admits a member who is named as a user, or who owns a named agent. `signalNamesRecipient` uses the same two tests, on `swarm.signal_recipients`, pinned to `route.workspaceId`.
- An agent call sets `userId` to null. The agent cannot use its owner's user row, and cannot use a sibling agent. It matches only its own principal. That is the same cut the read edge makes with `addressedToThisAgent`.
- A member who only owns some other agent does not match.
- A cross-workspace id fails earlier: the parent load is `workspace_id = route.workspaceId` and `kind IN ('ask','note')` and live `until`. No row, 403.
- Control in the served test: a member who is not in the set still gets 403 on `in_reply_to`.

This is the reply twin of the read path. It is not the delivery twin. That is the fail below.

## 1. Old clients

`to` does not sit in `modernKeys`. `modernKeys` is still `to_agent_principal_id` + `in_reply_to`. `to` is in `CHAT_SIGNAL_OPTIONAL_KEYS` and enters `exactKeys` only through `chatSignalKeys` / `Object.hasOwn`. A 0.1.54 post with no `to` has an empty chat group.

The read edge still takes `in_reply_to` as its modern group. `chatReadKeys` only adds `channel`. A post-only `to` does not open a read group.

The browser post still sends the scalar pair and `in_reply_to: null`. It does not send `to`.

Installed parsers ignore extra response keys (`recipients`, `oldest_pending_at`, a fourth capability marker). `checkedClaimCapabilities` requires the three old markers to be `1` and ignores the rest. That half is safe.

## 2. View recreation

The splice is two-step: tag the top-level `FROM swarm.signals ` first, then the first `WHERE` in the tail. The attachments `WHERE` stays in the head. Inner `WHERE` in the old predicate stays inside the wrapped predicate. Fail-closed if the `FROM` is missing, not unique, or `signal_recipients` is already in the live body.

The new disjunct has its own `is_member` gate. An OR at the top cannot admit a non-member. It admits the people the sender named, in person or through an agent they own. That is the same rule as the old scalar agent arm (also no `revoked_at` filter). A bystander is not admitted. The author is not admitted unless they are in the set. The postgres suite measures that.

`assert_view_clauses_preserved` is vacuous for the new marker on this run (`p_before` does not contain it). The DO block after the recreation is the positive control: it requires `AS recipients`, `recipient_user_id = auth.uid()`, and exactly one `FROM swarm.signals` boundary.

## 3. First-recipient guarantee

The deferred trigger checks contiguous `0..n-1` and that position 0 equals the scalar columns. Signals and recipient rows are append-only, so a later scalar edit is not a path. No `to` means no recipient rows; scalars stand alone. That is the old path.

`in_reply_to` and thread replies and `working-on` cannot carry `to`. A private reply writes no recipient rows and re-addresses the author on the scalar columns.

`resolveSignalWriteTarget` copies entry 0 onto the scalar columns. `postSignal` writes the list in order. I found no edge path that stores recipient rows with a null or disagreeing scalar. Direct SQL that disagrees fails at commit.

## 4. Two enforcement points

The view admits the owner of any named agent. The read edge then requires `to_agent = this principal` or `recipients @> [{kind:'agent', id: this principal}]`. A second agent can read. An agent that is not in the set cannot. `inbox: true` uses the same fragment.

`@>` is object-containment on array elements, so extra `position` on the view object does not block a match. Kind is in the object, so a user id that equals an agent principal id does not match. Ids come from uuid values; Postgres emits lowercase.

## 5. Delivery fan-out — this is the fail

`ON CONFLICT DO NOTHING` hits `PRIMARY KEY (signal_id, recipient_agent_principal_id)`. Kind gate is `ask`/`note`, same as `enqueue_signal_delivery()`. `working-on` does not enqueue. Neither trigger checks `until`; that is not new.

The postgres suite proves one ledger row per agent, and no duplicate for position 0. That is only the INSERT.

`claimAgentInbox` will lease a row for a second agent (the select is on `signal_deliveries`, not on the scalar). Then `hydrateDeliveryRefs` does:

```
AND s.to_agent_principal_id = ${args.recipientPrincipalId}::uuid
```

Position 0 is the scalar. For agent 2 this returns no row, so hydrate returns null. The handler writes `delivery_hydration_integrity`, returns 403 `delivery_unavailable`, and **commits** (`db.begin` commits a normal return). The lease and `attempt_count` stick. Ten failed claims terminalize the row as `delivery_attempts_exhausted`.

Ack `expired` uses the same scalar filter at `durable-delivery.ts:619`.

`src/` did not change. The installed (and this SHA's) client still does `signal.to_agent !== expected.principalId` → protocol error. Even a hydrate fix that returns the real row would break 0.1.54 unless the wire forges `to_agent` (that would make an old reader wrong) or the client changes (that is a flag day).

So a second agent can **read** the signal and cannot **claim** it. Fan-out is not “incomplete.” It inserts rows the claim path cannot hydrate.

This is the same class as the round-1 `in_reply_to` bug. That one was fixed. This twin was not. No test claims as a second agent.
