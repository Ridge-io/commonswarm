Claim 3 — Unified normalization + `{` guard + marker formatting
================================================================================
Tried to refute: detect vs decode disagree; `{` JSON classified as a token; `CSWA**RMA.` / `CSWA\nRMA.` fail parseAgentConnection.

`isAgentConnectionToken` (codec 63–68): trim, if startsWith `{` return false, else normalizeTokenCandidate (drop `[^A-Z2-7.]`) and includes(`CSWARMA.`).

`decodeAgentConnectionToken` does **not** call normalizeTokenCandidate. Marker is a different regex (116–118) allowing only `[\s*_\\`]` between C-S-W-A-R-M-A and `.`. Body/crc then keep alphabet chars only.

Claimed examples work: `CSWA**RMA.` and `CSWA\nRMA.` → detect true, decode and parseAgentConnection succeed (test 662–681; probe confirmed).

Leading-`{` guard: JSON.stringify(envelope) → isAgentConnectionToken false; parseAgentConnection takes JSON.parse (agent-profile.ts 78–81). Same for url `https://cswarma.example.com` (test 582–597). Guard is on detect/parse, not on decode-direct, which is the right split.

Residual (not a silent-accept defect): `CSW-ARMA.` + rest → detect true (hyphen stripped) but decode/parse throw token_marker_missing because `-` is not in the marker regex. Fail-closed. Markdown cases in the tests do not insert `-` inside the marker.

Could not refute the behavioral claim. The implementations are not one shared function; they agree on the listed markdown cases and fail closed when they disagree.
