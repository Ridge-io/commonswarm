## 4. The debounces

Cancel sites the patch added: `persistComposerDraft` and `clearComposerDraft` call `cancelComposerDraftTimer` (`DIFF.patch` 851–860); `closeMentionPicker` calls `cancelMentionPickerRender` (`DIFF.patch` 1027–1028). The comment at `DIFF.patch` 829–832 names those two paths and not `resetComposer`.

**The missing cancel is `resetComposer` (`DIFF.patch` 1054).** It calls `closeMentionPicker()` (mention timer dies) and never `cancelComposerDraftTimer()`. It also never writes the current body before it clears the textarea.

`persistComposerDraft` reads `input.value` at fire time, keyed by `composerDraftKey()` (`activeWorkspaceId` now). Callers of `resetComposer`: session teardown (id already `""`, so a late persist is a no-op) and `openWorkspace` when the workspace changes.

Sequence if a draft timer is still pending:

1. Timer armed on workspace A.
2. `resetComposer()` clears the textarea; timer still live.
3. `activeWorkspaceId` becomes B.
4. Timer fires: empty body, key B → `localStorage.removeItem(B)` if restore has not run; or it writes B’s restored text if restore already ran. A’s unflushed text is gone.

A pointer click on the workspace menu blurs the textarea first, and blur flushes (`DIFF.patch` 1117–1122), so the common tap path is saved. Enter-to-send also does not need this: send clears the field, then `clearComposerDraft()` on success. The hole is `resetComposer` itself, including any `openWorkspace` that does not come from a blur.

`scheduleMentionPicker` closes at once when there is no `@word` (`DIFF.patch` 1041–1046). Arrow keys still call `renderMentionPicker` directly. Enter within 150ms of the last key can submit while the picker is still closed; that race is larger than before, when the picker opened on the same keystroke.

Blur / `pagehide` / `visibilitychange` → hidden all call `flushComposerDraft` → `persistComposerDraft`, which cancels the timer and writes the live value. They do not write a stale closed-over body. They can write empty if they run after send has already cleared the field and before `clearComposerDraft`; success still clears.

## 5. The viewport sync

`syncDashboardViewport` (`DIFF.patch` 1001–1008): `scrollTo(0, 0)` only when `window.scrollX/Y` are not already 0, then return if `visualViewport` is missing, else write `--dashboard-viewport-height` and `scrollComposerCaretIntoView()`. Coalesced with `requestAnimationFrame` and no timer floor (`DIFF.patch` 1014–1017).

Loop: `scrollTo` is skipped at (0, 0), so a `scroll` event cannot keep scheduling work through that write. Not a loop.

Pinch-zoom: `visualViewport` `scroll` is how a zoomed visual viewport moves. `window.scrollTo(0, 0)` resets the layout viewport, not `visualViewport.offsetTop/Left`. If iOS also shifts `window.scroll` during a pinch, that pan is undone. Not established on a phone.

Stale height: a hidden tab may delay rAF; browsers usually run the queued frame on return. Unlike autogrow, there is no 32ms floor. A dropped rAF would leave `viewportSyncFrame` non-zero and every later `requestDashboardViewportSync` would return early. Not shown to happen.

No `visualViewport`: the custom property is left unset and `100dvh` applies, as the comment says (`DIFF.patch` 990–994). That is a first-paint / old-engine fallback, not a wrong `innerHeight` write during the keyboard.

## 6. The caret block

`composerCaretKnown` (`DIFF.patch` 932–937, 975–977) does stop the `{0,0}` restore on first focus. The 500ms pointer window (`DIFF.patch` 1124–1128) is only armed from `pointerdown` on the textarea (`DIFF.patch` 1107–1109). A tap in the field keeps the tap caret. A tap that focuses the field later than 500ms would restore over the tap; not shown.

**The flag is never cleared.** `resetComposer` (`DIFF.patch` 1054) does not touch it. `restoreComposerDraft` is unchanged. Send leaves it true and clamps to 0 on an empty field (harmless).

Workspace switch on a width above 52rem:

1. Blur on A stores A’s caret and sets `composerCaretKnown = true` (`DIFF.patch` 1118–1121).
2. `resetComposer` clears the textarea; the flag stays true.
3. `restoreComposerDraft` puts B’s body in the field.
4. `focusComposerOnEntry` skips only `max-width: 52rem`, then `focus({ preventScroll: true })` with no pointer.
5. `restoreComposerCaret` writes `min(A’s index, B’s length)` into B’s draft.

That is the same class of bug `f357cb3` fixed, on a different path. On a phone the auto-focus does not run; a tap skips restore. Tabbing into the composer after a switch still hits it.

`scrollComposerCaretIntoView` (`DIFF.patch` 951–972): end-of-text uses `scrollHeight` (the operator case). Mid-text counts hard `\n` only; the comment admits soft wraps can land a line off. Visible if the caret is in a long wrapped paragraph at max textarea height.

## 7. The new clearance rule and its harness

HTML order is toolbar, then `.dashboard__feed-more`, then `ol.dashboard__feed`. Adjacent siblings, no wrapper. Show/hide is `more.hidden = !signalHasMore` (the `hidden` attribute). `:not([hidden])` is the right test; a bare sibling combinator would also match the default-hidden node and zero padding when the button is off.

No CSS `display: none` on `.dashboard__feed-more` except the UA `[hidden]` rule. The 36rem block does not override the sibling rule; 320px is inside `max-width: 52rem`. The rule reaches both.

Harness (`DIFF.patch` 2091–2132): `more=1` sets `hidden = false`. Positive control: `feedMore !== null && height > 0`. The off variant must be `null`. Padding must be `"0px"` with the button and not `"0px"` without it. Gap `< 20`. If the knob did nothing, the first assert fails (the node starts `hidden` in markup). If the CSS rule is missing, padding stays `40px` and the gap assert fails. A 19px leftover gap would still pass; the padding assert is the tight control. The new case is only measured at 390×844, not at 320 or 36rem height.
