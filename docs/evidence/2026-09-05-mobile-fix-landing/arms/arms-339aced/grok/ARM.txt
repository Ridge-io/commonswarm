The transcript box (`.dashboard__channel-body`) therefore starts at the app bar’s bottom edge. That part of the operator rule holds.

The 2.5rem trio agrees with itself:

- toolbar `min-block-size: 2.5rem`
- `margin-block-end: -2.5rem`
- `.dashboard__feed { padding-block-start: 2.5rem }` (`DIFF.patch:1266-1304`)

`min-block-size` is a floor, not a cap. A wrapped row or a larger font can make the toolbar taller than 2.5rem. The negative margin and the list padding stay 2.5rem, so extra height stays in flow. ## 3. `contain: layout` on `.dashboard__message`

Added at `DIFF.patch:1080-1089`. Layout containment makes each row a containing block for absolute/fixed descendants and a stacking context. I looked for descendants that need to escape the row.

- Entity panel is a sibling of the channel (`data-entity-panel`), not a child of a message. `entityControl` opens that panel. Paint clipping would not have hit it either; the comment is wrong about that, but the panel is safe.
- Mention chips are `position: relative`.
- Brain-link is `display: inline` in the body. Focus ring is `box-shadow`. Layout containment does not clip overflow.
- Message toggle is in-flow.

Floating head is `position: absolute; z-index: 4` on `.dashboard__channel`, a sibling of `.dashboard__channel-body`. Contained rows cannot paint above it. The sticky filter row keeps `z-index: 2` (pre-existing). New stacking contexts on rows sit at auto. The band should still paint above messages. I did not see a popover inside a row that this would trap.

## 4. The debounces

Callers of `persistComposerDraft`: the 300ms timer, `flushComposerDraft` (pagehide / hidden / blur), attachment add/remove, `selectMention`, failed-send restore. Each of those either is the write or goes through `persistComposerDraft`, which cancels the timer (`DIFF.patch:768-769`).

Callers of `clearComposerDraft`: send success and the “all tags posted, render threw” path. Both cancel (`DIFF.patch:759-760`).

Callers of `closeMentionPicker`: `scheduleMentionPicker` when there is no `@word`, `resetComposer`, send start, arrow/escape paths. `closeMentionPicker` cancels the mention timer (`DIFF.patch:935-936`).

**The missing cancel is `resetComposer` (`DIFF.patch:962`).** It clears the textarea and attachments and closes the picker. It does not call `cancelComposerDraftTimer`. Comment at `DIFF.patch:739-742` names only `persistComposerDraft` and `closeMentionPicker`.

Counterexample: type (timer armed) → `openWorkspace` for another id with the textarea still focused (no blur flush) → `resetComposer` clears the box → `activeWorkspaceId` becomes B → timer fires `persistComposerDraft` against B’s key with an empty box → `removeItem(B)`. If that lands before `restoreComposerDraft`, B’s saved draft is gone. A click on the workspace menu usually blurs first and flushes, so the common pointer path is safe. The cancel is still missing on the function that invalidates the composer.

Send start (`input.value = ""`) also does not cancel. Focus is kept, so blur does not flush. The timer then persists empty, which deletes the draft; success later calls `clearComposerDraft`. That is not “put the sent text back”. The comment’s feared send bug does not happen, because the box is cleared before the timer runs. The stale-write risk is the workspace switch above, not send.

Blur / pagehide / `visibilitychange` flushes call `persistComposerDraft` on the current box. After an optimistic send the box is empty, so a hidden-tab flush can delete the draft while the post is in flight. Failure then writes it back. I did not find a flush that writes a previous workspace’s text after the key has changed, except the `resetComposer` race.

## 5. The viewport sync

`syncDashboardViewport` (`DIFF.patch:909-918`) always `scrollTo(0, 0)` when the layout viewport is off the origin, then returns if there is no `visualViewport`. Coalesce is one `requestAnimationFrame` with no timer floor (`DIFF.patch:922-925`).

- Fighting the user: the shell is `overflow: hidden` and sized to the visible viewport, so page scroll is the iOS keyboard bug this is meant to undo. Pinch-zoom pan is `visualViewport.offsetTop`, not `window.scrollY`. `scrollTo(0, 0)` does not reset that offset. I did not prove a pinch fight.
- Loop: the callback zeros `viewportSyncFrame` first, then may scroll. A sync `visualViewport` scroll would queue one more frame. If already at 0,0 the next pass does not scroll. Not an infinite loop.
- Stale height: the autogrow path at `DIFF.patch:814-817` says a hidden tab and a headless run may never get an animation frame, and puts a 32ms timer under it. Viewport sync has the same rAF and no floor. If that rAF is dropped, `viewportSyncFrame` stays truthy and every later `requestDashboardViewportSync` returns without writing. The shell can keep a keyboard-sized height after the keyboard is gone. Init still calls `syncDashboardViewport()` directly, so first paint is fine.
- No `innerHeight`: with no `visualViewport` the custom property is left unset and `100dvh` applies (`DIFF.patch:898-902`). That is a missing measured height, not a wrong one. Current Safari/Chrome/Firefox expose `visualViewport`.

## 6. The caret block

`composerCaretKnown` starts false and is set true in `rememberComposerCaret` and on blur (`DIFF.patch:842-850`, `1028`). **It is never set back to false.** Not on send, not on `resetComposer`, not on draft restore.

Counterexample on desktop: type in workspace A (known=true, caret at 50) → choose workspace B. Textarea blur stores A’s caret. `resetComposer` clears the box and does not clear the flag. `restoreComposerDraft` fills B’s longer draft. `focusComposerOnEntry` skips only `max-width: 52rem` and then `focus({ preventScroll: true })` with no pointer on the textarea (`composerPointerAt` is only set from the textarea’s `pointerdown`, `DIFF.patch:1016-1017`). The focus handler restores A’s caret into B’s text (`DIFF.patch:1032-1037`). On a phone `focusComposerOnEntry` does not run, and a tap is inside the 500ms window, so this path is desktop.

500ms window: a tap’s `pointerdown` then `focus` is well under 500ms, so the tap’s caret wins. A genuine keyboard return more than 500ms after an unrelated press in the textarea could restore over a new caret. I did not find a common iOS sequence that does that. VoiceOver double-tap timing was not established.

`scrollComposerCaretIntoView` (`DIFF.patch:859-879`): end-of-text uses `scrollHeight` (correct for wraps). Mid-text counts hard `\n` only. The patch says a caret in a long wrapped paragraph can be a line or two off. A reader in the middle of a wrapped line would notice. The operator case (caret at the end) is the exact branch.
