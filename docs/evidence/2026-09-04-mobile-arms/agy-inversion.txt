### ATTACK A: Floating Band & Clearance Geometry
**Verdict: BROKEN**
- **Geometry Deficit:** In `site/src/components/app/LiveDashboard.astro:10161`, `.dashboard__channel-head` has `padding: var(--s-1) var(--s-4)` (`var(--s-1)` is `0.25rem` in `site/src/styles/tokens.css:319`, so vertical padding is `0.5rem`). Inside it, `.dashboard__roster-button` has `min-block-size: 2.75rem` (`LiveDashboard.astro:8066`). However, the clearance on `.dashboard__feed` is only `padding-block-start: 2.5rem` (`LiveDashboard.astro:10238`) (40px). The numbers do not add up: the floating roster cluster extends `0.75rem` (12px) past the clearance, directly overlapping the top right of the first message at rest.
- **Double Clearance on "Load Older Updates":** `.dashboard__feed-more` carries `padding-block-start: 2.5rem` (`LiveDashboard.astro:10242`), and `.dashboard__feed` directly below it also carries `padding-block-start: 2.5rem` (`LiveDashboard.astro:10238`). When older updates are present (`data-feed-more` visible), the transcript list adds an extra 2.5rem of blank clearance between the button and the first message.
- **Scroll-to-Bottom:** The composer sits in grid row 2 of `.dashboard__channel-body` (`LiveDashboard.astro:8301`), outside the scroller, so the bottom of the transcript is not covered by the composer. However, scrolling upward passes text and timestamps directly behind the floating chips and the transparent gaps between them.

### ATTACK D: `scrollTo(0, 0)` On VisualViewport & Window Resize
**Verdict: BROKEN**

When a user resizes their desktop browser window at 1440x900, `syncDashboardViewport` runs line `2635`: `if (window.scrollX !== 0 || window.scrollY !== 0) window.scrollTo(0, 0)`.

If a user scrolls down on any of these views and focuses a field or triggers a viewport change (or pinch-zooms on mobile), `syncDashboardViewport()` runs and forces `window.scrollTo(0, 0)`, immediately scrolling the user's active input off-screen.

### ATTACK E: Composer Bounds on Short Viewport (390x508)
**Verdict: HOLDS**
- Under `@media (max-width: 52rem) and (max-height: 36rem)` (`LiveDashboard.astro:10457`), `.dashboard__composer textarea` is styled with:
  `max-block-size: min(calc(var(--dashboard-viewport-height, 100dvh) * 0.25), 5rem);` (`LiveDashboard.astro:10492`).
- At 390x508:
  - `508px * 0.25 = 127px`.
  - `5rem = 80px` (at 16px root font size).
  - `min(127px, 80px) = 80px`.
- The composer is bounded by **`5rem` (80px)** at rest. If the software keyboard opens and reduces `--dashboard-viewport-height` below 320px, the `25%` rule engages.

### ATTACK F: New DOM in Old Machinery (Desktop Menu Keyboard Trap)
**Verdict: BROKEN**
- In `LiveDashboard.astro:240`, the diff adds:
  `<button class="dashboard__workspace-create-button dashboard__workspace-settings-item" type="button" role="menuitem" data-workspace-settings-item>`
- Above 52rem (desktop), CSS hides this button via `.dashboard__workspace-settings-item { display: none; }` (`LiveDashboard.astro:8944`).
- In `LiveDashboard.astro:2809-2811`:
  ```ts
  const workspaceMenuItems = (): HTMLButtonElement[] =>
    all<HTMLButtonElement>("[data-workspace-menu] [role='menuitemradio'], [data-workspace-menu] [role='menuitem']")
      .filter((item) => !item.hidden);
  ```
  In DOM specifications, `item.hidden` reflects the HTML `hidden` attribute, **not** CSS `display: none`. Because the button lacks the `hidden` attribute, `workspaceMenuItems()` includes it on desktop.
- **Keyboard Navigation Failure on Desktop:**
  - **`ArrowUp` on Trigger:** `openWorkspaceMenu("last")` (`LiveDashboard.astro:5510`) selects `items.at(-1)` (`LiveDashboard.astro:2831`), which is the `display: none` button. Calling `.focus()` on a `display: none` element is a no-op in HTML. Focus fails to enter the menu.
  - **`End` inside Menu:** Keydown handler (`LiveDashboard.astro:5521`) sets `nextIndex = items.length - 1` and calls `.focus()` on the `display: none` item. Focus is lost.
  - **`ArrowDown` from Last Visible Item:** From `New workspace` (`items.length - 2`), `ArrowDown` (`LiveDashboard.astro:5524`) selects index `items.length - 1`. Focus call no-ops, stranding focus on `New workspace` and preventing wrap-around to the first workspace.

### ATTACK H: Caret Restoration on Restored Drafts
**Verdict: BROKEN**
- `composerCaret` initializes to `{ end: 0, start: 0 }` (`LiveDashboard.astro:2568`).
- `restoreComposerDraft()` (`LiveDashboard.astro:2536`) sets `input.value = draft.body`, but does not update `composerCaret`.
- On desktop, `focusComposerOnEntry` (`LiveDashboard.astro:2553`) programmatically calls `input.focus({ preventScroll: true })` whenever a workspace is opened. On any device, pressing `Tab` also brings focus without a pointer.
- Because no pointer event occurred within 500ms, the `focus` listener (`LiveDashboard.astro:5719`) triggers `restoreComposerCaret()`:
  ```ts
  input.setSelectionRange(
    Math.min(composerCaret.start, length),
    Math.min(composerCaret.end, length),
  );
  ```
- Because `composerCaret` is `{0, 0}`, `input.setSelectionRange(0, 0)` executes and `scrollComposerCaretIntoView()` scrolls to line 0.
- **Result:** On every workspace entry or keyboard navigation into a restored draft, the caret is slammed to the start of the draft (`index 0`), causing new keystrokes to be prepended rather than appended.

### Finding Rankings

#### BLOCKER
1. **Desktop Workspace Menu Keyboard Trap (`LiveDashboard.astro:2809-2811`):** `workspaceMenuItems()` includes CSS-hidden `<button data-workspace-settings-item>` because `!item.hidden` does not check CSS `display: none`. Breaks `ArrowUp` on trigger, `End` in menu, and `ArrowDown` wrap-around on desktop.
2. **Data Loss & Cross-Workspace Draft Deletion (`LiveDashboard.astro:2781`, `4649`, `6005`):** `resetComposer()` fails to cancel pending draft timer on workspace switch, causing `persistComposerDraft()` to delete Workspace B's draft under Workspace B's key. Sending via Enter clears input while leaving a timer that deletes new draft text upon network completion.
3. **Accidental Public Broadcast on Mention Autocomplete (`LiveDashboard.astro:5784-5816`):** Pressing Enter within 150ms of typing `@word` bypasses autocomplete due to debounce and submits a broadcast message to `{ kind: "everyone" }`.

#### SHOULD-FIX
4. **Caret Reset to Index 0 on Restored Drafts (`LiveDashboard.astro:2568`, `5717`):** Uninitialized `composerCaret` causes `restoreComposerCaret()` to reset selection to position 0 on desktop workspace entry and Tab navigation.
5. **Clearance Deficit & Content Overlap (`LiveDashboard.astro:10161`, `10238`):** `3.25rem` floating channel head exceeds `2.5rem` transcript clearance padding by 12px, overlapping the first message at rest.
6. **Unconstrained `window.scrollTo(0, 0)` Execution (`LiveDashboard.astro:2635`, `2649`):** Fires globally on desktop resize and forces scroll jumps on scrollable non-channel views.
7. **Weakened Test Suite Assertions (`mobile-feed-layout.observer.test.ts`, `header-roster.observer.test.ts`):** Removed upper bounds on header heights, eliminated ratio floors, deleted grid placement checks, and added synthetic lifecycle dispatches.

#### NIT
8. **Consistent CSS Fallbacks (`LiveDashboard.astro:6309`):** All 10 `--dashboard-viewport-height` CSS usages have `100dvh` fallbacks.
9. **Composer Short-Viewport Bounding (`LiveDashboard.astro:10492`):** Correctly bounded by `5rem` (80px) at 390x508.

VERDICT: FAIL
