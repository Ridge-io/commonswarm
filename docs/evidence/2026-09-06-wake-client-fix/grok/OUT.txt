**(1) next() / finishWait() order-of-operations**

origin/main `next()` builds a `finish` closure whose first statement is `if (this.waiter === null) return;`, then stores `resolve: finish` on the waiter. `finishWait()` at `src/listener/wake.ts:418-427` (HEAD numbering; body unchanged vs origin/main) does:

```
const waiter = this.waiter;
if (waiter === null) return;
this.waiter = null;
clearTimeout(waiter.timer);
remove abort listener;
waiter.resolve(reason);
```

On origin/main, `waiter.resolve` IS `finish`. `finishWait` has already nulled `this.waiter`, so `finish` returns before the Promise resolve. The deadline timer is cleared as a side effect of the failed teardown, so the wait never settles.

HEAD `next()` at `src/listener/wake.ts:362-377` stores the raw Promise `resolve` and routes the timer and abort listener through `finishWait`:

```
setTimeout(() => this.finishWait("deadline"), delay)
onAbort = () => this.finishWait("deadline")
this.waiter = { resolve, timer, onAbort, signal }
```

One guard. `finishWait` nulls waiter, clears the timer, removes the abort listener, then calls resolve once. A second `finishWait` sees `waiter === null` and returns. Confirmed by reading both versions, not by the comment.
