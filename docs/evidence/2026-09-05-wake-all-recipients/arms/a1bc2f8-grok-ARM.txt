## 1. Tenancy and authorization — PASS

`hydrateDeliveryRefs` and the `expired` ack keep `s.workspace_id = args.workspaceId` and `s.id` pinned. The new arm is:

```
EXISTS (
  SELECT 1 FROM swarm.signal_recipients AS addressed
  WHERE addressed.signal_id = s.id
    AND addressed.workspace_id = s.workspace_id
    AND addressed.recipient_agent_principal_id = <claimer>
)
```

`20260905000010` gives that table `FOREIGN KEY (signal_id, workspace_id) REFERENCES swarm.signals (id, workspace_id)` and `FOREIGN KEY (recipient_agent_principal_id, workspace_id) REFERENCES swarm.agent_principals (principal_id, workspace_id)`. A recipient row cannot point at another tenant. `principal_id` is a global PK, so the same agent uuid cannot live in two workspaces.

The EXISTS arm only matches an **agent** principal. A person row (`recipient_user_id` set, agent column null) cannot satisfy it. The scalar `OR` is the old path and is still workspace-scoped.

`hydrateDeliveryRefs` is only called with signal ids from `claimAgentInbox`, which already selected `recipient_agent_principal_id = claimer`. Replay takes those same stored refs; a tampered extra id that the claimer is not addressed on makes hydrate return null and the handler answers 403. The expired path looks up the delivery row on `(workspace_id, signal_id, recipient_agent_principal_id)` first; if that row is missing it returns `unavailable` before the TTL SELECT.

I could not build a row set that lets an unaddressed agent read a body or probe another workspace.

The comment that this is “the same set the read view uses” is slightly loose: the view also admits the owner of an addressed agent via `auth.uid()`. Hydrate is narrower (this principal, not the owner). That is fail-closed, not a leak.

## 3. Double wake and lost wake — PASS

Firing order is fixed by `signal_recipients_same_transaction`: recipient rows may be inserted only while the parent signal belongs to this xact, so the signal INSERT (and `signals_enqueue_delivery`) always runs first. Position 0 that is an agent is written twice; `ON CONFLICT DO NOTHING` hits `PRIMARY KEY (signal_id, recipient_agent_principal_id)` and keeps one row. The p1-local test counts **rows**, so a swallowed duplicate would show as 3, not as 2.

`signal_recipients_first_is_the_scalar` is `DEFERRABLE INITIALLY DEFERRED`. Enqueue is an immediate `AFTER INSERT` row trigger. If position 0 does not match the scalar, the xact aborts at commit and the delivery rows go with it.

Bare `ON CONFLICT DO NOTHING` (no target) swallows any unique or exclusion violation. `signal_deliveries` has only that PK. A later unique index could be swallowed silently. Today there is none, so it is equivalent to conflicting on the PK.

Lost wake for a wakeable agent: person at 0, agent later — scalar trigger no-ops (`to_agent_principal_id` is null), recipient trigger writes the agent. Measured on both the local and served tests. Scalar-only posts (no `to` list) still take only the signal trigger.

## 4. The three new refusal clauses — PASS

**`until > statement_timestamp()`.** Reachable only for a backdated direct insert. `20260724000003_signals.sql` has unnamed `CHECK (until > created_at)`. Postgres names that table check `signals_check`. The edge writes `created_at = statement_timestamp()` with `until` later than that. A normal edge post is never dead on arrival. The comment’s reach is accurate. Nothing live depends on enqueueing an already-dead signal.

**`revoked_at IS NULL`.** Reachable. Old trigger wrote a row `claimAgentInbox` step 1 can never take, so it sat in `pending_delivery_count` for ever. Refusing it is the fix. The comment is accurate. Revocation **after** enqueue is still open; the migration says so.

**Self.** The clause is gone. The command edge does not refuse self-address: `post_signal` has no `from_principal === to_agent` check. `runListenerAttendanceCanary` still posts `to_agent_principal_id: options.principalId`. The predicate has no self filter and no position filter, so a self-note wakes at every position. See round two.

## 5. Concurrency and claim/ack — PASS

`claimAgentInbox` steps 1–7 still key every lock, lease cap, pending count, poison ceiling, and `SKIP LOCKED` on `recipient_agent_principal_id`. Two recipients of one signal are two PK rows. They do not share a lease, an attempt counter, or a `FOR UPDATE` target.

`DELIVERY_MAX_OUTSTANDING_LEASES` (100) and `pending_delivery_count` / `oldest_pending_at` are per principal. Waking N agents does not enlarge one listener’s cap. `SKIP LOCKED` ordering is still `enqueued_at, signal_id` for that principal.

Two listeners on the **same** signal now run at once. Client `parseClaimSuccess` still refuses two deliveries in **one** claim response; that is one principal, one row per signal, unchanged. The pending-main queue uniqueness is per instance directory (per principal). Effect files are per instance. Receipts already keyed `(signal_id, recipient_agent_principal_id)`. I did not find a claim/ack invariant that assumed one delivery row per signal across principals.

## 6. Wire compatibility — PASS

`parseClaimLedger` still reads only body-free `delivery_refs`. It does not require `recipient_position` / `recipient_count`. Replay of an old stored ledger still parses, then `hydrateDeliveryRefs` fills the new fields on the **hydrated** response. `command/index.ts` replay (both the existing-key path and the race-winner path) goes through that pair.

A 0.1.55 client: `parseSignalRecord` ignores unknown keys; old `parseDeliveryRow` never used exact keys on the row; extra `recipient_position` / `recipient_count` / `recipient_fanout` are ignored. `to_agent` is the claimer, so the own-principal check passes at position 1. Ack does not send the new fields. The served test `accepted0155` is that reproduction.

A new client: both fields absent → nulls (old server). Half pair refused — a capable server always sends both (`COALESCE`/`GREATEST`, required on `HydratedDelivery`). `position >= count` or `count < 1` cannot come out of the live constraints plus those two expressions. `checkedClaimCapabilities` still requires only the original three markers `=== 1` and ignores extras.

## 7. `channels` read resource — PASS

Same two walls as every other agent resource: `workspace_id !== principal_workspace_id` returns `{ channels: [] }` **before** claims are installed; the query then runs as `swarm_read` with the owner’s `sub` on `swarm_read.channels`, which is `GRANT`ed to `swarm_read` and gated on `swarm.is_member(workspace_id, auth.uid())`. Another workspace cannot return another tenant’s rows.

Empty-envelope branch sits with `members` / `files` / `delivery_receipts` / `renewal_grants`, not after the query.

Human JWT: `if (!agentCredential && body.resource !== "renewal_grants") return 401`. `channels` is not `renewal_grants`. A browser session cannot reach the arm. The p1-server control measures 401.

The SELECT is generated from `CHANNEL_READ_COLUMNS`. Identifiers come from that `as const` array; the one value is `$1`. It is not a third typed copy of the list.
