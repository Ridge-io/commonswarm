## 1. Tenancy and authorization — PASS

`hydrateDeliveryRefs` and the `expired` ack both keep `s.workspace_id = args.workspaceId` and `s.id` pinned. The new arm is:

```
EXISTS (
  SELECT 1 FROM swarm.signal_recipients AS addressed
  WHERE addressed.signal_id = s.id
    AND addressed.workspace_id = s.workspace_id
    AND addressed.recipient_agent_principal_id = <claimer>
)
```

`20260905000010` gives that table `FOREIGN KEY (signal_id, workspace_id) REFERENCES swarm.signals (id, workspace_id)` and `FOREIGN KEY (recipient_agent_principal_id, workspace_id) REFERENCES swarm.agent_principals (principal_id, workspace_id)`. A recipient row cannot point at another tenant. `principal_id` is a global PK, so the same agent uuid cannot live in two workspaces.

The EXISTS arm only matches an **agent** principal. A person row (`recipient_user_id` set, agent column null) cannot satisfy it. The scalar `OR` is the old path and is still workspace-scoped.

`hydrateDeliveryRefs` is only called with signal ids from `claimAgentInbox`, which already selected `recipient_agent_principal_id = claimer`. The expired path looks up the delivery row on `(workspace_id, signal_id, recipient_agent_principal_id)` first; if that row is missing it returns `unavailable` before the TTL SELECT. I could not build a row set that lets an unaddressed agent read a body or probe another workspace.

The comment that this is “the same set the read view uses” is slightly loose: the view also admits the owner of an addressed agent via `auth.uid()`. Hydrate is narrower (this principal, not the owner). That is fail-closed, not a leak.

## 3. Double wake and lost wake — PASS

Firing order is fixed by `signal_recipients_same_transaction`: recipient rows may be inserted only while the parent signal belongs to this xact, so the signal INSERT (and `signals_enqueue_delivery`) always runs first. Position 0 that is an agent is written twice; `ON CONFLICT DO NOTHING` hits `PRIMARY KEY (signal_id, recipient_agent_principal_id)` and keeps one row. The p1-local test counts **rows**, so a swallowed duplicate would show as 3, not as 2.

`signal_recipients_first_is_the_scalar` is `DEFERRABLE INITIALLY DEFERRED`. Enqueue is an immediate `AFTER INSERT` row trigger. If position 0 does not match the scalar, the xact aborts at commit and the delivery rows go with it. No leftover double or zero.

Bare `ON CONFLICT DO NOTHING` (no target) swallows any unique or exclusion violation. `signal_deliveries` has only that PK. A later unique index could be swallowed silently. Today there is none, so it is equivalent to conflicting on the PK.

Lost wake for a wakeable agent: person at 0, agent later — scalar trigger no-ops (`to_agent_principal_id` is null), recipient trigger writes the agent. Measured on both the local and served tests. Scalar-only posts (no `to` list) still take only the signal trigger. Self/revoked/expired zeros are the new predicate, not an ordering bug.

## 4. The three new refusal clauses — FAIL

**`until > statement_timestamp()`.** Reachable only for a backdated direct insert, or a 1 ms floor plus a slow recipient-insert loop. `signals` has unnamed `CHECK (until > created_at)` (PG name `signals_check`) and the edge writes `created_at = statement_timestamp()` with `until` at least 1 ms later. A normal edge post is never dead on arrival. The comment’s reach is accurate enough. It refuses a shape the old trigger would enqueue. Nothing live depends on enqueueing an already-dead signal. This clause is fine.

**`revoked_at IS NULL`.** Reachable. Old trigger wrote a row `claimAgentInbox` step 1 can never take, so it sat in `pending_delivery_count` for ever. Refusing it is the fix. The comment is accurate.

**Self.** Reachable, and the command edge does **not** refuse it: `resolveSignalWriteTarget` only checks liveness. The comment is right about the edge.

It **does** refuse something that used to work and that this repo depends on. `runListenerAttendanceCanary` posts a self-note with the agent credential:

```
to_agent_principal_id: options.principalId
body: "CommonSwarm listener attendance canary. No reply is needed."
```

`cswarm listen canary` is that path. `from_kind = 'agent'` and `from_principal =` the same principal, so `agent_delivery_is_wakeable` is false on the scalar trigger. No delivery row. The canary stalls at `claimed`. The p1-local test now **locks that in** (`"an agent does not wake itself"`). The clause is applied to the scalar path, not only to fan-out, so the “group I belong to” rationale also kills the supported self-note.

That is a real behaviour change with a first-party caller, and this lane does not update the canary.

## 5. Concurrency and claim/ack — PASS

`claimAgentInbox` steps 1–7 still key every lock, lease cap, pending count, poison ceiling, and `SKIP LOCKED` on `recipient_agent_principal_id`. Two recipients of one signal are two PK rows. They do not share a lease, an attempt counter, or a `FOR UPDATE` target.

`DELIVERY_MAX_OUTSTANDING_LEASES` (100) and `pending_delivery_count` / `oldest_pending_at` are per principal. Waking N agents does not enlarge one listener’s cap. `SKIP LOCKED` ordering is still `enqueued_at, signal_id` for that principal.

Two listeners on the **same** signal now run at once. Client `parseClaimSuccess` still refuses two deliveries in **one** claim response; that is one principal, one row per signal, unchanged. The pending-main queue uniqueness is per instance directory (per principal). Effect files are per instance. Receipts already keyed `(signal_id, recipient_agent_principal_id)`.
