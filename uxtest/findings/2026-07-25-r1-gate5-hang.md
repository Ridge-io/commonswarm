## 3. WHAT IS REFUTED — recorded so nobody re-derives a dead end

- **"swarm's runtime becomes the node shim."** Dana's proposed mechanism, offered explicitly as
  unasserted. Refuted by reading `resolve_node()`'s *implementation* rather than its comment:
  order is `$SWARM_NODE` → `~/.swarm/node-path` → `command -v node`. `~/.swarm/node-path` **exists**
  on the laptop, is executable, and holds the same real node the shim delegates to. The pin is
  consulted **before** PATH, so swarm never resolves through the shim.
- **"origin outside the GUI session is the predicate."** Atlas's §1.2 hypothesis. Refuted by Dana's
  test B, which created a tab **from the same tool-layer subprocess in the same turn** as the
  hanging test A. Subprocess origin is not the predicate. Sound reasoning, wrong predicate — worth
  killing loudly, because it points at a structural platform wall when the cause is one PATH entry.
- **"the cmux socket is the blocker."** From SSH, `cmux ping` returns *"Access denied — only
  processes started inside cmux can connect"*: a **fast error, not a hang**. From inside, Dana gets
  `PONG` and `access_mode: cmuxOnly`. ★ This does incidentally give §1.2 its mechanism: the
  GUI-origin rule has always been right and its reason was guessed — it is an **explicit access
  control**, not a platform quirk. Worth folding into §1.2.

**WHAT IS STILL OPEN: the *why*.** `readlink`, `head`, `cat`, `grep`, `sed`, `tail`, `ls`, `find`,
`which` and `realpath` are all shimmed, and swarm's launcher calls `readlink` and `head` — so the
shims *do* intercept it, just not via node. But the shim only spawns its node logger when
`violating=true`, and neither `readlink /opt/homebrew/bin/swarm` nor `head -1 ~/.swarm/node-path`
touches a `$root` path, so both should fall through to `exec`. **That does not obviously hang
either.** One mechanism refuted, none confirmed. *Which variable* is proven and sufficient to fix
it; nobody should assert *why* without a test.

## 7. ★ SEPARATE FINDING — §7.2.2's ISOLATION ASSERTION IS A GATE THAT CANNOT FAIL

Found while checking whether the PATH trade-off was real. **It is independent of the hang and of R1
ever running**, and it is the more serious of the two.

§7.2.2 promises personas get a **copied** `coswarm` at `~/uxtest/bin` on their PATH, never a symlink
into the repo, and states that preflight asserts it. What preflight actually does — `preflight.sh:126`,

```bash
mini_resolved="$(PATH="$UXTEST_MINI_HOME_ROOT/bin:$PATH" command -v coswarm)"
[ "$mini_resolved" = "$mini_bin" ] || die "mini persona PATH does not resolve to the isolated launcher"
```

**It prepends a directory to PATH and then confirms `command -v` honours PATH precedence** — a
property of the shell, not of the harness. Atlas confirmed this *by construction* rather than by
reading: a throwaway directory containing a fake `coswarm` passes the identical check.

Sharpened (Atlas): it does not merely fail to observe the persona's PATH — **it cannot observe any
PATH it did not itself write.** The neighbouring checks are real and *do* discriminate: `:124`
executable, `:125` not-a-symlink, `:129-131` not-inside-the-repo. **Only the resolution assertion is
empty, and it is the one carrying §7.2.2's name.**

### Why this matters more than the hang

The open question is whether a cmux-created tab inherits the **spawning process's** PATH or the
**cmux app's** (pid 96420, running since long before any uxtest PATH existed).

- **Inherits from the spawn** → the isolation shims reach the persona, §7.2.2 holds, and the PATH
  trade-off in §4.2 is real.
- **Inherits from the app** → the persona never had the shim *or* its isolated `coswarm` copy. §7.2
  isolation was never in force, and preflight's construction could not possibly have detected it.

**No round has run, so nothing is retroactively voided.** But a round run before this is settled
could report clean isolation that was never enforced — and the gate that is supposed to catch that
is the one demonstrated above to be incapable of failing.

**Cheapest resolution:** in any existing cmux tab on the laptop, `echo "$PATH"; which coswarm`. No
spawn, no round state, seconds. A tab that lacks `uxtest/bin` shows a cmux tab does not carry it by
default, which reduces the question to whether a spawn's PATH propagates into the tab it creates.

## 9. ★ THE BUNDLE IS PINNED; THE RUNTIME IS NOT — and preflight cannot see the difference

Found while auditing the harness against Vane's non-login-shell finding. **Same class as §7: preflight
verifies a property of an object it constructs, not the object the persona uses.**

`dist/cli.js` opens `#!/usr/bin/env node`, so `coswarm` resolves its runtime **from PATH at execution
time**. Measured on the laptop:

| Actor | How node is resolved | Version |
|---|---|---|
| `preflight.sh` version gate | the pinned `product/NODE_BIN` | **v24.14.1** |
| a login **interactive** shell (`zsh -lic`, what `remote_zsh` uses) | nvm | **v24.14.1** |
| a login **non-interactive** shell (`zsh -lc`) | `/opt/homebrew/bin` | **v25.9.0** |
| **a spawned persona tab** | the cmux app's PATH, which Dana measured as containing `/opt/homebrew/bin` and **not** `uxtest/bin` | **v25.9.0 — strongly supported, not directly measured** |

So the harness certifies the bundle under one runtime and the persona would execute it under another.
§1.1 makes the `dist/` SHA-256 manifest "the sole version authority" — that is a statement about the
**code**, and it is satisfied. Nothing in the harness pins or observes the **runtime**, and
preflight's `--help` comparison runs under `NODE_BIN` on *both* machines, so it is structurally
incapable of detecting the difference.

§7.5 lists version skew as a confounder preflight must fail closed on. It fails closed on bundle
skew. **Runtime skew is invisible to it.**

★★ **CORRECTION, AND THE SKEW IS BIGGER THAN THIS SECTION FIRST SAID (Vane, measured).** I framed
it as preflight-vs-persona-tab on one machine. **The skew is ACROSS THE TWO MACHINES whose comparison
is the entire point of the harness.** Confirmed by my own execution:

```
mini    NODE_BIN -> /opt/homebrew/bin/node                     v26.5.0
laptop  NODE_BIN -> /Users/tom/.nvm/…/v24.14.1/bin/node        v24.14.1
```

**Two major versions apart.** Mechanism, one line, twice: `sync-machine2.sh:123` and `:161` do
`command -v node > NODE_BIN` — **so NODE_BIN is a SNAPSHOT OF WHOEVER INSTALLED, not a pin.** On the
mini the installing shell is the script's own (homebrew); the laptop half runs through `remote_zsh`
(`zsh -lic`), which loads nvm. Nothing declares an intended version.

★ **`preflight.sh` compares the two `--help` OUTPUTS and never the two runtimes** (`:161-171`). Each
machine runs the CLI under its own `NODE_BIN`, and only the version *line* is compared — so identical
output under different interpreters passes.

★★ **CORRECTION TO MY OWN PROPOSED FIX (Vane), AND IT IS THE IMPORTANT PART.** I first wrote *"one
equality check closes it, in a function that already has both values."* **IT DOES NOT HAVE BOTH.**
The laptop's node path is assigned *inside* the `remote_zsh` string — which executes on the laptop —
and only stdout crosses the wire:

```bash
mini_node="$(<".../NODE_BIN")"                    # local, kept
laptop_version="$(remote_zsh "
  node_bin=\$(cat '.../NODE_BIN')                 # SUBSHELL-LOCAL, discarded
  \"\$node_bin\" '.../dist/cli.js' --help | head -n 1   # only this returns
")"
```

**So the naive one-liner would compare a real value against a variable that does not exist locally.**
The remote half has to *return* its node path (and ideally its version) before anything can compare
them. I proposed a fix that would have planted a defect while closing one — which is the same shape
as §7 and worth recording as a near-miss rather than quietly fixing.

★ **But the failure direction Vane gave is the opposite of the real one, and I checked rather than
accepting it.** Vane wrote that the check would *"pass silently"* — a new gate that cannot fail.
`preflight.sh` runs under `set -euo pipefail`, and I measured it: referencing the unset variable
raises **`laptop_node: unbound variable`** and kills the script. So the naive fix produces a **loud
false RED**, not a silent green. Both are wrong; they are wrong in *opposite directions*, and the
distinction decides which is more dangerous. A gate that always dies gets fixed within the hour. A
gate that always passes is what §7 is about. **We would have got the safe failure.**

★★ **SEVERITY CUTS THE OTHER WAY, AND IT IS MEASURED (Vane).** One bundle shipped to the laptop,
verified byte-identical at both ends, executed under both runtimes with only the interpreter
changed: `--help`, the `--url is required` path, `workspace create` usage, and the not-logged-in
`feed` path all produced **byte-identical output**. **Observed behavioural risk on reachable paths:
zero.**

★ **But only OFFLINE paths were reachable** — arg parsing, usage, unknown-command, not-logged-in.
**Not exercised:** TLS/undici, webcrypto in the PKCE flow, keychain child processes, any Supabase
client I/O — i.e. exactly where node majors actually diverge. They were unreachable because that
laptop has no login, which is the same door everything else is behind. And v26.5.0 was not tested
against either, because the mini has only v26.

**Recommended disposition (Vane, and I agree): fix as a declared pin plus a cross-machine equality
check in preflight. NOT an R1 blocker on top of the isolation one.** The gate hole is real,
confirmed and structural; the demonstrated risk is not.

★ **Honest limit:** the persona-tab row is inferred from Dana's `ps -Eww` measurement of spawned tabs'
PATH, not from running `node --version` inside one. The four orphan surfaces (§6) make that directly
measurable by anyone with GUI access to the laptop, and it should be measured before this row is
treated as fact.

★ **And the interactivity split is itself worth knowing:** `zsh -lc` and `zsh -lic` resolve
*different node versions* on that machine. Any probe that picks one and reports it as "the machine's
node" is §3's right-property-wrong-object. `remote_zsh` uses `-lic`; Vane's audit used `-lc`; both
are correct about their own shell and neither is the persona's. (Vane, on the dogfood doc's
`command -v` findings.)

## 10. ★ KNOWN CONTAMINATION IN THE MEASUREMENT SUBSTRATE — exclude before counting anything

§4.1 makes metrics *"server-authoritative DB event timestamps, not parsing the chat"*. That
substrate is **not clean**, disclosed by Ledger before measuring rather than discovered afterwards:

- **6 real signals** posted into Dogfood Workspace `3ab184b3-fbb4-5ee9-afad-3842a604439a`, bodies
  marked `infra latency probe N (Ledger, ignore)`, TTL 1m. They age out of the default feed — **but
  signals are immutable, so they persist under `--include-stale`.**
- **`swarm.audit_log` driven from 19 to 45 rows** — 20 malformed unauth probes plus those 6 posts.

**Exclude both from any R1 or dogfood count.** A round that counts rows without this exclusion will
report contaminated numbers with a clean-looking provenance, which is precisely the failure mode
§4.1 was written to avoid.

★★ **AND THE BIGGER HALF, WHICH IS NOT ABOUT LEDGER'S SIX ROWS: `audit_log` IS AN UNAUTHENTICATED,
STRUCTURALLY UNLIMITABLE WRITE PATH.** Raised by Ledger, verified by me in the source:

- `enforceSignalRate` (`supabase/functions/command/index.ts:2161`, called at `:2518`) takes an
  `AuthContext` and keys its bucket on `auth.credentialKind` + `credentialId`/`actor.user`, throwing
  if there is no stable identity. **It cannot run before the caller is identified.**
- `:2518` sits inside the transaction, *after* the workspace-membership authz check.
- `insertAudit` (`:654`) begins `const auth = audit.auth ?? null` — **auth is optional** — and
  `standaloneAudit` (`:681`) wraps it in its own transaction. Its call sites include pre-auth
  validation failures: a malformed `command_id` writes an audit row and returns 400 **before any
  authentication happens.**

So the write is not merely unlimited in practice; **it is unlimitable by the mechanism that exists**,
because a limiter keyed on identity cannot protect a path that runs before identity exists.

★ **Consequence for §4.1, and it is larger than the disclosed contamination: `audit_log` ROW DELTAS
ARE NOT A SAFE METRIC SUBSTRATE.** Any unauthenticated traffic to `/command` — a scanner, a
misconfigured client, another agent's probe — inflates the table. A round that counts rows must
control for malformed unauthenticated requests, or it is measuring the internet as well as the
persona. **This is a property of the system, not of anyone's cleanup.**

★★ **THE LATENCY LIMIT IS LIFTED AND REPLACED BY A REQUIREMENT — THE AGENT PATH IS 6.6x SLOWER.**
This section previously said the agent measurement did not exist. Lead6 cleared an agent-token mint,
Ledger timed it, and it now does (same workspace, same three signals, same view, n=15, TTFB p50):

```
HUMAN  feed via rest/v1/signals   ->  95 ms
AGENT  feed via functions/v1/read -> 625 ms      6.6x
```

**R1's whole subject is what an AGENT-DRIVEN persona experiences.** So the persona's feed is the
625ms path, not the 95ms one, and **any round reporting "feed latency" without naming the credential
kind is off by a factor of six.** Requirement, replacing the old prohibition: **every latency claim
in a REPORT must state which credential produced it.**

★ **And the cause is structural, not incidental** (Ledger's model, which holds to 5% across both
edge functions): `latency ≈ boot floor + (DB round trips × ~32ms)`. The read function makes **13
sequential round trips** for one feed. **Six of them compute nothing** — I verified them in the
source at `supabase/functions/read/index.ts:137-140` (`SET TRANSACTION ISOLATION LEVEL`, `SET LOCAL
ROLE`, `SET LOCAL search_path`, `SET LOCAL lock_timeout`) and `:175-176` (`SET LOCAL ROLE`, `SET
LOCAL search_path` again). Each is its own `await tx.unsafe(...)`, so they **serialise**. The human
path is one PostgREST query (`src/cloud/signals.ts:103`). That accounts for the entire gap.

**Consequence for R1's validity, not just its numbers:** a persona that feels the product is slow is
feeling six no-op round trips, and a report that attributes that to product design would be wrong
about the cause while being right about the experience.

## 11. ★ R1 CANNOT NAME THE COMMIT IT TESTS — §7.7's "version under test" is not a version

Found while running Lead6's dogfood-validity check. **The equality claim is sound; the provenance
claim does not exist.**

§7.7 requires every REPORT to state *"Version under test: mini `<sha>` / laptop `<sha>` (must
match)"*, and §1.1 makes the `dist/` SHA-256 manifest *"the sole version authority"*. Measured:

```
SOURCE_SHA is bundle_sha of product/dist          sync-machine2.sh:125, :170
dist/ is gitignored                                .gitignore:2 — 0 tracked files
SOURCE_SHA f12b47b8…  ->  NOT A GIT OBJECT
run/synced-source.sha 910c399f…  ->  also a bundle hash, not a commit
```

**Nothing in the harness records a commit.** So a report can truthfully say *both machines ran
identical bytes* — which is real, valuable, and exactly what the fail-closed gate enforces — and
**cannot say which source those bytes were built from.** A reader in six months has a content hash
that maps to nothing they can check out.

★ **This is not the same defect as §9.** §9 is *the runtime is unpinned while the bundle is pinned*.
This is *the pinned bundle has no provenance*. Together: R1 knows its two machines agree, and knows
neither what code they agree on nor what interpreter runs it.

★ **And the obvious fix is wrong in the obvious form.** §1.1 states plainly that *"the laptop's Git
HEAD is not a version signal for this harness"* — source is rsynced while its git history
intentionally lags — so recording the laptop's HEAD would record a lie. **The mini's HEAD at sync
time is the meaningful one**, because the mini is the rsync source. The two facts do different jobs
and both are needed:

- `SOURCE_SHA` — proves the two machines **match**. Keep exactly as is; it is the fail-closed gate.
- a recorded **mini commit at sync time** — says what they match **to**. Currently absent.

**Suggested, not applied** (nothing is applied here, by ruling): have `sync-machine2.sh` write the
mini's `git rev-parse HEAD` plus dirty-flag beside `SOURCE_SHA`, and have §7.7 print both.

★★ **BUT A DIRTY FLAG CANNOT DETECT A STALE BUNDLE, AND THAT IS TRUE BY CONSTRUCTION (Ledger).**
`dist/` is gitignored, so **git cannot see the built artifact at all** — `git status` reports a clean
tree whose bundle is arbitrarily old. Demonstrated on the mini at the time of writing:

```
git status --porcelain (tracked)          0 changes  — CLEAN
dist/ visible to git                      NO (gitignored)
src/cloud/config.ts   ship-3 string:  1   mtime 18:00:45
dist/cli.js           ship-3 string:  0   mtime 18:00:44
```

**A clean tree, a source containing the fix, and a bundle that does not.** So `HEAD + dirty` would
record *"built from `<commit>`, tree clean"* — **true about the source and false about the bytes.**

★ **And note the mtimes are ONE SECOND apart**, with the bundle *older*. Any staleness check based on
mtime ordering is operating at its own resolution limit here — which is Ledger's quantisation finding
(*"a threshold placed within the instrument's quantisation is a coin"*) applied to the check one would
naturally reach for. **The content comparison shows a real gap that the timestamp comparison nearly
misses.**

★ **So the fix needs a third element, and the cheap one already exists:** record the mini's HEAD, the
dirty flag, **and** the bundle hash — which `SOURCE_SHA` already is. **The pair `(commit, bundle_hash)`
is falsifiable**: a future reader rebuilds from the commit and compares. Without that, the recorded
commit is a claim about source the bytes do not have to honour. The alternative Ledger offers —
*build at sync time from the recorded SHA* — closes it at the source instead, and is stronger if the
sync path can afford a build.

★★ **CORRECTION TO THIS SECTION, SAME TURN IT WAS WRITTEN (Atlas).** I wrote that the source is
unrecoverable. **I had not tried.** Atlas flagged that a search might find it and said plainly it had
not attempted one either. I attempted it:

```
a62823a  Jul 24 16:46  "uxtest: GUI-origin rule — serve must originate in the GUI session"
harness build mtime    Jul 24 16:47:06      <- ONE MINUTE LATER
SUCCESSION §0d         "HEAD `a62823a`, tree clean"   <- Lead4's baton, that same moment
```

**There is a strong candidate with independent corroboration**: a commit one minute before the
build, and a baton written at that time naming it as HEAD with a clean tree. So the honest status is
**"provenance is not RECORDED, but is probably RECOVERABLE"** — which is a materially weaker defect
than the one this section originally claimed.

★ **It is a candidate, not a confirmation, and verifying it costs something I declined to spend.**
Confirmation means checking out `a62823a`, rebuilding, and comparing `bundle_sha` to `f12b47b8…`.
Two reasons not to, tonight:

1. **Rebuilding in the shared tree overwrites `dist/`** — which is exactly what the global `coswarm`
   resolves to and what the fleet measured tonight. That is the shared-tree hazard, and verifying a
   provenance claim by mutating the artifact everyone else is running is a bad trade.
2. The envelope is the condition closest to firing (swap 6112M of 7168M at this reading), and a
   full `npm install` + build is the heaviest thing available.

**A worktree build would avoid (1) and not (2).** Recorded as the cheap next step for whoever picks
this up with the machine quiet: worktree at `a62823a`, build, compare — one comparison either
confirms the provenance or proves it genuinely lost.

★ **Why it matters beyond bookkeeping:** the fleet spent tonight establishing that a build with no
ref is a measurement with no timestamp. **R1's version gate is that exact object, and it is the gate
whose output goes into the validity header of every future round.**
